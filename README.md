# BLOSTOM

ブロックでロボを組み立てて戦わせる、ロボット対戦ゲーム。
**タイトル画面**から入り、**ソロプレイ**（ウェーブ制の実戦）と
**テストフィールド**（ルール無しの練習場）、**エディタ**、**パーツ編集（ワークベンチ）** を行き来する。

運動モデルは `ZMF (ZOE Motion Framework) Core v1.0.0` をそのまま実装している。

ブラウザでもデスクトップアプリでも、**同じコードがそのまま動く**。
配信するのは後者（7節）。

```bash
npm install

npm run dev      # ブラウザで開発する
npm run game     # デスクトップアプリとして起動する（Steam配信と同じ形）
```

テスト:

```bash
npm test
```

描画・DOM を含む全網羅テストは `npm run dev` してから `/tests.html` を開く（詳細は 6 節）。

## 1. 画面

| | |
|---|---|
| **TITLE** | 入口。**組んだ機体がそのまま台の上で回っている**。↑↓ と Enter、またはクリックで選ぶ。 |
| **SOLO** | ソロプレイ。ウェーブで出てくる敵を、残機 3 のうちに倒し続ける。スコアとベスト記録つき。 |
| **EDIT** | コアブロックにパーツを生やしてロボを作る。設置・移動・寸法変更・ボクセル加工。 |
| **PART** | パーツ 1 個だけをじっくり作り込むワークベンチ。作ったものは「パーツ庫」に保存して EDIT で呼び出す。 |
| **TEST FIELD** | ルール無しの練習場。敵機 3 体（2脚・多脚・1脚）が無限に復活して相手をする。 |

エディタ右上の `⌂` でタイトル、`⚔ ソロプレイ` で出撃、`▶ TEST FIELD` で練習場。
`Enter` でも練習場に出られる。フィールド中は `Esc` でポーズ、そこから編集画面にもタイトルにも戻れる。

### ソロプレイ

**アリーナは同じで、上に載っているルールだけが違う。** 敵の湧き方も、負けの条件も、
点数も、`SoloRun`（`src/game/SoloRun.js`）というルール層が持っている。
フィールド側は「機体を1体出せ」「1体やられた」しか知らない。

| | |
|---|---|
| ウェーブ | 全滅させると次が来る。数は `2 + wave/2`（最大6体）、硬さは 1 ウェーブごとに +16% |
| 顔ぶれ | 4種（STRIDER / CRAWLER / POGO / FUNNEL）をウェーブごとにずらして混ぜる |
| 強化個体 | 5 ウェーブごとに 1 体。硬さ 2.4 倍、撃破点 3 倍 |
| 残機 | 3。やられると 2.6 秒後に復帰し、0 で終了 |
| ウェーブ突破 | 最大耐久の 35% を修復し、弾倉を全補充 |
| スコア | 撃破点（後半ほど高い）＋ 突破ボーナス `300 × ウェーブ` |
| 記録 | ベストスコアは `blostom.solo.best.v1` に残り、タイトル画面に出る |

**この分け方には理由がある。** ルール層はメッシュもカメラも DOM も触らないので、
紙のフィールド（4メソッドだけのスタブ）を相手に、レンダラ抜きで 100 ウェーブぶんを
一瞬でテストできる。逆にフィールド側は「誰が勝つか」を知らないままでいられるので、
練習場は今までどおり**ルール無しのまま**残っている。

ルール層は**固定ステップの中で動く**（試合の一部だから）。
一方、結果画面を出すかどうかを決めるのは `App.frame()` の側で、
これは画面の都合＝試合の外側だから。

### 見えないパーツに手が届くこと

**クリックは手前のものしか掴めない。** そしてまともに組んだ機体は、コアを外装の中に、
ボーンを手足の中に隠す。つまり「そこにあるのに一生選べないパーツ」が必ず生まれる。
プリセットを組み直したらコアが4機とも完全に埋まったので、これは机上の話ではなくなった。

出口を2つ用意してある。

| | |
|---|---|
| **同じ場所を再クリック** | レイ上のパーツを手前から1枚ずつ潜っていく。一周したら手前へ戻る。Ctrl+クリック（追加選択）のときは潜らない |
| **右パネル「パーツ一覧」** | 全パーツを親子関係つきで一覧。クリックで選択、**カメラもそこへ寄る** |

一覧のインデントは親子関係そのもの。「これは何にぶら下がっているのか」も
3D ビューでは答えられない質問なので、ついでにそれも見える。

選択できても見えなければ意味がないので、一覧から選ぶと `.`（選択に寄る）が自動で走る。

**加工中（削る／盛る／塗る）と設置中もカメラは動かせる。** 左ボタンは道具の専用になり、
視点回転は右ドラッグ、平行移動は中ドラッグ、ズームはホイールに移る。
配置が長いあいだ左ボタンをカメラと共有していて、しかも**押した瞬間**に置いていたので、
**見回そうとするたびにブロックが1個落ちていた**。

#### 矢印キーで詰める

ギズモのドラッグは 0.25 の格子に乗るが、**最後の数センチは矢印キーのほうが速い**。

- **画面の向き基準**で動く。カメラを回しても「→」は常に画面の右
- `Shift`+上下で高さ、`Alt` で 0.05 刻み（格子より細かく）
- 複数選択なら剛体としてまとめて動く。親と子を同時に選んでも子は二重に動かない
- 1回の押下が 1手のアンドゥ

#### パネルは今使うものだけ出す

寸法スライダを全部並べると、左パネルは画面の倍以上の長さになって、いま効く3つが
埋もれる。そこで **「ツール設定」には選択中のツールの設定だけを出す**。

- 選択 → ギズモ / ブロック → 新規ブロック寸法 / ボーン → 新規ボーン寸法 /
  装備 → プレートの種類と径 / 削る・盛る・塗る → ブラシと解像度
- ツール自体の並びは**作業の順番**にしてある。選ぶ → 組む（ブロック・装備）→
  ボーン（**フェイス → アーム → レッグ → カスタム**、ロボの上から下の順）→ 呼び出す
- 薄く表示するのではなく**消す**。薄いままでは場所を取り続けるので意味がない
- 「加工 (上級)」のツール一覧は既定で畳んである。キーボード（`X` `Z` `P`）で
  加工ツールに入ったときは自動で開く
- 右パネルの各セクションは見出しクリックで畳める。**既定で開いているのは
  「パーツ一覧」「色」「インスペクタ」** — 色は組み立て中いちばん多く触る決定で、
  パーツ一覧は隠れたパーツに手が届く唯一の道だから
- **armしたツールの設定は、必ず画面内に入る。** 上のツール一覧は畳まれないまま
  312px を占めるので、720高のウインドウでは装備ツールの設定が**247px 画面外**に
  あり、プレート径スライダは下端の 111px 下にあった。ツールを持ち替えたのに
  その設定が見えないのは、パネルが今頼まれたものを隠していることになる。
  ツール切替時に**下方向にだけ**必要な分スクロールする（何も隠れていないのに
  パネルが動くのは、それはそれで邪魔なので）

#### 機体の性能値は常に出しておく

質量・機動・耐久・脚数を**右パネルの最上段に1行**。折りたたみの中ではなく、常に。

ブロックを20個足したときに**動きがどう変わったかのフィードバックが無い**まま組めて
しまうのは、組み立てゲームとして肝心なところが抜けている。詳細は「スペック」パネルに
残してあるが、この4つだけは畳めない。

#### 複数選択は、選んだ全部に効く

8つある「選択に適用」系の操作のうち、**全部を回っていたのは2つだけ**で、
残る6つは黙って先頭の1つだけに効いていた。同じパネル、同じ選択、
どちらになるかは画面のどこにも書いていない。

- 寸法・形・ボーンの長さ/太さ/可動域・プレート径・回転設定・関節の効き —
  **全部が選択全体に効く**
- 複数選択時のインスペクタも、**連結／複製／削除**だけだったのをやめて、
  選択の中身に応じて**寸法・形・ボーン寸法・プレート径**を出す
  （ブロックとボーンが混ざっていれば、両方の欄が出る）
- 脚を4本選んでまとめて太くするのが、複数選択がある理由そのもの。
  それを4回やらせていた

#### 色は「選んで、塗る」

スウォッチは**これから置くパーツの色**を決めるだけだった。既に置いたブロックを
塗り替えるには、畳まれた「色」を開き、選び、インスペクタを「中身」まで下って
「全塗り」を押す — **4アクション**。組み立て中いちばん多く下す決定なのに、
いちばん遠い場所にあった。

いまはスウォッチのクリックが**選択中のブロックをその場で塗る**（同時に次に置く色も
決める）。選択が空なら何もしない — 履歴に空の1手を積んだりはしない。

#### ギズモは選択に付く。ツールには付かない

ギズモは選択ツールのときしか出ていなかったので、**「置く → 位置を直す」**という
誰もが回すループが、毎回モード切替を挟んでいた。置いた直後のパーツは既に選択されていて、
インスペクタにも出ているのに。

いまは**加工ツール以外なら常に出る**。配置ツール中は**一回り小さく**する —
ハンドルは次のパーツを置きたい面の真上に伸びるので、腕が短いほうが邪魔にならない。
配置クリックの抑止は `dragging` ではなく **`axis`**（ハンドルにポインタが乗った瞬間に
立つ）で見る。`dragging` はギズモ側のハンドラが走ってからでないと立たず、
どちらのリスナーが先かはこちらの決められることではないので。

#### 左右対称は既定オン、そして押す前に見せる

ほとんどの機体は左右対称なので、既定でオンのほうが手数が半分になる。ただし
**「1クリックで2個置かれる」を押した後に知る**のは体験が悪いので、
**もう一方のゴーストを先に出す**。設定が自分で自分を説明するなら、
チェックボックスを見つけてもらう必要がない。

#### ヘルプ（F1）

上部バーの `？`、`F1`、`?` キーのいずれかで開く。ポーズ中のメニューからも入れる
（そのときは「テスト」の操作ページが開く）。ページは
**はじめに / 編集画面 / 形 / ボーン / 装備 / テスト**。

**中身は全部、ゲームが実際に使っているテーブルから生成している。**
装備テーブルにプレートを1行足せばヘルプにも出るし、キーを割り当て直せば
操作ページの表記もその場で変わる。手で書き写したヘルプは1週間で嘘になり、
**嘘のヘルプは無いより悪い**（読んだ人が試してから間違いに気付く分だけ損をする）。

このウインドウも縁のドラッグでサイズを変えられる。

#### ウインドウのサイズは自分で決められる

**左右のパネルも、キー設定・共有のポップアップも、縁をドラッグしてサイズを変えられる。**

- **内側の縁**で幅、**下の縁**で高さ、**角**で両方。掴める場所は触ると光る
- **ダブルクリックで既定サイズに戻る**
- サイズは `localStorage` に覚えるので、次に開いても広げたまま
- 画面の 60% より広くはできない（パネルだけになってしまうので）。
  小さい画面に切り替えたときも、画面からはみ出さないように詰め直す

実装で 2つ引っかかった点:

| 問題 | どうしたか |
|---|---|
| パネル自体がスクロールしていたので、縁に置いた掴み手が中身と一緒にスクロールして消える | パネルを**スクロールしない外枠**にして、スクロールを内側の `.panelscroll` に移した |
| 右パネルは画面右端に固定なので、右の縁を引いても伸びる向きが逆 | 右パネルの幅の掴み手は**左の縁**に置いた（実際に動くのはそちら側） |

画面中央に出るポップアップは、1px ドラッグしても縁は 0.5px しか動かないので、
**倍のゲイン**で追従させている（そうしないとポインタから置いていかれる）。


実測で、左パネルの中身は **1586px → 563〜674px**。ほとんどのツールでスクロールなしに収まる。

「左右対称でつける」を入れると ±X 位置の設置が自動でミラーされる。

### フィールド操作

| キー | |
|---|---|
| `W A S D` | 移動（機体前方基準、**A が右 / D が左**） |
| `W`/`A`/`S`/`D` を2回押し | **ダッシュ。前後左右すべて可能** |
| `Space` | 上昇 / 接地中はジャンプ。押しっぱなしで飛行 |
| `Shift` | 下降 |
| `E` | ブースト |
| `F` | ロックオン / 解除、`Tab` でターゲット切替 |
| `1` `2` `3` | ABC レイヤー切替（Active / Balance / Cooling） |
| **`1` `2` `3`**（ウェーブ間） | **休憩の選択を取る**（装甲 / 弾薬 / 温存）。この間はレイヤーは切り替わらない |
| マウス | 視点 |
| **左クリック** | **選択中の武器を撃つ** |
| **`C` / `X`** | **武器を次 / 前に切替** |
| **右ドラッグ**（`Alt`+マウス） | **カメラを機体のまわりで回す**（機体は向きを変えない） |
| **ホイール** | **ズーム。ブームの長さが伸び縮みする** |
| `R` | リスポーン |
| `Esc` | **ポーズ / 再開** |

**この表はゲーム内にも出ている。** フィールド上部の帯に、**武器のキーを先頭に**して現在の
割り当てが並ぶ。キーコンフィグで変えれば帯の表示もその場で変わるので、
「撃つボタンが分からない」が起きない。

**フィールドに入るとすぐゲームが始まる。** `Esc` でポーズすると、止まった画面の上に
**［再開］［リスポーン］［キー設定］［編集画面に戻る］** が出る。
マウスがロックを外れたときも自動でポーズ。

左右の割り当ては `InputManager` の `profile.invertStrafe` 1つで入れ替わる
（既定 true ＝ A が右）。

ダッシュは推力コマンドではなく **インパルス** として入る。スプールを通すと、わざと鈍く
してある後退プロファイルに後ろダッシュが吸われてしまうため。

### キーコンフィグ

**全アクションを自由に割り当て直せる。** 上部バーの `⌨` か、ポーズメニューの［キー設定］から。

- 行のキーをクリック → 押したキーがそこに入る（`Esc` で中止）
- `＋` で **1アクションに複数キー**（既定でも前進は `W` と `↑` の2つ）
- `×` で余分なキーを外す。**最後のひとつは外せない**（無言で操作不能になるのを防ぐため）
- マウスボタンも割り当てられる。`F5` `F11` `F12` `Esc` はブラウザ側に必要なので拒否する
- **1キー1役**。すでに使われているキーを割り当てると前の持ち主から取り上げ、
  「○○ から移しました」と表示する。取られた側が空になったときは
  **「○○ が未設定です」と警告し、その行を赤で表示する**
- 変更は localStorage（`blostom.keys.v1`）に保存。**既定から変えた行だけ**保存するので、
  あとから既定が増えても新しいキーがちゃんと入る
- ［初期設定に戻す］でいつでも全部戻せる

ゲーム側は**キーではなくアクションだけを読む**（`input.isDown('fire')`）。だから
割り当てを変えても、物理も武器もヒント帯も何ひとつ書き換えずに追従する。

## 2. パーツの仕組み

### コアブロック

銀色のブロック。ロボのルートで、削除できない。
**ローカル +Z が前方**（＝移動進行方向）、+Y が上。エディタの床に出ている水色の矢印がそれ。

### 配置：ソケットは廃止、位置は完全に自由

パーツの位置は **親の座標系における自由な position + rotation**。格子もソケットもない。

- **面をクリック** → 押した**その場所**にぴったり吸着して置かれる
- **何もない所をクリック** → **床の上**に置かれる（Shift+ホイールで高さを上げ下げ）
- **ドラッグ** → 連続で置く（1ドラッグ＝アンドゥ1回）
- **R / Shift+R** → 置く前に90°ずつ回す
- **Alt+クリック** → その部品の形・寸法・色を今の道具に写す
- **右クリック** → 道具を持ち替えずに、カーソルの下の部品を消す
- 置いたあとは **ギズモで任意の場所へ**。スナップの粗さ（0.05〜0.5）と 15° は切り替え可能
- インスペクタで座標・角度を直接数値入力もできる

#### ドラッグ配置が、列ではなく蛇を作っていた

「ドラッグで連続配置」を入れたあと、実測したらこうなっていました。
4×0.5×4 の甲板を横切って1回ドラッグ:

| | |
|---|---|
| 置かれた数 | 29個 |
| **甲板に乗っていた**もの | **1個** |
| **前のブロックに数珠つなぎ**になったもの | **28個** |

しかも向きが揺れる（横→前→横）。**空中を蛇行する鎖**です。
原因は単純で、1個置くたびに選択が移り、次のホバーが**いま置いたばかりのブロック**に
レイキャストしてその面に吸着していました。単発クリックは正しく動いていた
（3クリック→3個とも甲板の子として、押した位置に）ので、壊れていたのは**ドラッグの輪**だけ。

そして28深の親子連鎖は、フィールドでは「28個が最初の1個に乗って一緒に動く」を意味します。
**土台を1個消すと28個消える。**

- **ドラッグ中は、最初の親と面を固定する。** 以降は接線位置だけが動く。
  面の平面を外したときに通常のレイに**戻さない**のが肝で、戻すと「いま置いた部品」に当たる
- 空中から始めたドラッグも同じ（作業平面に固定する）。ここを分けていなかったので、
  甲板の外から始めると最初の1個が浮遊配置になり、以降が全部鎖になっていた
- **グリッドは、置くものより細かくならない。** 0.25のグリッドに0.5のブロックだと
  1ノッチ隣が半分重なる。タイルにならないグリッドは助けになっていない
- **列は列として選択される。** 20個置いて最後の1個だけ渡されても、色も変えられないし戻せない

#### カメラと道具が同じボタンを取り合っていた

配置ツールを持っている間、**左ボタンはカメラ回転と配置の両方**に割り当てられていて、
しかも配置は**押した瞬間**に走っていた。つまり**機体を見回そうとするたびに、
まずブロックが1個落ちていた**。彫刻ツールは同じ理由でとっくに左ボタンを専有していたので、
配置にも同じ扱いを与えた（左＝配置、右＝カメラ回転、中＝平行移動）。

選択ツールのほうは左ボタンをカメラに残したまま、**離した時点で、ほとんど動いていなければ**
選択する、に変えた。ついでにこれがタッチの答えにもなる — 指を置いた時点でゴーストが出て、
動かして狙いをつけてから、離して確定できる。

#### 「どの面か」ではなく「面のどこか」

`faceAnchor` は法線方向にしかオフセットしていなかったので、**3×1×3 の胸板の角を狙って押しても、
必ず面の真ん中**に着いた。肩を1列に並べるだけで「置く→ギズモで動かす」の往復になる。
クリック点の接線成分をグリッドで丸めて足すようにした。カーソルとゴーストが一致し、
**ドラッグで面をなぞって並べる**が成立する。

#### 外接箱ではなく、形そのものの表面に置く

21形のうち14形（球・ドーム・円錐・皿・カプセル…）は外接箱から離れて曲がっている。
親の箱の面に吸着していたので、**球の上に置いた部品は実際の球面から浮いていた**。
`surfaceAlong()` は形のマスクを法線方向に外から内へ舐めて、その位置での「皮」の高さを返す。
立方体はどこでも 1 を返すので、**これまでの配置は1ミリも変わらない**。
筒の穴のように線が形に当たらないときは外接箱に落とす — 親の中心に埋めるほうが奇妙だから。

#### 「左右対称」が対称にしていた面

`_mirror` は**親のローカル座標のXを反転**していた。それが体の中心線になるのは
親が体の中心にあるときだけなので、**左肩に飾りを付けると、右肩ではなく同じ左肩の反対側に
双子が出ていた**。チェックボックスは「左右対称でつける」と言っていたのに、
対称にしていた面が違った。

いまは**機体そのものの中心線**で折り返し、親に鏡像の相方がいればそちらにぶら下げる
（無ければ同じ親のまま、位置だけ正しい側へ）。プレビューの双子ゴーストは
**同じ関数の出力**を描くので、見えているものと置かれるものが一致する。

#### 姿勢の中で置かない

空中配置だけがワールド座標を「**今の姿勢の**」親ローカルに変換していたので、
歩行プレビュー中に置くと、止めた瞬間に位置がずれた。連結・解除・親替えは
`_restPose()` を通してから計算していたのに、配置だけ通っていなかった。
いまは空中配置がルートの**静止フレーム**で計算され（それは解析的にわかる）、
プレビュー中の確定時には配置全体を静止姿勢に戻してから測る。

#### 置く前に見えているもの

- **ゴーストの輪郭が形に沿う。** 中身は選んだ形なのに、枠は箱の稜線固定だった
- **親になるパーツが光る。** 配置は「どこに」だけでなく「誰の子として」も決めていて、
  その半分が見えていなかった。親は、機体が動き出したときに何と一緒に動くかを決める
- **重なると赤くなる。** 禁止はしない（わざと埋める作りがある）。ただし黙ってはいない
- **床の輪と垂線。** 空中の部品は高さを測る手がかりが何もない
- **カーソルの脇に「形・寸法・向き・高さ」。** 形は左パネル、色は右パネル、場所は中央 —
  ブロック1個置くのに視線が3か所に飛んでいた

#### 置いたあと

- **面付けしたブロックは、寸法を変えても面から離れない。** ブロックは自分の中心を軸に
  育つので、追加した寸法の半分が親の中に沈んでいた（内側なので見た目でも気づけない）。
  どの面に付けたかを mount に持たせ、リサイズ時に法線方向へ半分だけ押し戻す
- **削除は巻き込む数を言う。** `remove` は子孫を丸ごと消すのに、選択の枠は自分しか
  囲まない。土台を1個消したら腕ごと消えた、が黙って起きていた
- **貼付は元のブロックの大きさぶん離れる。** 固定 0.25 では、2m のブロックの複製が
  ほぼ完全に元と重なって出てくる
- **ブラシは実寸で効く。** ボクセルの格子は常にブロックいっぱいに張られるので、
  「格子の何%」は世界の中では固定サイズではない。同じスライダーが 4m のブロックでは
  1m のブロックの4倍の穴を開けていた。1m を基準にした実寸で数えるようにした


**触れていないパーツを作れる。** ビットやファンネルのような浮遊ブロックはこれで作る。
プリセット「浮遊ビット FUNNEL」がその例。

パーツは位置とは別に **連動先（親）** を持つ。これは「どのパーツと一緒に動くか」だけを決める
もので、位置には一切影響しない。ボーンを連動先にすると、その関節から先で動く。
インスペクタの「連動先」で後から変えられ、変更しても見た目の位置は動かない。

複数選択したまま動かすと、剛体としてまとめて移動・回転する。親と子を同時に選んでも
子が二重に動くことはない（親だけに変換を適用し、子は階層で付いてくる）。

### 連結（コネクト）

**複数選択して `J` を押すと、最後に選んだパーツに他の全部が連結される。**
最後に選んだパーツ＝連結先は **水色の枠** で表示され、他は黄色。連結関係は
**緑の線** で描かれるので、何が何に付いているかが常に見える。

- ボーンの先で動いているブロックに連結すれば、**その関節で一緒に振れる**（ビットや増加装甲など）
- `Shift+J` でコアに戻す（連結解除）。位置は一切動かない
- 連結しても解除しても **見た目の位置は 1mm も動かない**。ワールド変換を新しい親の座標系に
  変換し直しているだけ
- 親と子を同時に選んでも、内部の構造は壊れない（最上位のパーツだけが付け替わる）
- 自分の子孫には連結できない（木が自分を食べてしまうため）

ボーンに **直接** 連結した場合は、中点より手前なら「固定側」、奥なら「可動側」になる。
どちらに入ったかはインスペクタと連結時のメッセージに出る。固定側だと動かないので、
動かしたいときはギズモで中点より先へずらせばよい。

### 装備プレート

**平べったいシールのような薄板**を、ブロックやボーンの好きな面に貼りつける。形は 2 種類だけに
統一してある。

| | |
|---|---|
| **〇 丸** | 武器プレート |
| **□ 四角** | その他プレート（効果はさまざま） |

厚みは固定で、変えられるのは**径だけ**（0.3〜1.6）。「機体にキットを貼った」ように見せたいので、
シルエットは揃えてある。面をクリックすればその面にぴたりと寝て、法線が外を向く。ボーンの側面に
貼れば、シャフトの表面に外向きで乗る。

#### 武器プレート（丸）

| | 弾数 / リロード | 撃ち方 | 弾色 |
|---|---|---|---|
| **ビーム** | **長く細い一線を撃つビームライフル。**威力は高いが連射は効かない（5発／リロード1.4秒） |
| **スナイパー** | 超長射程・高威力の一撃。**`Q` でスコープ**（画角が狭まって拡大される） |
| **レーザー** | **押している間、太いレーザーを撃ち続ける。**弾ではなく熱で払う。溜まりきると強制冷却 |
| **ガトリング** | 押しっぱなしで連射。30発でリロード3秒 |
| **ショット** | 3方向へ拡散。6発でリロード3秒 |
| **スプレッド** | 9発を大きく拡散。近ければ全弾当たる |
| **マグナム** | 至近距離用の一撃。射程は短いが非常に重い |
| **グレネード** | 山なりに飛ぶ爆弾。着弾点で小爆発（範囲ダメージ） |
| **ミサイル** | **小型5発をばらまいて追尾。**白い航跡を引く |
| **ブレード** | 押している間、**連結したブロックがまとめて光り**、触れた敵を削る |
| **シールド** | 機体を覆うバリア。**被弾を肩代わりし、体当たりでダメージ。**時間で消える |
| **ブースト** | **ブースト（`E`）が使えるようになる。**ダッシュの効果も小アップ（+14%、重ね貼りで加算） |
| **グラビティ** | **空中浮遊不可**になる代わりに耐久 +45%。**1枚しか付けられない** |
| **ローリング** | **貼りついたブロックを回し続ける。**向き（正転/逆転）と速さ（5〜400rpm）を選べる |
| **サークル** | 貼った場所を中心に**円線**が出る。その線に触れているパーツが線に沿って回る |
| **フロート** | 常に地面から少し浮く。1枚のみ |


#### 撃ち方が違うものは、仕組みも違う

弾を飛ばすだけの武器ばかりでは同じものが並ぶので、**「何で払うか」**を分けてある。

| 払うもの | 武器 |
|---|---|
| **弾数** | ビーム / スナイパー / ガトリング / ショット / スプレッド / マグナム / グレネード / ミサイル |
| **熱** | レーザー（押している間ずっと溜まり、離すと冷める。溜め切ると強制冷却） |
| **時間** | シールド（張った瞬間から自分の時計で減る。トリガーは関係ない） |
| **接触** | ブレード（弾も熱もない。当たっている間だけ削る） |

- **レーザーは弾ではなく線**。毎フレーム、銃口から射程まで線分を引き、
  **最初に当たった1機だけ**を焼く（後ろの機体は前の機体が遮る）
- **グレネードは落ちる**。速度に重力を足しているだけで、着弾点で範囲ダメージ。
  距離に応じて減衰するので、直撃と至近弾で差が出る
- **マグナムの射程は寿命**。速度×寿命がそのまま届く距離になる（約36m）
- **シールドは `Robot.damage` の手前に入る**。吸収しきれなかった分だけが機体に届き、
  0 になったバリアはその場で割れる

#### スコープ

スナイパーを選んで `Q` を押している間、**カメラの画角を 42% まで絞る**。
カメラを動かさずに拡大するので、機体は今いる場所のままで狙える。離せば戻る。

#### ブースト

**ブーストは「巡航では届かない速度に連れて行くもの」**として調整してある。
巡航 18m/s に対して**ブースト時のピークは 31m/s（約1.75倍）**。

| | 変更前 | 現在 |
|---|---|---|
| 速度上限の倍率 | ×1.55 | **×2.35** |
| 推力の倍率 | ×1.55 | **×2.05** |
| ダッシュの初速 | 22 | **34** |
| ダッシュの再使用 | 0.42秒 | **0.26秒** |
| 立ち上がり | 0.035 | **0.018**（半減期） |

燃費も少し軽くしてある（0.40→0.34/秒）。**待たされるブーストは使われなくなる**ので、
立ち上がりと再使用の速さは速度そのものと同じくらい効く。

**ブーストは装備しないと使えない。** プレートが1枚もない機体は `E` を押しても何も起きないし、
燃料も減らない（`canBoost` が false のまま、入力を受け取る前に切れる）。

**噴射エフェクトはプレートそのものから出る。** 貼った面の向き（+Y）が噴射方向なので、
背中に貼れば後ろへ、腹に貼れば下へ吹く。ローリングと同じで**どこに貼るかがそのまま設定**。

- プレート面に**白いディスク**、そこから**円錐の炎**が伸びる。炎がカメラに対して真横を
  向いていなくても光源が読めるように、この2枚構成にしてある
- プレート中央のアクセントも一緒に増光する（emissive を 0.85 → 4.0 まで）
- 消えるときは**すぐ切れずに落ちていく**。パチンと消える推進器は「切った」ように見えて
  「使い切った」ようには見えないので
- 機体後方の汎用プルーム（推力に連動する円錐の噴射）はそのまま。ブーストの炎はそれとは別物

なお、以前は機体の原点に**放射状のスプライト**も置いていて、推力に応じて光っていた。これは
「コアブロックが光っている」ようにしか見えず、ダッシュのたびに胸が発光する見た目になっていた
（ダッシュ自体が発光させていたわけではなく、ダッシュ中はスプールが振り切れるため）。
プレートが自前の炎を持つようになった今、機体の真ん中で正体不明にぼやける光は
**どのパーツが仕事をしているのか**を分かりにくくするだけなので撤去した。噴射はプルームだけ。

実測: 素の2脚が最高 22.1 m/s のところ、背中にブーストを1枚貼ると **30.9 m/s**。

#### ローリング

**貼った面の向きがそのまま回転軸**になる。上面に貼れば水平に回り、側面に貼れば縦に回る。
どこに貼るかが設定を兼ねているので、軸を選ぶ UI がいらない。

- 回るのは**ブロックごと**。そのブロックに載っているもの（別のブロック、ボーン、他のプレート）も
  一緒に回る。レーダー、砲塔、観覧車、プロペラはこれで作る
- **編集画面でも回っている。**「常に回る」パーツが止まって見えるのはただの嘘なので、
  歩行プレビューとは無関係に常時回す
- **コアには貼っても回らない**（機体ごと回ってしまうため）。ボーンに貼っても回らない。
  どちらもインスペクタが赤字で警告する
- 左右対称配置でミラーすると、**対になったほうは逆回転**になる（左右のプロペラのように）

グラビティは「浮けなくなる」のであって「跳べなくなる」のではない。脚があればジャンプはできる。
できなくなるのは、上昇入力で重力を買い戻して**飛び続ける**ほう（4節「空中戦と地上戦の両立」の
`gravityScale` がそのまま 1 に固定される）。

2枚目のグラビティは、置こうとしても・型を差し替えようとしても・パーツ庫から移植しようとしても
弾かれる。ルールが 1 箇所ではなく、通り道すべてで効いている。

### 敵が撃ってくる

長いあいだ、この戦闘は**一方通行**だった。敵は武器プレートを3枚・4枚・5枚積んでいるのに、
**一度も引き金を引いていなかった** — 敵の `Robot.update()` は武器システムを駆動しておらず、
それをやっていたのは `FieldScene._fire()` だけで、そこはプレイヤー専用だったから。

計測: 武装した敵3体の真ん中に5秒立って **HP 174/174（無傷）**。

**その結果、積み上げてきたものの大半が実際のプレイでは一度も発火していなかった** —
低速弾も、カプセル判定も、偏差の手前撃ちも、のけぞりも、吹き飛ばしも、
被弾方向の弧も、自機の赤いフラッシュも、シールドプレートも。
そしてソロプレイの**残機3は減りようがなかった**（＝負けられない）。

- 弾の判定対象も `enemies` だけだった。**全機**（プレイヤー含む）に変えた
- 同士討ちは無し。ただし**両方が陣営を名乗っているときだけ**除外する。
  名乗らないもの（テスト用のダミー、残骸）は当たる側に倒す — 当たらないバグは見えるが、
  味方に当たるバグは見えない

#### 撃ち方は「読める癖」であって、賢さではない

- **バースト撃ち**。トリガーを握りっぱなしの機体が3体いると、出てくる弾は誰にも
  さばけない量になり、しかも**途切れない** — 動く隙が無いので、撃ち合うしか残らない。
  **隙間こそがゲーム**で、そこが「詰める」「遮蔽から出る」「狙いをつける」時間になる
- **リロード中と手負い（HP35%以下）は下がる**。プレイヤーが見て使える情報
- **飛んでくる弾をダッシュで避ける**。プレイヤーがやることを敵もやる。
  ただし**自分に向かっている弾だけ** — 全部に反応する機体は痙攣して見える
- **正面（内積0.55以上）かつ武器の射程内でしか撃たない**。
  射程は武器から出す（速度×寿命、レーザーは射程、ブレードはリーチ）ので、
  マグナムを90m先に撃ち込んだりしない

#### 難易度は「時間」で上げる

ウェーブが進むと上がるのは**耐久だけ**だった。それは敵を硬くするだけで、
戦い方は同じまま試合が長くなる。

いま上がるのは**攻撃の密度**（`aggression` 0.25 → 1.0 を5ウェーブで）。
**ダメージも命中率も触らない** — 弱い弾を撃たせると「弾1発の重さ」について
嘘を教えることになるし、わざと外させると何も教えない。
序盤のウェーブが与えるのは**時間**で、進むほどその余裕が削られる。

計測（ウェーブ1、敵2体、10秒）:

| | 受けたダメージ |
|---|---|
| 棒立ち | **102** / 174 |
| 左右に振る | **55** / 174（**46%減**） |

#### 自分のHPは画面の「縁」で

HUDは**ターゲット**のHPをレティクルの弧で描いていたが、**自機のHPはどこにも無かった**
（撃たれなかったので問題が表に出ていなかった）。

数字は正しいが役に立たない — 特定の場所にあるので、視線を戦闘から外させる。
**60%を切ると画面の縁が赤く沈み、30%を切ると脈打つ**。目の端で読めるものだけが、
戦闘中の注意力に見合う。健康なうちは**何も出さない** — 常に赤い縁は見えなくなる縁で、
そうなったら何も警告できない。

#### 遮蔽がロックを切る

アリーナは最初から柱だらけなのに、**使う理由が無かった**（撃たれないので）。
そしてコストの無いロックオンは、判断の無いロックオンだった。

**視線が0.55秒切れるとロックが外れる。** 一瞬柱をかすめただけで切れるロックは
無いほうがマシなので、即時ではない。柱に二つ目の仕事ができ、走り込む意味ができる。

#### 音が「出来事」を持つようになった

`KineticFeedback` は AudioContext もマスターゲインもミュートも**持っていた**が、
鳴っていたのは推力ドローンと歪みノイズだけ — 推力とジャークで**連続駆動**される
共感覚レイヤーで、**イベント音のAPIが無かった**。発砲音も着弾音も爆発音も、1つも。

- **合成。サンプルではない。** 発砲はフィルタが落ちるノイズバースト、着弾は同じものを
  短く高く、爆発は長いものにサイン波の芯を敷く。**3つの形で1ゲーム分の出来事を賄える**し、
  失くすオーディオファイルがどこにも無い
- **連続音とは別のバス**に流す。同じゲインに混ぜると、自分のエンジン音の上で銃声が聞こえない
- **自機の音と他機の音を分ける**（自分の発砲は明るく、被弾は体のある低音）
- **クリック前は何も開かない**。ロード時にオーディオデバイスを開くゲームは
  ブラウザに止められるし、勝手に鳴るタブになる

#### 撃破は、被弾と同じ見た目ではいけない

撃破しても残骸とパルスだけで、**当てたときと同じフィードバック**だった。
ループの報酬が支払われる唯一の瞬間なので、専用の輪・専用のマーク（×に丸）・
専用の低い音・強めの揺れを与えた。

#### 武器を持ち替える理由

10種の武器はコスト構造がきれいに分かれているのに、**敵が全員同じ20m前後に立っている**
かぎり、1つの銃で全部に答えられてラックは飾りだった。

対戦相手の距離を**離した** — CRAWLER は11mまで踏み込み、FUNNEL は40m を保つ。
短射程の武器はFUNNELに届かず、長射程で構えているとCRAWLERに詰められる。
**手に持っているものが、答えのある問いになる。**

### 画面が、ゲームの状態を隠していた

実際に開いて座標を測ったところ、**ソロプレイの読み出しが操作説明バーの真下に描かれて**いました。

| | 位置（1440×810） |
|---|---|
| 操作説明バー | x 14–1426（**画面幅の98%**）、y 14–68.8 |
| ウェーブ／のこり | (22, 26–52) |

**両方ともバーの矩形の中。** つまり走っている間ずっと、いま何ウェーブか・敵が何体残っているか・
スコア・**残り残機**が、ひとつも見えていなかった。800×450 ではバーが画面の高さの38%を占めます。

- **操作説明は6秒で畳む。** 家具ではなく挨拶なので。`?`／`F1` で戻り、**ポーズ中は出しっぱなし**
  （止まっているときこそキーを確認したい）
- **読み出しは、バーが実際に占めている高さの下から始まる。** 固定値ではだめで、
  バーは狭いウィンドウで行が増えるため、1440で足りる余白が900では足りない。
  アプリがバーの高さを測ってフィールドに渡し、HUDがそれを読みます
  （HUDはDOMを知らず、UIはHUDを知らないまま）
- **ウェーブ・のこり・スコア・残機を1か所に。** 左上と右上に散っていたものを、1つの縦積みに

#### 開発用の数値が出荷されていた

右下の `ZETA / JERK / ASSIST / FRAME` は**運動モデルの調律用**で、プレイヤーには何も意味しません。
テストフィールドでは全部、**ソロプレイでは `LEGS` だけ**に。

#### HPを賭けた選択なのに、HPが分からなかった

画面の縁が赤くなるのは60%を切ってからで、それ以上は何も出ません。戦闘中の設計としては
正しい（常時赤い縁は見えなくなる）のですが、**ウェーブ間の「装甲45% / 弾薬+15% / 温存」を
選ぶには、いま何%かを知っている必要があります**。選択が出ている間だけ、その上に
`装甲 73 / 174` を数字で出すようにしました。戦闘中は今まで通りです。

#### 狭いウィンドウでの破綻

- **下部ヒントバーがウィンドウ幅と無関係に1198px固定**で、900pxのウィンドウでは
  左右298pxが画面外。文字が単語の途中から始まっていました。折り返すようにし、
  さらに狭いときは先頭の数項目に絞ります
- **編集パネルが1440で30%、900で48%**を占め、**組んでいる対象より操作UIのほうが広い**
  状態でした。1024px未満で端に畳み、タブ（▸ ◂）で手動でも開閉できます。
  一度手で開いたものを次のリサイズで閉じ直したりはしません

#### 細かいところ

- **レティクルに暗い縁取り。** 1pxの淡い輪だけでは、コアの発光ブロックの上では消えます
- **キーキャップは折り返さない。** 「左クリック」が「左クリッ／ク」で割れていました

### 数字を見て直したこと

持続DPS（弾倉を撃ち切ってリロードするまでの平均）を全武器について出したところ、
**射程とDPSが噛み合っていませんでした**。

#### ガトリングが全武器中ワーストだった

持続 **14.1**。次に低いのが20.5、最高が56.3。TTKは他が3〜8秒のところ**12.3秒**。
「押しっぱなしの主力」という顔をしているのに、一番弱い銃でした。
しかも**「握ると散る」を入れた直後**だったので、握る前提の銃を握ったことで罰していた。

1発 2.4 → **3.6**（持続21.2）。射程167mと弾数30はそのまま。

#### ショットにも居場所が無かった

スプレッドの下位互換でした。散布は狭い（0.14）が **throughputが1/3**（21/発 vs 45/発）で、
狭さで埋まる差ではない。**距離で分けました。**

- **ショット** = 中距離の精密弾（1発 7→**11**、散布 0.14→**0.10**、射程118m）
- **スプレッド** = 至近専用（寿命 1.5→**0.9** で射程81m→**49m**）

#### スナイパーの射程576mは、半径120mのアリーナで意味を持たない

ビーム（246m・DPS31・0.55kg）がスナイパー（576m・26.4・0.90kg）を**射程以外の全項目で上回って**
いました。ビームの射程を**123m**（アリーナの幅くらい）に落とし、
スナイパーは1発 52→**68** にして「一撃の重さ」で立たせています。

結果、**DPSが射程と逆相関**する形になりました:

#### 武器は4枚まで

**搭載枚数に上限が無く**、プレート1枚の重量は機体質量の1割未満でした。
つまり**10種類ぜんぶ積んで巡回するのが最適解**で、
きれいに分かれた10通りのコスト構造は、誰も答えなくていい問いだった。

**4枚。** 近接1枚・遠距離1枚・好みで2枚。**編集画面での選択が判断になります。**
システムプレート（ブースト・タンク・フロート等）は枠を使いません。

#### コアのスライダーが、他の全要素より強かった

`durability = 40 + コア辺長² × 60 + 質量 × 5` ——**二乗**でした。

| コア辺長 | 旧・耐久 | 新・耐久 |
|---|---|---|
| 1.0 | 174 | 174 |
| 2.0 | 389 | **307** |
| 3.0 | 782 | **521** |
| 4.0 | **1383** | **841** |

スライダー1本で**耐久8倍**。代償は機動性ゼロですが、敵全体のDPSは実測で15前後なので、
1383HPは**90秒立っていられる**ことを意味します。避けられなくても関係ない。
指数を **1.4** に落として、4.8倍にしました。大きな選択ではあるが、
他の全部を無意味にはしない。

#### 後半が作業になっていた

耐久の伸び 0.16/ウェーブ → **0.10**。ウェーブ20の総HPは 5,202 → **3,734**
（持続35DPSで149秒 → **107秒**）。

そして**速攻ボーナスは45秒固定**だったので、ウェーブ7以降は
**取れないボーナスとして画面に居続けて**いました。基準時間を
`45 + 8×(ウェーブ-1)` 秒にして、最後まで狙えるようにしています。

**腕前ボーナスがウェーブ係数を持つようになりました。** 無被弾400・速攻300・命中250は
固定だったので、ウェーブ1では950対800で拮抗し、**ウェーブ20では950対9,450＝10%**。
腕が効くべき場面で腕が点にならない、という一番まずい形をしていた。

### エナジータンク

エネルギーは飛行・ブースト・ダッシュの全部を払う唯一の資源なのに、
**どの機体でも同じ1つの大きさ**でした。つまり「どれだけ飛んでいられるか」は
組んで変えられる値ではなかった。

**タンクは燃料をタダにするのではなく、持久力を買う部品です。**

- 消費が**大きなタンクの小さな割合**になる ＝ 長く飛べる、長くブーストできる、ダッシュが多く撃てる
- **回復も同じ割合で遅くなる** ＝ 満タンに戻るのに時間がかかる
- **重量1.3**（ブーストの3.7倍、フロートより重い）

だから**一度の長い飛行をしたい機体には効き、短く飛んで頻繁に充電したい機体には損**。
そこが選択になります。複数積めば累積します（1枚 ×1.55、2枚 ×2.10）。

HUDのENバーは**タンクぶん横に伸びます** — 減りが遅いだけで幅が同じだと、
「なぜか燃費がいい」に見えてしまうので。編集画面のスペック帯にも
タンクを積んだときだけ `EN x1.55` が出ます。

### 判断のある試合にする

敵が撃ち返すようになって「**負けられる試合**」にはなった。その次に足りなかったのは、
**判断**だった。撃ち合いは成立しているのに、プレイヤーが選んでいるものが一つも無い。

#### 死ぬほうが得だった

撃破されると残機を1つ払う代わりに **HP全快・弾倉全回復**で戻ってきた。
一方ウェーブクリアの回復は**35%だけ**。つまり **HPが低いときは、生き残るより
わざと落とされるほうが強かった**。残機というコストが、回復というご褒美に負けていた。

復帰は **60%** にした。残機は「高くつく逃げ道」であるべきで、割引券ではない。

#### 補給が無料だったので、我慢する理由が無かった

リロードは自動、ウェーブごとに全弾補給、死んでも全補給。
**10種の武器がコスト構造で分かれているのに、そのコストを払う場面が一度も来なかった。**

ウェーブ間の3.4秒は、バナーが出るだけの空白だった。そこを**選択**にした:

| | |
|---|---|
| **1 装甲** | HP 45% |
| **2 弾薬** | 全弾＋HP 15% |
| **3 温存** | 残機を1つ買い戻す |

取るのは **ABCレイヤーと同じキー**（既定で `1` `2` `3`）。戦闘中の意味を、
戦闘が無い3秒だけ借りる — **新しい割り当てを覚える必要が無く、
キーコンフィグで変えれば両方ついてくる**。この間、押したキーはメニューが飲み込むので、
メニューを抜けた拍子にレイヤーが変わっていることは無い。

**何も押さなければ次のウェーブ開始時に1番が取られる** — 走っている試合が
メニューで止まってはいけない。

#### 難易度を「硬さ」から「行動」へ

5ウェーブごとのエースは **`toughness × 2.4` だけ**で、戦い方は他と1ミリも変わらなかった。
**硬さは同じ戦闘を長くするだけで、難しくはしない。**

エースは**リロード中に下がらず、詰めてくる**ようにした。他の全機はリロードの隙を
くれるが、こいつはその隙を「急に近くにいる理由」に変える。バーストも長い。
手負いでも下がらない。**硬さは据え置き。**

#### 4体が「距離の違う同じ相手」だった

`orbit` / `rusher` / `flyer` は**同じ射撃ロジック・同じバースト・同じ後退条件**を
共有していて、違うのは `preferredRange` と移動の癖1行だけだった。
プレイヤーから見れば、4体とも「距離が違う同じ相手」で、個別に覚えることが無い。

**撃ち方に癖**を付けた（`HABITS`）。どれも既存のトリガーにゲートを1行足しただけで、
**見て覚えられる**差になる:

- **CRAWLER**（`closer`）: 詰めきるまで1発も撃たない。**渡ってくる時間が、こちらの番**
- **POGO**（`peak`）: 跳ねた頂点でだけ撃つ。リズムがアリーナの反対側からでも読める
- **FUNNEL**（`salvo`）: 長い溜めのあと、長く吐き出す。遮蔽に入るか、全部受けるか
- **STRIDER**（`steady`）: 正面かつ射程内なら撃つ。基準になる相手

#### ロックオンに、初めて値段が付いた

切れるのは遮蔽だけで、取得は即時・無料・無期限、乗り換えは1キーで最善の的が選ばれた。
**6体いる場面で「誰を狙うか」が判断になっていなかった。**

取得に **0.35秒**かかるようにした。短いので待たされた感じはしないが、
**戦闘中に狙いを変えるのは、もう一度その分を払うこと**になる。

#### 撃ち続ける理由しか無かった

敵にはバースト規律を入れたのに、**プレイヤー側は引き金を握りっぱなしが最適**のままだった。
連射武器は**握っているほど散る**ようにした（1.6秒で最大、離すと0.7秒で戻る）。

**ダメージは下げないし、撃てなくもしない。** 長いバーストは今も当たる — ただ、精密ではなくなる。
戻りが速いので、**短く撃つ分にはコストがゼロ**。

#### 柱を撃ち抜けていた

アリーナは最初から柱だらけで、その仕事は「ロックを切る」の1つだけ。
**弾は柱をすり抜けていた** — つまり柱の後ろに立っても撃たれる。
これは遮蔽が無いことより悪い。**効きそうに見えて効かない**から。

弾は柱で止まるようにし、**柱は削れて、最後には崩れる**ようにした。
無くならない遮蔽は「そこに立って勝つ場所」だが、無くなる遮蔽は
**いつ出るかという判断**になる。試合をやり直せば柱も戻る（同じ種は同じ試合）。

#### スコアに腕が入っていなかった

`100 × ウェーブ係数` ＋ `300 × ウェーブ`。**命中率も、無被弾も、速さも1点にならず**、
ベストスコアは「どれだけ長く座っていたか」の記録だった。

| ボーナス | |
|---|---|
| **無被弾** | 400 |
| **速攻** | 最大 300（45秒で消える） |
| **命中** | 最大 250（撃った弾に対する当てた弾） |

命中は**発射した弾数で数える**ので、散弾9発は9発。ブレードだけで倒した人は
0発中0発で、**罰されないが、払われもしない**。

#### 6体いると、脅威の順序が読めなかった

HUDの弧は**ロック中の1体**にしか出ず、残り5体は**撃たれてから**方角の弧で知らせてくる。
いま**引き金を引いている機体だけ**、画面端に方向マーカーを出す。
全機に出すとただの輪になって何も言わなくなる。

#### 弾はどこへ飛ぶか — そして、なぜ全部は当たらないのか

ロックオン中は、**プレートごとに自分で偏差射撃を解く**。相手の位置と速度、そして
**その武器の弾速**から会合点を求める（不動点反復2回）。

機体のエイムアシストが向いている先ではダメだった。アシストは「機体を向けるためのリード」を
出していて、弾速の違う武器それぞれの正解ではないので、遠距離では丸ごと外れる。実測すると
25m の相手に62発撃って**命中0**だった。

**そして、会合点をそのまま撃つのもダメだった。** 今度は逆に全部当たる。相手が何をしようと
弾はもう「これから相手がいる場所」へ向かっているので、ロックオンは照準ではなく**確約**になる。
避けても意味がないなら、動く理由もない。試合は2機が棒立ちでダメージを交換するだけになる。

そこで、**解いた会合点の手前を撃つ**。武器ごとに「どれだけリードしてよいか」を決めてあり
（`lead`、`WEAPON_LEAD_DEFAULT`）、狙って撃つ武器（スナイパー 0.6）は正解に近く、
ばら撒く武器（ガトリング 0.3、ショット 0.25）は遠い。1.0 の武器は無い。
撃った弾は**相手が選んで居ないことにできる場所**へ飛ぶ。それが避けるという行為の中身。

#### 弾の見た目は、色ではなく形で作る

弾は**加算合成でプレイヤーの選んだ色**で描かれる。なのでテクスチャは**グレースケールの
マスク**で、色を置き換えるのではなく**掛ける** — 青いビームとオレンジのビームが
同じ1枚から同じ形をもらう。キャンバスではなくピクセル配列から作っているので、
DOM の無いテストでも同じものが焼ける。

- **弾（ボルト）** … 先端が白熱し、尾に向かって落ちる。加えて**細い帯を2本**。
  帯が無いと速い弾はただの尾を引く染みになり、目が追う手がかりが無い
- **ミサイル** … 逆の形。**暗い機体、尾でモーターが燃え、先端の弾頭が光る**。
  ミサイルは「エンジンの付いた物」であって、いちばん明るいのは当たらない側の端
- **グレネード** … まだらな殻。山なりに飛ぶ弾が**転がって**見える

テクスチャは形ごとに1枚で、全スロットが共有する。マテリアルが指す先を差し替えるのは
タダだが、**マップの有無が変わるとシェーダが組み直される**ので、全スロットが常に1枚持つ。

#### ミサイルは1回しか追わない

**最接近を過ぎた瞬間に追尾をやめ、まっすぐ飛んでいく。**

燃料が尽きるまで曲がり続けるミサイルは、外しても旋回して戻ってきて、また来る。
つまり**避けても何も買えない** — 追跡が終わる唯一の方法が「当たること」になる。
諦めることが、避ける行為に意味を与えている。

- 判定は**最接近距離**。それより 2m 開いたら「外した」（0mではない — 相手が鼻先を
  横切ると距離は数cm揺れるので、それで諦めていたら何にも届かない）
- **振り切っても同じ**。30m/s のミサイルより速く逃げれば距離は開き続けるので、諦める
- **棒立ちなら当たる**。旋回半径の内側に入られない限り、追尾は完走する

#### 当てにくさは3つの掛け算

「ロックしていれば当たる」を壊すのに効いたのは、狙いだけではなかった。

**① 弾が速すぎた。** ビーム 320m/s では 25m を 0.08 秒＝**5フレーム**で渡ってしまう。
見えないものは避けられない。全体的に落として、25m の飛行時間が最低でも 0.1 秒
（＝6フレーム）を超えるようにした。ニンテンドウ64の『カスタムロボ』のように、
**弾が飛んでいく様子が見える**のが前提の速さ。

| 武器 | 旧 | 新 | 25m の飛行時間 |
|---|---|---|---|
| スナイパー | 620 | **180** | 0.14s |
| ビーム | 320 | **112** | 0.22s |
| ガトリング | 175 | **88** | 0.28s |
| マグナム | 130 | **70** | 0.36s |
| ショット | 110 | **62** | 0.40s |
| スプレッド | 95 | **54** | 0.46s |
| グレネード | 46 | **40** | 0.63s |
| ミサイル | 38 | **30** | 0.83s |

（射程は「速度×寿命」なので、寿命を伸ばして届く距離は概ね据え置いた。
マグナムだけは短射程が持ち味なので約36mのまま。）

**② 的が機体より大きかった。** 弾の当たり判定は `extent`＝**外接球の半径**を使っていた。
7m の人型なら 3.5m。つまり**機体の3.5m横を通った弾も命中**していた。これでは避けようがない。
機体は球ではないので、**立った円柱（カプセル）**に置き換えた。

- 高さは**機体の実際の高さ**。脚を撃っても当たる
- 太さは**機体が実際に持っている体積**から出す — 同じ体積・同じ高さの円柱の半径
  （`Robot._measureHitVolume`）。外接ボックスから出すと、肩に砲身を1本足しただけで
  1cm も太っていない機体の当たり判定が倍になる
- 体積は脚にも入っていて脚は細いので、平均をそのまま使うと本体が痩せる。
  そのぶんだけ太らせる係数を1つ置いてある（`HIT_COLUMN_SPREAD`）

結果、人型の当たり判定は半径 3.5m → **0.9m**。`extent` のほうは残してある
（間合い、爆風、接触判定にはあれが正しい）。

**③ 動いても当たっていた。** ①②の結果、実測はこうなった（25m、ロックオン中、1トリガー）:

| 横切る速さ | 0 | 4 | 8 | 12 | 16 m/s |
|---|---|---|---|---|---|
| ビーム | 命中 | 命中 | 命中 | 外れ | 外れ |
| ガトリング | 命中 | 命中 | 外れ | 外れ | 外れ |
| マグナム | 命中 | 命中 | 外れ | 外れ | 外れ |

**棒立ちは相変わらず致命的**で、歩く程度では避けきれず、走れば抜けられる。
距離が伸びるほど飛行時間が伸びるので、遠いほど当たらない。ロックしていないときは
機体の正面へ素直に飛ぶ。

内蔵バルカン（武器を1枚も積んでいない機体の既定射撃）はヒットスキャンなので
「弾を避ける」ができない。代わりに**外れる確率**を持たせてあり、距離だけでなく
**相手が視線を横切る速さ**でも上がる。

#### 強く撃たれた機体はのけぞる

被弾が体力バーの数字でしかないと、撃たれても撃たれなくても同じ操作ができてしまう。
**重い一撃には、そのぶんの時間を払わせる。**

- **溜めて判定する。** 直近のダメージを短い記憶（0.18秒）で足し合わせ、
  **最大HPの8%**を超えたところからのけぞる。22%上乗せで最大
- 溜めるのは、**ショットガンの9発は1発の衝撃**だからだ。1発ずつ見ていたら、
  どれも軽いので何も起きない。逆に、**細かい弾を撃ち続けても閾値には届かない**
  （ガトリングの定常値は閾値の半分）。連射は削るための武器であって、
  相手を固めるための武器ではない
- 判定は**その機体自身の耐久**に対する割合。同じ弾が軽量機を折り、重量機には効かない
- **のけぞり中は推力が 85% 消える。**速度ではなく推力を消すので、走っていた機体は
  滑り続ける。撃たれて足が止まるのではなく、**足が利かなくなる**
- **トリガーも効かない**（0.35以上のとき）。これが無いと、のけぞりは飾りでしかない
- **ノックバックは水平**。上から撃たれた機体は地面にめり込むのではなくよろける
- 見た目は**衝撃の来た方向と逆に上体が反る**。走りのリーンとは符号が逆で、
  ここを間違えると機体が撃った相手にお辞儀をする（弾は足ではなく胴に当たるので、
  上体は置いていかれるのではなく**押される**）
- のけぞりは**上書きされない**。重い一撃の直後に軽い弾が当たっても、深いほうが残る

#### 一定以上の衝撃は、のけぞりではなく吹き飛ばし

のけぞりの強さを「最大1」で頭打ちにしていたら、**バーを超えた重い武器が全部同じ手応え**に
なった。マグナムも、スナイパーの直撃も、同じようによろめくだけ。

そこで**1で止めるのをやめた**。衝撃は「のけぞり何回分か」という単位で測っていて、
1を超えたぶんは**上向きの力**に変わる。

- **ノックバックはインパルス**（`ZMFBody.knockback`）。速度を書き換えるのではなく足すので、
  **走っている最中に撃たれるほど遠くへ飛ぶ**
- 1未満：水平にだけ押す。上から撃たれた機体を地面にめり込ませても、
  下から撃たれた機体を打ち上げても、それは足がやることではない
- 1以上：押しが増え、**一部が上向きに変わる**。機体は床から離れ、
  `downed`（0〜1）が立って**推力が完全に消える**
- **`downed` は時計で消えない。** 着地して落ち着くまで持続する。
  空中で待っていればやり過ごせる、では吹き飛ばしにならない
- 吹き飛ばされた機体は、**軽くても着地に失敗する**。重さのゲートは「段差を降りた」と
  「落ちてきた」を分けるためのもので、アリーナの端まで飛ばされたのはどちらでもない
- 見た目は**のけぞりと同じ動きを数倍**（`FLINCH.sprawl`）。着地するまで戻らない

**接地の平滑値では「落ち着いた」を判定できない。** `grounded` は3ステップかけて上がるので、
撃たれた直後の数フレームは「まだ接地」と言い続ける。その間に `downed` が半分溶けた。
上下方向の速度も落ちていることを条件に足した。

#### 横に流されている2脚は、歩かずに滑る

**自分の脚では出せない速さで横に動いているとき、歩容を走らせるのをやめる。**
脚が届く以上に遠くを、動ける以上に速く振ることになり、
実際**時速100kmでムーンウォークする機体**が出来上がっていた。

- 判定は**その機体自身の数字**から出る。滑り始めは `groundSpeedCap`（脚で出せる上限）、
  滑り切りは `dashSpeed`。**間の数字は誰も決めていない**
- 横にその速度が出るのは**ダッシュ（インパルス）だけ**。推力では上限の壁に阻まれるので、
  「自分の力で走っていたら滑る」は起きない
- 滑っている間、**歩調は0にブレンドされ**、代わりに**両脚が同じ側へ寝る**
  （`axisSplay` 周りに最大42°）。足を床に置いていかれ、body だけ先へ運ばれる形
- 上体は**流されている方向へ深く傾く**。ストレイフのリーンと同じ符号で、量が違うだけ
- **土埃が増える**（間隔が0.4倍、粒も大きい）。足を上げずに引きずっているので
- 立ち上がりは**半減期0.015秒**。ダッシュの速度は0.2秒で壁に食われるので、
  これより遅いと**ピークを一度も見ないまま終わる**

#### 重い機体は、着地でふんばる

空から落ちてきて何事もなかったように走り出す機体は、数字が何と言おうと**軽い**。
機体の重さが実際に見えるのは、止まるときだ。

- **一定の重さから上だけ**（`LANDING.weight` 〜 `full` で 0→1）。軽量機がホップの
  たびに踏ん張ったら、ただ動きが鈍いだけの機体になる
- **落下速度でも決まる**。段差を降りるのは着地ではない
- 見た目は**膝が畳まれ、その上に body が沈む**。歩容を置き換えるのではなく
  **上乗せ**するので、走りながら着地した機体は走り続ける — 最初の一瞬だけ腰を落として
- 床には**輪と土埃**。輪の大きさは機体の**足の幅**であって胴の幅ではない
- **操作は奪わない**。のけぞりと違って、これはポーズ。重量機が着地のたびに
  0.5秒動けなくなるゲームは誰も頼んでいない

**着地の検出は接地の平滑値では取れなかった。** `grounded` は3ステップかけて上がるので、
「着地した」と言えるようになった頃には、**どれくらいの速さで落ちてきたかが消えている**
（次のサブステップでは落下速度が跳ね返しで書き換わっている）。地面プローブが接触した
**そのサブステップ**でだけ落下速度を記録し、ステップ内の最大値を採る。

#### 機体を分類名で呼ばない

内部では歩容を `hover / hop / walk / multileg` に分けている。**どの脚を振るかを決めるため**の
分類で、機体の種別ではない。

画面に出した瞬間に種別になる。「二足歩行」と表示された機体は二足歩行という**カテゴリの
所属物**になり、次に作るものはそのラベルに向けて作られる。作ったのは自分の形のはずなのに。

- スペックパネルの**歩容バッジを外した**
- フィールドの読み出しは `GAIT: WALK` → **`LEGS: 2`**。脚の本数は
  **部品についての事実**なので出す。そこから何が言えるかは、機体が動いて見せる
- プリセット名から本数を外した（`2脚 STRIDER` → **`STRIDER`**）。
  4機の一覧が、**選ぶカテゴリの一覧**に見えていた
- ヘルプとボーンの説明文からも分類語を外した
- `GAIT_LABEL`（表示名の表）は**削除**した。使わないものが残っていると、また誰かが出す

### ボーンを組むのが楽になる仕掛け

ボーンは「中央が関節、手前半分は動かない」という構造が強い代わりに、
**組んでフィールドに出るまで結果が分からない**のが弱点だった。そこを 3 つ潰してある。

**1. 関節が見える。** ボーンを1本選ぶと、その場に読み取り線が出る。

| | |
|---|---|
| **青い弧** | 可動範囲。`可動域` を変えると弧も広がる／狭まる |
| **黄色い線** | 回転軸そのもの（ヒンジ） |
| **緑の線** | **動く側**（関節から先端まで）|

「思っていたのと逆に曲がる」「なぜ動かない（＝固定側に付けていた）」が、
出撃せずに分かる。

**2. 先端にボーンを継げる。** インスペクタの `＋ 先端に○○ボーン` 一発で、同じ属性のボーンが
先端に生える。太腿→脛のような連結を、数ピクセルの棒の先端を狙ってクリックせずに作れる。

**3. 固定側／可動側をボタンで移せる。** ボーンに付いている子を選ぶと
`根元へ` `可動側へ` `先端へ` が出る。中点をまたぐドラッグを目分量でやらずに済む。

### カスタムボーンの動きを作る

「軸・振幅・速さ・ソース」だけでは、実際どう動くのか想像するしかなかった。

**動き方（波形）を選べるようにした。**

| | |
|---|---|
| **波（なめらか）** | サイン波。既定 |
| **往復（一定速）** | 三角波。等速で往復する |
| **パタパタ** | 矩形波。2つの角度を行き来する |
| **回転（ぐるぐる）** | **可動域を無視して回り続ける。**プロペラ、レーダー、タイヤ向け |

- **回転だけは可動域を無視する。** 70°で止まるプロペラはプロペラではないので
- 回転の駆動ソースは**角度ではなく回転速度**にかかる。速度連動にしておくと、
  減速したときに角度が巻き戻らず、回転がゆっくりになるだけで済む
- **中心角**（-90〜90°）で振れの中心をずらせる。「上向き45°を中心に±20°」が作れる
- **位相ずらし**（0〜1）で、同じ設定のボーン同士の動きをずらせる。多脚の波打ちや、
  左右で逆位相の腕はこれで作る
- **選択している間、編集画面でその動きが再生される。** 他の関節は止めたままなので、
  いま触っているボーンの動きだけが見える

### アンドゥ・リドゥ

**すべての編集操作が 1 手ずつ戻せる。** `Ctrl+Z` / `Ctrl+Y`、または左上の `↶` `↷`。

方式はスナップショット式で、変更の**直前**の文書全体（JSON、ボクセルは RLE）を積む。差分方式に
しなかったのは、彫刻・寸法変更・連結・パーツ移植が同じ木を別々の粒度で触るので、差分の定義自体が
操作ごとにばらけるため。スナップショットなら「復元 = `Assembly.fromJSON` してリグを組み直す」の
一手で、どの操作から戻ったかを気にしなくてよい。

- 履歴は **60 手 / 48MB** のどちらかに当たった時点で古いものから捨てる
  （1/100 解像度のブロックを何個も抱えたまま 60 手ぶん持つとメモリが破綻するため）
- ボタンの tooltip に「元に戻す: 削る」のように**何が戻るか**が出る
- 彫刻は **1 ストローク＝1 手**。ドラッグ中のフレームごとには積まない
- **スライダも 1 ドラッグ＝1 手**。これは後から直した — 寸法スライダを 1.0→3.0 に
  動かすと **9 手積まれ、元に戻すのに 9 回**押す必要があった。1手が機体まるごとの
  スナップショット（約 8.5KB）なので、**スライダを7回動かせば履歴が全部流れる**。
  ギズモは最初から正しくやっていた（ドラッグ開始時に1回だけ積む）ので、
  同じ考え方をスライダにも入れた
- **時間では判定しない。** 0.5秒あけた2回の調整は2手であって、時計にはその区別が
  つかない。ウィジェット側が「掴んだ／離した」を宣言する（`beginGesture` /
  `endGesture`）。`input[type=range]` はパネル全体で**1箇所に委譲**して拾うので、
  今あるスライダも、これから足すスライダも、書き忘れようがない
- 履歴は**文書ごとに独立**。メイン機体とワークベンチのパーツは互いの履歴を汚さない
- プリセット読み込み・ファイル取込は履歴をクリアする（そこが新しい起点になる）

### コピー＆ペースト

`Ctrl+C` / `Ctrl+X` / `Ctrl+V`。複数選択したままでも動く。

コピーは選択パーツ（の配下ごと）を **独立した文書として切り出し**、貼り付けは
それを木に**移植**する。つまりコピペとパーツ庫は同じ 2 つの操作でできている:

| | |
|---|---|
| `Assembly.extract(id)` | 部分木を独立した文書へ。ルートは `block` に降格し、使っている色だけを持つ小さなパレットに詰め直す |
| `Assembly.graft(doc, parent, mount)` | 文書まるごとを別の木へ。ID を振り直し、パレットを併合し、貼り先のボクセル解像度に合わせる |

同じものを何度貼っても ID は衝突しない。コアをコピーしても、貼られる側は普通のブロックになる
（コアが 2 つある機体は作れない）。

### パーツ編集（ワークベンチ）とパーツ庫

上部の `パーツ編集` に入ると、**パーツ 1 個だけの文書**を編集する画面になる。ルートはコアではなく
ただのブロックで、機体と同じようにブロック・ボーンを生やし、寸法を変え、削って盛って塗れる。

- **`パーツ庫に保存`** … 名前を付けて localStorage（`blostom.parts.v1`）に保存。同じ名前は上書き
- **`新規`** … まっさらな 1 ブロックから作り直す
- **`← メイン編集`** … 機体編集へ戻る。**機体とパーツは完全に別の文書**なので、往復しても
  どちらの編集内容も履歴も失われない

メイン編集の右パネルに **パーツ庫** が出る。

- **`配置`** … スタンプツールが装填される。**置きたい場所をクリックするとその場に移植される**。
  面をクリックすれば吸着、何もない所なら作業平面の上。1 手で戻せる
- **`編集`** … そのパーツをワークベンチで開く（庫の中身とは独立したコピーなので、
  保存するまで元は変わらない）
- **`×`** … 庫から削除
- **`選択パーツを登録`** … 逆向き。**機体で選んでいるパーツを配下ごと庫に入れる**。
  作り込んだ腕を反対側にも使う、といった用途

### ブロックとサイズ

ブロックの面にさらにブロックやボーンを生やせる。

- **寸法は XYZ 個別に 0.25〜4.0 を 0.25 刻みで自由に変更できる**（インスペクタのスライダ）。
  隣り合うブロックの間隔は「双方の寸法の半分ずつ」で計算されるので、どんな寸法でも面がぴたりと合う。
- ボーンは **長さ**（0.5〜12）と **太さ**（0.04〜0.6）を自由に変えられる。細／中／太はプリセットボタン。

### ブロックの形（20種）

**ブロックは四角だけではない。** ツールパネルとインスペクタの「形」から 20 種類を選べる。

| 分類 | 形 |
|---|---|
| **基本** | 立方体 / 球 / 円柱 / カプセル / 六角柱 |
| **先細り** | ドーム / 円錐 / 円錐台 / 四角錐 / 八面体 |
| **角** | 四面体 / 面取り / 斜面 / 三角柱 / 階段 |
| **抜き** | 筒 / 輪 / アーチ / 十字 / 皿 |

#### 形は「別のジオメトリ」ではなく、ボクセルの詰め方

20種類を現実的な工数で入れるための一手。**形はマスク関数 1本**で、ブロックは今まで通り
ただのボクセルグリッドのままにしてある。おかげで

- **どの形でも削る・盛る・塗るがそのまま効く**（球を彫れる）
- グリーディメッシャ・保存・共有コード・当たり判定は**一切変更していない**
- **重さが勝手に正しくなる。** 質量は元から実体セル数で計算しているので、
  球は同じ寸法の箱の **約53%** の重さになる

代償は「球がボクセルの球になる」こと。ただしボクセルブロックで組む
ゲームなので、**なめらかな球のほうが浮く**。こちらが正しい側の割り切り。

#### 寸法に合わせて伸びる

マスクは **正規化座標**（各軸 -1..1）で判定している。つまり形は常にブロックの箱いっぱいに入る。
`2 × 0.5 × 1` のブロックに球を入れれば**潰れた楕円体**になる。円柱を薄くすれば板になる。
形 20 種 × 自由な寸法なので、実際に作れるシルエットはもっと多い。

#### 覚えておくこと

- **形を変えると中身は作り直される。** 彫った跡は消える（1手のアンドゥで戻せる）
- 複数選択したまま形を選べば**まとめて切り直す**。ボーンや装備プレートは黙って飛ばす
- 形は「何から切り出したか」の記録。そのあと彫れば、当然その通りにはならない
- **コアの面取りも今は形の 1つ。** 従来 `bevel(0.22)` で削っていたものと
  既定解像度 1/32 で**1セル違わず同じ**になるよう合わせてあるので、既存の機体の見た目は変わらない
- 古い保存データに形の情報は無いが、当時は全部四角だったので**そのまま四角として読む**
- **設置カーソルも選んだ形になる。** 「球」を選んでいるのに四角い枠が出ていたら、
  カーソルが嘘をついていることになる。プレビューは本番と同じ `VoxelBlock` と
  メッシャで切っているので、出るものがそのまま出る
  - ただし**解像度は 1/32 で頭打ち**。半透明のプレビューで 1/100 との差は見えないし、
    マウスを動かすたびに 100万セル刻むのは高すぎる。形ごとに 1回だけ切って使い回す
  - **白い枠線は箱のまま。** これは形ではなく**占有する範囲**で、次のパーツが
    どこに置けるかを決めているのはこちらなので

#### 解像度を上げると、彫っていない形は切り直す

加工の細かさを変えたとき、**まだ誰も彫っていないブロックは新しいグリッドで形を切り直す**。
再サンプルだと球の階段が拡大されるだけで、細かくした意味がないため。
一度でも彫ってあるブロックは従来通り再サンプルする（彫った跡を消さないため）。

### 加工（ボクセル）

1 ブロックの中身を削る／盛る／塗れる。刻みは **1辺あたり 1/16・1/32・1/50・1/100 から選択**（既定 1/32）。

> **1/100 は 1 ブロックあたり 100×100×100 = 100 万セル**になる。破綻せず編集できるよう、
> グリッドをチャンクに分割し、ブラシが触れたチャンクだけメッシュを作り直している。
> それでも 1/100 はメモリ 1MB/ブロックを食うので、既定は 1/32 にしてある。
> 解像度を切り替えると既存の形状は最近傍でリサンプルされる。

ブラシサイズは **ブロック辺長に対する %** で持っている。解像度を変えても削れる範囲は変わらない。

#### ブラシの形は立方体

**削る・盛る・塗るは、いずれも軸に沿った立方体で加工する。** 半径 r なら
`(2r+1)³` セルぴったり。

丸いブラシはグリッドに落とすと形が保たない。半径 1 の球は「中心＋面隣接 6 セル」＝
**十字（3D のプラス記号）**、正四面体は塊にはなるものの**斜めに欠けた楔**になり、
どちらも「どこがどう削れるのか」が読めない。立方体なら

- **カーソルの箱がそのまま結果になる。** 見えている通りに削れる／盛れる
- **常に正方形。** どの向きから見ても同じで、面と角がグリッドに揃う
- **同じクリックは必ず同じ形。** 半径はセル単位の整数なので、余裕（スラック）も要らない

ボクセルグリッドの上に四角いブロックを積んでいくゲームなので、加工の単位も四角が正しい。

#### 盛るはブロックの外へはみ出せる

**ブロックの外側を「盛る」と、その方向にブロックが 0.25 だけ伸びる。** 面で止まらない。

やり方はいくつか考えたが、採ったのは「**箱を伸ばして中身を組み直す**」案。

| 案 | 却下した理由 |
|---|---|
| はみ出した分を別ブロックとして生やす | 1つの形が細かいブロックに分裂して、あとで扱えない |
| グリッドをブロックの外にはみ出させる | 「ジオメトリは単位立方体空間」という前提が壊れる |
| **箱を伸ばして中身を再グリッド** | 採用。形も寸法も 1つのブロックのまま |

グリッドは常に n³ でブロックの箱ぴったりを覆うので、箱が伸びると**セルが大きくなり**、
既存の中身は新しいグリッドの一部分を占めることになる。そこで再グリッドでは
**新セルが覆う旧セルを全部見て、1つでも実体があれば実体にする**。
最近傍で拾うと 1セル厚のディテールが消えるが、この方式なら太る方向にしか転ばない。

- **既存の形はその場から動かない。** 箱の中心が半分ずれるぶん、ブロック自身の
  マウントを同じだけ動かして相殺する
- **そのブロックに付いているものも動かない。** 子のマウントを逆向きに同じだけ動かす。
  でないと「+X に伸ばしたら -X 側の腕まで一緒に動いた」ことになる
- コアにはマウントが無いので、そこだけは子だけが動く
- カーソルがブロックの外に出ると**黄色**に変わる（次のクリックで箱が伸びる合図）
- 上限は通常の寸法と同じ 4.0。超えるとトーストで断る
- 1回の拡張＋盛りが 1手のアンドゥ

加工が効くのは見た目だけではない：

- **質量は「実際に詰まっているボクセル体積」で決まる**
- **推力は「ブロックの表面積」で決まる**

つまり **中を刳り抜くと、推力そのままで軽くなる** = 機動性が上がる。
逆に **ブロックを大きくすると質量は体積（3乗）で、推力は表面積（2乗）でしか増えない** ので、
大型化は必ず鈍重になる。

### 色

- **標準色 16 色** … 固定。パレット先頭に常に居座るので、インデックスの意味が変わらない。
- **カラーサークル** … HSV の色相環＋明度スライダ＋16進入力。選んだ色はパレット末尾に追加され、
  カスタム色として並ぶ。保存時に、どのボクセルからも参照されていないカスタム色は自動で掃除される。

色はボクセル1つ1つがパレットの添字を持つ形で保存されるので、後から色を選び直しても
すでに塗った面の色は変わらない。

### ボーン

細長い骨パーツ。**中央が関節**で、手前半分は親側と一体、奥半分から先が可動部になる。

```
      親ブロック
          │
   ┌──────┴──────┐
   │  near half  │  ← 親と一体（ここに刺したブロックは動かない）
   ├─────●───────┤  ← 関節（ここが曲がる）
   │  far half   │  ← 可動（ここに刺したブロックが動く）
   └─────────────┘
          ↓ 先端にさらにボーンを繋げば「膝」になる
```

シャフトにはブロックを串刺しにできる。位置は自由なので、シャフト上のどこにでも置けるし、
シャフトから離して浮かせることもできる。**中点より手前なら親と一体、奥なら可動部**という
判定だけがあり、ギズモで中点をまたいで動かすと連動先の半分が自動で切り替わる。

| 属性 | 挙動 |
|---|---|
| **レッグボーン** | 脚。1 本なら跳ねる、2 本なら歩く、3 本以上は**多脚**歩行 |
| **アームボーン** | 腕。移動中は歩調と逆位相で振り、ロックオン中はロック方向を向く |
| **フェイスボーン** | 顔。進行方向に傾き、ロックオン中はターゲットを向く |
| **カスタムボーン** | 軸（前後／ひねり／上下）・振幅・速さ・駆動ソース（常時／**歩調**／速度／推力／衝撃／ロックオン） |

> **「脚 1 本 / 2 本 / 3 本以上」は “脚の本数” で数えている。**
> レッグボーンの総数ではない。腿＋脛のように 1 本の脚をボーンで繋いだ場合、
> 上流にレッグボーンを持たないボーンだけを 1 本の脚として数える。
> そうしないと「膝のある二足歩行」が作れないため。

#### 肩・股関節・腰は、種類を増やさずに属性で作る

肩ボーン・腰ボーン・股関節ボーン…と種類を足していくと、**組み合わせのぶんだけ
実装が増えて、しかもどれを使えばいいのか分からなくなる**。そこで種類は 4 つのまま、
**すべてのボーンに 2 つの数値**を持たせた。

| 属性 | 範囲 | 何を決めるか |
|---|---|---|
| **効き** (`gain`) | 0〜2 | その属性の動きを**どれだけ取るか**。0 で固定、1 で標準、2 で大振り |
| **ずらし** (`lag`) | 0〜1 | 歩調 1 周のうち**いつ動くか**。先端側ほど遅らせるとしなる |

これで、よくある関節はすべて既存のボーンで表せる。

| 作りたいもの | 作り方 |
|---|---|
| **肩** | アームボーンを腕の付け根に置き、効きを 0.4 程度まで落とす |
| **肘** | その先にアームボーンを繋ぐだけ（後述の自動減衰が働く） |
| **股関節** | 脚の根元のレッグボーン。効きは標準のまま |
| **膝** | その先のレッグボーン。ずらしを 0.05〜0.1 入れると脛が振れて見える |
| **腰** | カスタムボーンで軸「ひねり」、駆動ソース「**歩調**」 |

インスペクタには **肩／股関節／しなり／固定** のワンクリック設定も置いてある。

**アームの連鎖は自動で減衰する。** アームボーンの上にさらにアームボーンがある場合、
下側は「前腕」とみなして振り幅が `0.55^深さ` になり、少し遅れて追従する。
これがないと肩と肘が同じ角度だけ曲がり、**腕が二重に折れて**しまう。

**駆動ソース「歩調」** は、波の時計に**歩行サイクルそのもの**を使う。
自由な時計で回すと足の運びとだんだんズレていくが、歩調なら定義上ズレない。
腰のひねりに必要なのはこちら。止まれば歩調も止まるので、腰も止まる。

#### ボーンの向きについての注意

パーツの位置と回転は **常に親のローカル座標** で解釈される。ボーンの先端に別のボーンを繋ぐと、
その回転は「親ボーンのローカル軸」基準になる（ボーンのローカル +Y ＝ シャフト方向）。
横向きのボーンの先に「-Y 方向」を繋ぐと、下ではなく機体側へ折り返してしまう。
多脚プリセットは **股関節を真下に向けて生やし、開き（splay）はアニメーション側で付ける**
構成にしてあるのはこのため。

#### 走ったときに形が固まらないこと

歩容そのものは前から動いていたが、**走っている機体の「形」が止まって**いた。
原因は2つとも脚ではなかった。

| | |
|---|---|
| **肘が伸びきったまま** | 腕の振り幅が最大26°、しかも肩の効きが0.45で実質12°。腕を伸ばしたまま前後に少し揺れるだけの人形になっていた |
| **胴が起きたまま** | 前傾の上限が0.20rad（11°）。全力で走っていても直立していた |

直したのは Animator 側なので、**プリセットだけでなく自作機にも効く**。

- 腕の振りを 26° → 34°、プリセットの肩の効きを 0.45 → 0.85
- **連なった腕（＝前腕）に、速度に応じた「畳み」を入れた**（5°〜42°）。
  止まっていればほぼ真っ直ぐ、走れば肘が上がる。肘が伸びきった腕は、
  脚がどれだけ正しく動いていても「引きずられているマネキン」に見える
- 前傾の上限を 0.28rad（16°）へ

畳みは**振りではなく休息姿勢**なので、「前腕は肩より振らない」という以前からの
決まりはそのまま。ただし測り方は変えた — 静止姿勢から見た角度の大小では、
オフセットを持つ関節が常に大きく出てしまう。ストライド軸まわりの**符号つきの振り幅**で
測るようにして、畳みと振りを混ぜずに比べられるようにしてある。

#### サークル：線を引いて、その上のものを運ぶ

ローリングが「貼りついたブロックを回す」のに対して、サークルは
**貼った場所を中心に円線を引き、その線の上に立っているものを線に沿って運ぶ**。
砲塔のリングや回転する足回りはこれ。

- **半径**をインスペクタで決める（0.5〜6.0m）＝ 円線の大きさ。ただし
  **貼った時点で、まわりに立っているパーツに合わせて自動で決まる**（下記）
- **円線の向き**もインスペクタで決める（面に沿う／縦・前後／縦・左右）
- 対象は**円線に触れているパーツ**。そこから先に繋がっているものは全部一緒に回る
- **どのブロックに付いているかは問わない。** 頭にプレートを貼って、胴に生やした
  ポッドが線に触れていれば、それは回る（そこが親子でないのは作った側の都合であって、
  遊ぶ側には見えない）。**間に関節があってもいい** — 首の先の頭にプレートを貼り、
  胴に付けた球が線の上にあるなら、球はリングに乗り、ついでに首の動きにも乗る。
  そこで何かを横取りしているわけではないので、止める理由がない
- 逆に**プレートより先のボーンにぶら下がっているものは対象外**。腕の先の手は腕のもので、
  リングが横取りすれば腕だけが空を振ることになる
- 「触れている」は**そのパーツ自身の body が線に届いているか**で判定する。
  中心からの距離ではなく、**その方向にどれだけ張り出しているか**（箱の支持関数）を測るので、
  同じブロックでも**向きを変えれば届いたり届かなかったり**する。
  余裕（あそび）は足していない — 見えない数字で決まると、同じくらい近い2つのどちらが乗るのか
  誰にも読めなくなる。位置も半径も 0.25m 刻みなので、「触れる」は狙って合わせられる
- **円の中に置いただけのものは回らない。** ここは「面」ではなく「線」
- **線から軸方向に離れているものも回らない。** 判定は「円線という1本の線に body が届くか」
  であって、半径さえ合っていれば高さは問わない、ではない（それだと頭に貼ったプレートが
  機体の反対側の脚まで掴む）。ただし**線の上に立っているものは足元が線に触れている**ので、
  高く伸びたパーツもまるごと一緒に回る
- インスペクタに「回るパーツ」の数が出る。0 なら線から外れている

**半径は貼った瞬間に合わせにいく。** 既定値を 2m 固定にしていた頃、
**普通の大きさの機体では線が部品より外を通り、貼っても何も掴まなかった**。
プレートが壊れて見えるうえ、直す手段は「何か動くまで半径スライダを勘で動かす」しかない。
パーツはプレートを貼る時点でもう並んでいるのだから、プレート側が見ればいい —
**いちばん多くのパーツに触れる円**を選ぶ（同数なら小さいほう）。
半径を明示して置いた場合は、その値を勝手に触らない。

判定は `Rig.fitRingRadius`、つまり**組み上がったリグの実座標**で行う。
マウントから計算すると「別のブロックに付いているパーツ」を取り違えるが、
そここそ合わせたい相手なので、実物を測るほうに置いている。

**向きを変えられるようにした理由。** 円線の向きは、既定では**貼った面**が決める。
デッキの上面に貼れば水平の円が出るが、胸の前面に貼ると円は**縦に立つ** — そこには
たいてい何も立っていないので、「乗るはずのパーツが乗らない＝ギミックが壊れている」に見える。
プレートを貼り直す以外に直す手が無かったので、向き自体を選べるようにした。
（円の**中心**は貼った場所のままなので、砲塔リングを作るならデッキの**上面の中央**に貼るのが早い。）

**円線はプレートに付いていく。** 円の土台はリグを組むときに1回だけ置かれていたので、
プレートをドラッグすると**線だけ元の場所に取り残されていた**（乗っていたパーツごと）。
土台の位置は所詮プレートのマウントから導けるものなので、編集画面では毎フレーム導き直す。
乗り手の位置も同じように自分のマウントから導き直すので、プレートを動かしても
**乗り手が一緒に引きずられることはない**。
誰が線の上にいるかの再判定だけはリグの組み直しなので、**ドラッグの終わりに1回**やる
（マウスを動かすたびに出入りさせても意味がない）。

**回るパーツが0のときは、パネルが理由を出す** — 向き・円の中・線からの高さ・関節の先の4つ。
0 という数字だけを出すのは、「壊れている」と読ませるのと同じこと。

**円線は編集画面にだけ出る**（左パネルの「サークルの円線を表示」で消せる）。
どこに置けば乗るのかが見えないと、半径のスライダは当てずっぽうになる。
フィールドに出た機体は自分の足場を身につけたりしない — 同じ機体文書から組んだリグでも、
ガイドを点けるのは編集画面だけなので、そのまま出撃しても線は出ない。

**面ではなく線にした理由。** 半径の中身を全部回していた頃、半径スライダの意味は
「機体のどこまでを巻き込むか」だった。それは狙って決められる数字ではない。
線なら「ここに置けば回る」が一目で分かり、置く場所そのものが設計になる。

**ギミックは1枚ずつ止められる。** 回っているリングの上には何も置けない
（置こうとした先がカーソルの下から動いていく）ので、インスペクタの「動かす／止める」で
そのプレートだけ止められる。**編集中だけの話**で、フィールドでは止めた覚えのない
ギミックも含めて全部回る。

どのパーツがリングに乗るかは**リグを組むときに決まる**（プレートと同じ剛体の中を歩いて、
線に触れているものを回転グループに付け替えている）。プレートを置いた時点では
まわりのパーツがまだ存在しないので、これだけは木を組み終えてからの後処理にしてある。
半径・向きを変えると組み直す。

付け替えるとき、乗り手の位置は**ワールド行列から取り直して**リングの枠に入れる。
親が違えば座標系も違うので、自分のマウントの数字をそのまま使うと**貼った瞬間に
機体が並び替わる**。乗り手はホストの枠から見た自分の居場所を覚えていて（`ringHome`）、
プレートが動いてもそこへ戻る。

#### フロート：接地しない

**常に地面から 1.4m 浮いた状態で「着地」する。** 実装は乗り高（rideHeight）を
その分だけ上げているだけで、歩行も旋回もジャンプもそのまま動く。脚は宙に浮く。

**グラビティとは同時に装備できない。** 片方が「地面から離れない」、
もう片方が「地面に触れない」と言っているので、両立しようがない。
付けようとすると理由を出して断る。

#### 浮いている間の脚は、歩かない

床が無いのに歩容を再生すると「宙で足踏み」になる。そこでフロート装備時は
**歩調の時計そのものを止め**（腕は待機の揺れに落ち、歩調駆動の腰も止まる）、
脚は歩容ではなく**慣性**で動かす。

土台は 1本のベクトルだけ。**振り遅れ（legSway）** ＝
「加速の逆向きに放り出され、進行方向に引きずられる」を減衰で追わせたもの。
遅れて着いて遅れて止まるので、*保持されている*のではなく *ぶら下がっている* ように見える。

| 脚 | 動き |
|---|---|
| **1本** | 純粋な振り子。慣性が置いていった場所にいる。膝は伸び切らない |
| **2本** | ANUBIS のジェフティのように、少し後ろへ垂らして膝を軽く畳み、爪先を伸ばす。推力が強いほど後ろへ流れ、左右は逆位相でわずかに揺れる |
| **3本以上** | 内側へ円を描いて折り畳む（虫の飛行時）。関節ごとに同じ向きへ少しずつ多く曲げると、その連なりが弧になる。前脚は前へ、後脚は後ろへ畳むので、脚が真ん中で団子にならない |

> **符号について。** ストライド軸は `Z × S` で、`(Z × S) × S = -Z`。
> つまり**正の回転で先端は後ろへ**動く（横方向も同じで、正で内側へ）。
> フロートの姿勢はすべて「後ろ・内側が正」で書いてある。
> ぶら下がった脚は、生の軸の符号よりそちらの言葉のほうがはるかに素直に書ける。

### 耐久力と、負けたときの壊れ方

**HP はコアブロックのサイズと機体の重さで決まる。**

```
HP = 40 + コアの一辺² × 60 + 質量 × 5      （×グラビティの +45%）
```

コアの一辺は体積の立方根なので、`4×1×1` のような平たいコアも体積で正しく評価される。

| コア | HP（2脚・質量約9） |
|---|---|
| 0.5 | 95 |
| 1.0 | 144 |
| 1.5 | 231 |
| 2.0 | 359 |
| 3.0 | 752 |

- **タフさを買う手段はコアを大きくすること。** その代わりコア自体の質量で鈍くなるので、
  「硬いが遅い」「脆いが速い」がひとつのつまみで表現される
- 重さも効くが**穏やかに**。そうしないと「とりあえずブロックを盛る」が
  「コアを設計する」に勝ってしまう

#### 爆発とバラバラ

HP がゼロになると、機体は**自分のパーツのままバラバラになる**。

- 破片は**そのパーツのジオメトリと色をそのまま使う**。汎用のキューブを撒くと、
  このゲームの唯一の取り柄（自分が組んだ形が壊れる）を捨てることになるので
- 破片は死んだ瞬間の**そのパーツのワールド変換から**飛び出す。腕は腕の位置から、
  脚は脚の位置から離れていく
- 中心から外向き＋やや上向きに射出され、重力で落ち、地面でバウンドして転がって止まる。
  3〜4.5秒で消える
- 爆発は 白い閃光 → オレンジの火球 → 地面を走る衝撃波リング ＋ 火花。
  **大きさは機体の寸法から決める**（アリーナの寸法から決めたら核になった）

#### お試し：撃破したら復活する

デバッグフィールドなので、**倒された機体は 2.6 秒後に復活する**。

- 敵はプレイヤーから 34〜60m 離れたアリーナ内のどこかに、HP 満タン・弾倉満タンで戻る
- プレイヤーが落ちたときはスタート地点に戻る（通常のリスポーンと同じ経路）
- 復活待ちの機体は AI も物理も止まる。残っているのは転がっている破片だけ

### QRコードで共有する

上部バーの `⧉`（パーツ編集では ⧉ 共有）から、**いま編集しているものを QR とテキストコードで
持ち出せる**。機体でもパーツでも同じ画面。

**彫っていないブロックは、セルの並びではなく「形＋色」で保存される。**
球のボクセルグリッドは、誰も触っていなくても RLE で数千のランになる。それを書き出すと
20種の形を使った機体は QR に入らない — プリセットを組み直した時点で、STRIDER の
JSON は 152,174 文字あった。形と色だけ書けば 8,272 文字。**18分の1**。

読み込み側は、セルが書いてあればそれを使い、書いていなければ形から切り直す。
判定（「このグリッドはまだその形のままか」）は**全セルの走査**なので、
メッシュの dirty フラグに相乗りしてキャッシュしてある。**保存は編集のたびに走る**
（アンドゥ履歴の実体がそれ）ので、毎回 25ms 走らせるわけにはいかない。
書き込みのある経路は必ず dirty を立てるから、「触ったのに触っていないと答える」ことは
構造上できない。アンドゥ履歴もそのぶん小さくなり、同じメモリ予算でずっと深く遡れる。

書き出し:

- **QR** … 画面表示、［拡大］で全画面、［PNG保存］でファイル
- **テキストコード** … `BRO1:` で始まる1行。チャットに貼れる

読み込み:

- **QR画像をドロップ**（またはクリックして選択）
- **コードを貼り付け**
- 読み込んだものが**機体なら編集画面へ、パーツならパーツ庫へ**入る。
  作業中の機体がパーツ1個で上書きされることはない
- 取り込みは 1手のアンドゥで戻せる

#### 中身と、正直な制約

JSON をそのまま QR に入れるのは無理（2脚で 4.9kB、QRの上限は 2953バイト）。そこで
**deflate して base64url** にしている。2脚で **1.0kB**、4脚で 1.1kB。プリセットは全部収まる。

| | JSON | 共有コード |
|---|---|---|
| コアのみ | 1.5kB | 489B |
| 2脚 | 4.9kB | 1.0kB |
| 4脚 | 5.5kB | 1.1kB |

**制約: この密度の QR は小さく写すと読めない。** 実測で、129モジュールの QR は
1モジュールあたり約6ピクセル（＝760px 以上）ないと読み取りに失敗する。

- スマホで読むなら **［拡大］で全画面表示**してから写す
- ファイルで渡すなら **［PNG保存］（10px/モジュール、約1400px）をそのまま送る**。
  途中で縮小されると読めなくなる
- 細かく彫り込んだ機体はコードが伸びる。QR に入らない場合はその旨を表示して、
  テキストコードだけを出す

エンコードは `qrcode-generator`、読み取りは `jsqr`。どちらも実績のある実装で、
**書き出した QR を実際に jsQR で読み戻せることをテストで確認している**
（自前で QR コーデックを書くと、外部の読み取り機で検証できないまま
「読めない QR」を出荷する危険があるので避けた）。

## 3. 歩容

| 脚 | キー | 動き |
|---|---|---|
| 0 | `hover` | ホバー。脚はふわふわ流れるだけ |
| 1 | `hop`（単脚） | 接地で縮んで溜め、離陸で伸び、空中では畳む |
| 2 | `walk` | 位相反転のストライド＋片方向にしか曲がらない膝 |
| 3+ | `multileg` | **多脚**。左右交互＋前後スイープの位相配分 |

**脚は慣性の向きに踏み出す。** 真横に平行移動しているときは足も真横へ、斜め移動なら斜めへ。
機体のローカル水平速度から進行方向 D を出し、ストライド軸を `A = D × S` として毎フレーム
組み替えている（`Z×S` と `X×S` の線形結合で済む）。進行方向ベクトルは lerp ではなく
**角度で回して**いる — 真後ろへの反転を lerp すると原点を通って潰れ、後退時に足が
逆位相にならないため。

多脚は「前後のストライド」「振り出し時の持ち上げ」「膝の畳み」「外向きの開き」を別チャンネルで
駆動している。関節をどの軸で回すかは **バインド時にボディ座標から解いている**：

> ボーンを軸 A で回すと先端は `A × S`（S はシャフト方向）に動く。
> だから前へ踏み出したいなら `A = Z × S`、持ち上げたいなら `A = Y × S`。
> 真下に伸びた脚は `Y × S` が退化する ＝ 股関節では足を持ち上げられないので、
> その場合は持ち上げを膝に全部任せる。

これのおかげで、真下向きの脚でも横向きの脚でも、同じ「前へ踏み出す」が正しく出る。

### プリセット

**プリセットは 4 機とも「そのまま出撃できる状態」で組んである。**
ブーストは装備プレートがなければ使えないので、装備の無い機体を初期状態に置くのは
「動かない機体」を配ることになる。武装も同じ。

| プリセット | 歩容 | 武装 | その他 | 見どころ |
|---|---|---|---|---|
| **2脚 STRIDER** | walk | ビーム（右手）／ガトリング（左手）／ミサイル（胸） | ブースト×3 | **肩・肘・腰・膝**の作例。標準機 |
| **1脚 POGO** | hop | ショット（頭）／ブレード×2（腕）／ビーム×2（ビット） | ブースト×3 | 効き 1.2〜1.3 の大振り。接近戦 |
| **4脚 CRAWLER** | multileg | ガトリング（頭）／ミサイル×2（アウトリガー）／ビーム（尾） | **グラビティ**／ブースト | 重量機。飛べない代わりに耐久 +45% |
| **浮遊ビット FUNNEL** | hop | ビーム（前）／ショット×3（ビット）／ミサイル（脚） | **ローリング**×3／ブースト | 浮遊ビットが回り続ける |

**4機とも20種の形で組み直してある。** 手足はカプセル、関節は球、足先は円錐台や斜面。
箱を積んだだけの機体は、置ける形が20種あることを何も教えてくれない。

組み直しで直した3つ:

| | |
|---|---|
| **腕が腰を貫いていた** | 肩を胴より外に出し、腕は骨盤の手前で終わるようにした。テストで機械的に検査している（下記） |
| **コアが腹から見えていた** | どのプリセットもコアを完全に覆う殻を持つ。**先細りの形は思ったより覆えない** — 八面体は自分より小さい立方体の角を8箇所とも通してしまう |
| **走っても形が固まっていた** | 肘が伸びきったまま、胴も起きたままだった。→「走り方」の節 |

**武器の並び順＝パーツ木の順**なので、出撃した瞬間に選ばれている武器が
「撃てない武器」にならないよう、近接武器は腕より上流に置かないようにしてある。

グラビティは 1 枚制限なので、積んでいるのは CRAWLER だけ。

- 右パネルの「スペック」に歩容バッジが出る。ただし**脚が0本のときは出さない**。
  「ホバー」は歩き方ではなく歩き方が無いことなので、出すと在りもしない歩行の
  調整を誘ってしまう。テスト中の右下の読み出しからも同じ理由で GAIT 行が消える

### 空中戦と地上戦の両立

仕様書は無重力前提だが、地上戦も気持ちよくする必要があるので次のように橋渡ししている。

- 重力は常にかかっているが、**上昇入力を握っている間だけ `gravityScale` が 0.14 まで落ちる**。
  「飛ぶと決めた瞬間に重さを買い戻す」ことで、空中では ZMF そのままの無重力挙動になり、
  離した瞬間から 0.3 秒で重さが戻ってくる。
- 接地中は推力が水平面に射影され、**脚の本数がそのままトラクション**になる（`grip`）。
- ζ（抗力）は接地中に少し増える。これが「地面に足が付いている感触」。
- カメラのブームはピッチに **42% しか追従せず、さらに水平から 20° 相当で頭打ち**にしてある。
  急降下時に真上からの視点になるのを防ぐため。

#### 接地中はロックオンしても浮き上がらない

真上の敵をロックオンすると機首が上を向く。これをそのまま素直に扱うと、機体は
**4つの経路で勝手に離陸してしまう**。接地中はそのすべてを水平面に閉じ込めてある。

1. **推力** … スプールを機体姿勢そのままで回すと、上を向いた機首が推力を揚力に変える。
   接地中は **ヨーだけの座標系** で推力を組み立て、垂直成分は上昇入力チャンネルだけに任せる。
2. **アシスト** … Pro-Nav の加速度指令は上空の敵を指すので、接地中は Y 成分を落とす。
3. **向心力アシスト** … 運動量を機首方向へ回すと、走る速度が上昇速度に化ける。
   接地中は水平成分だけを回し、垂直成分には触れない。
4. **フレームロック（§5 相対空間）** … ロックした相手は参照フレームとして登録され、
   その速度の一部を機体が「一緒に運ばれる」形で受け取る。相手が跳ねる機体だと、
   **近づいた瞬間にその上昇速度をもらって浮いてしまう**。接地中は
   **垂直成分だけを接地度に応じて落とす**（水平成分はそのまま）。地面に立っている間、
   乗っているのは地面であって相手ではない。

この 4 番目は「敵に近づいたときだけ浮く」という形で出るので厄介だった。フレームロックは
**距離で効き始める**（相手の半径の約 5.7 倍以内）ので、遠距離では何も起きない。

離陸したとたん 4 つとも解除されるので、空中では今までどおり機首方向に飛べるし、
大きな相手に持ち上げられる §5 本来の挙動も戻る。

#### そもそも接地中は機体が傾かない

上の 4 つは「浮かない」ようにする話で、**見た目**は別問題だった。真上の敵をロックすると
機体はのけぞったまま歩く。物理的には浮いていなくても、**浮きそうに見える**。

そこで接地中は、**コアブロックを常に地面と平行に保つ**ようにした。狙うのは
「傾く」のではなく「**向き直る**」ことでやる。

- 接地度に比例して、姿勢の目標ベクトルから**ピッチ成分だけを抜く**。ヨーはそのまま効くので、
  真上の敵でも機体はちゃんとそちらを向く
- **狙いは落とさない。** 抜く前のベクトルを `aimForward` として別に持っていて、
  フェイスボーン（頭）はそちらを向くし、武器もそちらへ撃つ。頭だけ見上げて胴は水平、になる
- ロックしていないときも同じ。マウスで上を向いてから離陸すると、**足が離れた瞬間に
  機首がそこへ向く**（`freeForward` にピッチが残っているため、スナップしない）
- 接地度でクロスフェードするので、ジャンプでも段差でも切り替わりが見えない
あわせて、接地中は注視点の上振れも抑えてあり、真上の敵をロックしても自機は画面内に残る。

### ロックオン中のカメラは、追跡カメラをやめる

追跡カメラは**運転のためのカメラ**だ。尻尾に付いて、機首の行き先を見て、機体を画面の
真ん中に置く。銃撃戦ではその3つが全部まずい。

尻尾から見ると、**狙っている相手はちょうど自分の機体の真後ろ**に来る。機体が的を隠し、
的へ渡っていく弾も隠す。「どこへ飛んでいるのか見えない」の正体はこれで、
実際に撮ってみると **26m 先の敵が自分の頭の陰に完全に隠れていた**。

そこでロックオン中は、ブームを**射線の側へ**組み替える（`CameraDynamics.config.combat`）。

- **射線の後ろに回る。** ブームの向きを、機首ではなく**自機→相手の方向**へ寄せる（0.85）。
  地上では機体が相手を向くので大差ないが、**横に流している間**と**上下に離れている相手**では
  機首と射線が割れる。見たいのは射線のほう
- **射線から一歩どく。** ブーム長の 34% だけ横へずらす。真後ろに居るかぎり自機と相手は
  画面上で重なる（奥行きで離れているだけだから）。横にどけば**2機が画面上で分かれ**、
  その間の空間＝弾の通り道が見えるようになる
- **持ち上げる。** ブーム高を 60% 増し。地面すれすれを飛ぶ弾を真横から見ると読めない
- **間合いを見る。** 注視点は自機でも相手でもなく、**その間の 40% の点**。
  自機は手前側に、相手は奥側に収まる
- **距離で開く。** 45m でブームが 1.5 倍まで伸びる。遠い試合でも2機が同時に入る
- **前方リードは引っ込む。** 「機首の行き先を見る」は運転の都合なので、戦闘中は 15% まで下げる

切り替えは**ロックの有無**で駆動する。エイムアシストの強さで駆動してはいけない —
アシストは手動で視線を振った瞬間に降りるので、**手で見回すたびにカメラが組み替わる**ことになる。

---

### 追跡カメラを自分で回す

ブームは基本的に機体の後ろに付いてくるが、**右ドラッグ（または `Alt`+マウス）で
機体のまわりを自由に回せる**。ホイールでブームの長さも変えられる。

- 回している間、**マウスは機体ではなくカメラを動かす**。機首は動かない
- しかも**照準の振れとしてカウントしない**ので、カメラを回してもロックオンは外れない
  （ロックのソフト解除はエイム入力の大きさで判定しているため、ここが分かれていないと
  「見回したらロックが切れた」になる）
- ピクセル→角度の直接対応。エイムのようなレート＋エキスポ curve は通していない。
  カメラは手に 1:1 で付いてこないと壊れて感じる
- **止まっている間は回した位置を保つ。走り出すと後ろへ戻ってくる**
  （戻る速さは実速度に比例。横を向いたままの追跡カメラでは運転できないので）
- 真上・真下は少し手前で止まる（`lookAt` が破綻するため）
- 大きく回すと注視点が機体そのものへ寄る。前方リード点のままだと、正面から見たときに
  機体が画面外へ出るため
- ズーム倍率は **0.42〜2.8 倍**。リスポーンで角度は戻るが、**ズームは好みなので残る**

### 重さ・軽さの調整点

`computeStats()`（`src/core/Assembly.js`）が唯一の真実。ここから下流は全部これを読む。

| 出力 | 由来 | 効く先 |
|---|---|---|
| `mass` | 実ボクセル体積 + ボーン長×太さ² | 加速度、ABC の効き |
| `thrust` | ブロック体積^(2/3) の総和 + 脚の本数 | 最大加速度 |
| `weightClass` | 質量 0〜1 正規化 | ζ の粘性、旋回権限、マウス感度 |
| `agility` | 推力重量比 | スプール、最高速、FOV |
| `extent` | リグの外接半径 | 間合い・爆風・接触、カメラブーム長 |
| `solidVolume` | 実ボクセル体積 | **弾の当たり判定（立った円柱の太さ）** |
| `gait` | 脚の本数 | 歩容 |

## 動かし方の設計

### 試合は固定ステップで進む

**画面が何fpsでも、試合は 1/60 秒の固定ステップで進む。** 余った時間は次のフレームへ
繰り越し、1フレームで進めるのは最大4ステップまで。

以前は実フレーム時間をそのまま物理に流し込んでいた。これには3つ問題があった。

- **同じ操作が同じ結果にならない。** 走らせるマシンの速さで試合が変わるので、
  再現もリプレイもできない
- **重いフレームが1回入ると、その1回が巨大な1ステップとして積分される。**
  機体が壁を抜ける典型的な原因
- **遅れを取り戻そうとすると、さらに遅くなる。** 上限を切らない追いつき処理は、
  重いフレームがもっと重いフレームを呼ぶ悪循環になる

上限に当たったぶんは**捨てる**。時間の進みが遅くなって見えるが、これは回復できる。
追いつこうとして雪だるま式に崩れるほうは回復できない。

### 「試合を決めるもの」と「見え方を決めるもの」を分ける

`update()` は試合だけを進め、`present()` はカメラ・画面効果・読み出しだけを扱う。
**`present()` は試合を読むが、変えない。**

この線引きがあるから、

- 読み出し（HUD）は **30Hz に落とせる**。2Dキャンバスの全面再描画で、
  144Hz で毎フレーム描き直す価値がない
- カメラをどう振っても、bloom を切っても、**試合の結果は1ビットも変わらない**
- 重いときに削るなら `present()` 側から削れる、と場所が決まっている

### 乱数は種から再生できる

`Math.random()` を使っていた箇所（弾のばらつき、AIの回避、敵の湧き位置、命中判定）は
**種を持つ生成器**に置き換えた。試合は「どの種で、どのステップに何を押したか」だけで
完全に決まる。

**ストリームは2本に分けてある。**

| ストリーム | 決めるもの |
|---|---|
| 試合用 | 弾のばらつき、回避の向き、湧き位置、命中判定 |
| 演出用 | 破片、火花、画面の揺れ |

分けてあるので、**破片を多く出しても弾の飛ぶ先は動かない**。同じ生成器を共有していると
「演出が増えた回だけ弾がズレる」という、原因の分からないバグになる。

### 重い処理を、試合の事実で割り振る

遠くの機体は**姿勢の更新回数を落とす**（26m まで毎ステップ、55m まで2ステップに1回、
それ以遠は3ステップに1回）。飛ばしたぶんの時間は次の姿勢計算に渡すので、
歩調の速さは変わらない。

**割り振りの根拠は「機体間の距離」＝試合の事実であって、フレーム時間やカメラの向きではない。**
これは重要で、姿勢は銃口の位置を決める＝試合に影響するため、
画面都合で決めると同じ操作が同じ結果にならなくなる。

（視錐台カリングのような**描画だけ**の間引きは逆に、実時間やカメラで決めてよい。
同じ「間引き」でも、試合を変えるものと変えないものは別物として扱う。）

### 計算を1回に

| 直したもの | 何が起きていたか |
|---|---|
| ワールド行列の更新 | 機体を組み終えたあと**1回だけ**更新する。以前は武器側が毎フレーム再度全走査しており、約200オブジェクト×機体数ぶん、同じ行列を2度計算していた |
| 弾の向き付け | 定数ベクトルを**毎フレーム・毎弾**確保していた |
| 回転パーツの更新 | 2つの配列を毎回結合していた（多くの機体では空の配列を作るためだけに） |
| AIの進行方向 | ベクトルを毎ステップ複製していた |
| 読み出しの座標計算 | 毎描画でベクトルを2本確保していた |

**実測（機体4体、同一条件）**

| | 変更前 | 現在 |
|---|---|---|
| 1ステップの試合処理 | 1.55 ms | **0.42 ms** |
| 1フレームの表示処理 | （試合処理に同居） | 0.16 ms |
| 読み出しの再描画 | 毎フレーム | 30Hz |

## 絵づくり

見た目は「暗い場所で、光るものが光って見えること」に賭けている。この game は
ほぼ真っ暗な中で、**意味のあるものがだいたい光源**（ビーム、曳光弾、スラスター、
ブレード、爆発、装備プレートの発光）だから、そこを描けるかどうかで全部決まる。

### 1枚のポストチェーン

シーンは **HDR ターゲットに1回描いて、画面に1回解決する**。その間に明るい部分を
抜き出してぼかす。全部で小さなパス5枚、`src/game/PostFX.js` に閉じてある。

```
scene → [HDR target, MSAA×4]
          ├→ bright pass (1/2)  → blur H,V (1/4) → blur H,V (1/8)
          └→ 最終合成（bloom + 色収差 + スピードライン + 粒子 + ビネット + トーンマップ）
```

- **明度抽出は 1/2、ぼかしは 1/4 と 1/8。** いきなり 1/4 に落とすとテクセルを
  飛ばすので、ビームや曳光弾のような**細い明るいものがチラつく**。1回きれいに
  半分にしてから落とすのがそれを止める
- **2スケール合成。** 光源のすぐ周りの締まったグローと、遠くまで広がるハローは
  1つのぼかし半径では両立しない。光は両方やる
- **ソフトニー付きのしきい値**。硬く切ると、明るさがしきい値を跨ぐたびに
  bloom が点いたり消えたりしてチラつきに見える
- **ブルームのコストは、ポスト有効時のフレームの約19%**（実測、ソフトウェア
  ラスタライザ上での比率）。`setBloom(0)` でチェーンごと丸ごと飛ぶ

### アンチエイリアス

**シーンをターゲットに描いた時点で、キャンバスの `antialias: true` は何もしない。**
ずっとギザギザだったのはこれが理由で、いまはオフスクリーンターゲット自体に
**MSAA×4** を要求している。

### 空と、金属が映すもの

`src/game/Sky.js` が**手続き的な空**を1枚作る。64×256 のキャンバスに縦方向の
グラデーションを描き、PMREM に通してラフネス別のミップにしたもの。

- **見える背景であり、同時に `scene.environment`。** 映り込みと目に見える空が
  食い違いようがない
- ボーンやプレートは metalness の高い金属で、**映すものが無い金属はただの黒い染み**。
  ライトを何本足しても解決しないのはこれ
- 環境光が入ったぶん、**半球ライトは 1.45 → 0.62 に落とした**。両方全開だと
  二重に照らして立体感が消える
- アリーナと編集画面で色味だけ変えた同じ仕組みを使う

### アリーナ

| | 変更 |
|---|---|
| 床 | 反射を少し拾う暗い金属寄りに。外周に**光るリング**（ここが終わりだと遠くからも分かる） |
| 柱のキャップ | 発光を 1.4 → 2.1 に。**bloom が拾うのはここ** |
| 地平線 | 外周に**遠景のビル群**を加算で並べた。フォグで消えるだけの縁ではなく「遠く」になる |
| フォグ | 空の地平線バンドと同じ色に。距離が空に溶ける |
| リムライト | 冷たいのと暖かいのの2本。1本では、動き続けるカメラのある角度でしか効かない |

### 機体

- ボーンの `envMapIntensity` を上げた。**空を映してはじめて機械加工の金属に見える**
- プレートの発光を 0.85 → 1.9 に。**1を超えないと bright pass が拾わない**＝
  光らないランプになる
- ブースターの炎の芯は逆に**落とした**（0.8 → 0.55）。bloom が自前で光を撒くので、
  そのままだと中心が白飛びする

### 手応えのエフェクト（[Effects.js](src/game/Effects.js)）

撃った・当たった・降りた・走っている、が**画面から分かる**ようにするための層。
全部プールで、起動時に1回だけ作る（初弾で確保が走ると、その武器を初めて撃った瞬間だけ
カクつく）。**乱数は演出用のストリームから引く**ので、火花を増やしても弾は1mmも動かない。

| | 何が出るか |
|---|---|
| **発射** | 銃口に短い炎（円錐）＋芯（球）。**弾の色**で光る |
| **被弾** | 着弾点に閃光＋火花。**弾が飛んできた向きの逆**へ散る |
| **接地移動** | 足元から土埃。**1.6m 走るごとに1個**（秒あたりではなく距離あたり） |
| **着地** | 床を走る輪＋足元から外へ散る土埃 |
| **影** | 機体の真下の薄い影。高さで**広がって薄くなる** |

**火花は「入ってきた向きの逆」へ散る。** そのまま突き抜ける散り方は、当たった絵ではなく
**外れた絵**になる。当たったことを言うのが仕事なので、向きは反転させている。

**銃口の炎は円錐と球の2つ。** 円錐だけだと、**真後ろから見たときにほぼ消える** —
そしてプレイヤーが見ているのはまさにその角度。

**土埃は距離あたりで出す。** 秒あたりにすると、速い機体も遅い機体も同じ数の埃を撒くので、
速い機体が**滑っているように見える**。

**1つの被弾＝1つのマテリアル。** 閃光も火花も同じマテリアルを共有しているので、
「弾の色で染める」「まとめて薄くなる」が火花1個ごとのマテリアルを持たずに済む。
逆に**土埃は1個ずつ自前のマテリアル**を持つ。共有すると軌跡全体が同時に消えて、
土埃が沈むのではなく**照明が消えた**ように見える。

### 名前を変えても、保存したものは失わせない

`BroStom` → **`BLOSTOM`**。表示名はすべて置き換えたが、**データは片方向にしか変えていない**。

| | 新 | 旧 |
|---|---|---|
| 保存形式のタグ | `blostom.assembly` | `brostom.assembly` も**読める** |
| 共有コードの接頭辞 | `BLO1:` / `BLO0:` | `BRO1:` / `BRO0:` も**読める** |
| ブラウザ保存キー | `blostom.*` | 新しい方が無ければ `brostom.*` を**読む** |
| 書き出すファイル名 | `〜.blostom.json` | — |

**古い名前は読むだけで、二度と書かない。** 名前を変えたことは、先週保存した機体が開かなく
なっていい理由にはならない。共有コードは既に誰かの手元にある（印刷された、メッセージに
貼られた、QRとして保存された）ので、なおさら。接頭辞の**後ろの中身は何も変わっていない**ので、
4文字を読み替えるだけで済む。

環境変数（`BLOSTOM_SMOKE` / `BLOSTOM_STEAM_APP_ID` / `BLOSTOM_DEV_SERVER`）と
Electron の `appId` は開発者側のものなので、そのまま改名した。

### 当たった手応え

弾が当たっても、**どこかのバーの数字が動くだけ**だった。当てたのか外したのかが
分からないので、撃ち合いが作業になる。要るのは2つ — **自分の弾が当たったこと**と、
**自分に当たった弾がどこから来たか**。

**① 被弾した機体が光る**（`Rig.setHitFlash`）。ブロックは1つのマテリアルを共有していて、
ボーンも種類ごとに1つなので、**機体まるごとの発光がプロパティ2〜3回の書き込み**で済む。
消えているときのコストはゼロ。

- 明るさは**その機体の耐久に対するダメージの割合**。ガトリングはチラつき、
  マグナムは白く飛ぶ手前まで光る
- **上限は画面で測った**。トーンマッピングは1のずっと手前で飽和するので、
  上限を超えると**機体の形が消えて白い塊**になる。0.45 ならシルエットもパネルの線も
  プレートも残ったまま、「とても強く殴られた」だけが伝わる
- 色は**自機が赤、相手が白熱色**。今起きたのがどちらなのかは、画面上で一番役に立つ1ビット
- **点灯はダメージ処理のその場で**。ダメージが解決されるのは全機のポーズが済んだ後なので、
  減衰パスに任せると**弾より1フレーム遅れて光る** — その1フレームが全部だった

**② 当てたら相手の位置にマーク、当たったらレティクルの周りに弧**（`Hud`）。
どちらも**ワールド座標から毎フレーム投影**しているので、
相手が画面外でも背後でも機能する — そしてそれこそ、教えてほしい場面だ。

- マークは**×**（＋はレティクルに見えるので）。撃破した相手には輪が付く
- 弧は**同じ方角のものをまとめる**。散弾9発が9本重なると白い染みで、警告ではない
- 背後から撃たれると投影が反転するので、**方角を裏返して**から描く

### 影は2種類ある

**① 本物の影**（キーライトのシャドウマップ）。ただし**シャドウカメラが原点に固定**で、
箱は 46m 四方しかなかった。アリーナは半径 120m あるので、
**中央から離れた機体には影が無かった**。箱をプレイヤーに追従させ、ついでに 30m まで
絞った（同じ 2048px がずっと狭い床を覆うので、影は前より**くっきりする**）。
光源の**向き**は変えない — 歩くたびに向きが変わると、アリーナごと回って見える。

**② 真下の影**（[Effects.track](src/game/Effects.js)）。本物の影は 30m 横に落ちるので、
飛んでいる機体の「**今どれくらい浮いているか**」には答えられない。真下の薄い影は
高さに応じて**広がって薄くなる**ので、影だけ見て高度が読める。柱の上に降りるには
これが要る。

ブロックのジオメトリは **単位立方体空間** で作られ VoxelBlock 側にキャッシュされる。

v1（gauge 名でボーン太さを持っていた頃）と v2（ソケット＝面／スロット指定）は、読み込み時に
自由な position + rotation へ変換される。ソケットで表現できたことは自由変換の特殊ケースなので、
情報は失われない。

#### 20分（ときに数時間）から2分になった経緯

**① 誰も見ないピクセルを7,600回描いていた。** スイートは `app.frame()` を
約7,600回呼びますが、**ピクセルを見るテストは419件中9件だけ**。
描画ありの1フレームは、可視ウインドウで約5ms、**バックグラウンドのタブでは93〜260ms**。
`app.frame({ paint: false })` を足して、描画だけを飛ばせるようにしました
（シーングラフの行列更新は残すので、「どこに着いたか」を見るテストの答えは変わりません）。

**② 5件のテストが全体の79%を食っていた。** 固定ステップの再現性を見る
`the fight runs on its own clock` の5件が、1,142秒中の**897秒**。
どれも同じ試合を2回流して結果を比べるもので、**比べているのは数値であってピクセルではない**のに、
唯一 `paint: false` に変えそこねたヘルパーでした。1件190秒 → **1秒**。

**③ 保存するたびに1件目からやり直していた。** `test:browser` は
**開発サーバー**を開いていたので、テストページが読むファイルを保存すると

編集しながら回すと**永遠に終わりません**。いまはビルド済みのページを
`vite preview` で配ります。

**④ 乱数の流れが419件で共有されていて、一度も巻き戻らなかった。**
敵の湧く位置はフィールド自身の乱数から引かれるので、

**脚が無いときの歩容表示**（バッジもHUDの行も出ないこと）、
**フロートとサークル**（浮くこと・グラビティとの排他の理由表示・半径スライダで線が動き乗り手が入れ替わること・

結果はページ上と `window.__TEST_RESULTS` に出る。

> テスト間の yield は `setTimeout(0)` ではなく `MessageChannel` を使っている。
> バックグラウンドのタブではタイマーが「1分に1回」まで絞られるので、
> setTimeout だとスイートが遅くなるのではなく **止まる**。
>
> ブラウザスイートはアプリと同じオリジンで動くので、起動時に localStorage の
> `blostom.assembly.v1` と `blostom.parts.v1` を消して白紙から始める。
> **残しておきたい機体・パーツがあるなら、走らせる前に `書出` で JSON に出しておくこと。**

### テストで見つけて直したもの

書きながら実際に潰れたバグ（どれも手触りに直接効く場所だった）:

- `slew()` がスティックを離した瞬間（目標 0）を「符号反転」と誤判定し、常に上昇レートを使っていた。
  仕様の非対称スプール（後退の制動 Jerk を高くする）が効いていなかった。
- `smoothstep()` が逆順の境界（減少ランプ）を扱えず 0 を返していた。
  §8.1 の「エネルギー限界付近のジッター振動」が一度も発火していなかった。
- `KineticFeedback` が範囲外の衝撃値をそのままシェーダ uniform に流していた。
- カメラのブームがピッチ追従を減衰させるだけでは足りず、急降下で真上に回り込んでいた。
- 多脚のボディバウンドが、脚数ぶんの周波数で振動して平滑化に吸われ、見えなくなっていた。
- 空のタンクでもブーストの燃料を請求し続けていた。
- 複数パーツを同時にドラッグすると、共有していた一時行列が上書きされ、2個目以降に
  壊れた変換が適用されていた。
- 親と子を同時に選択して動かすと、子に変換が二重に適用されていた。
- 進行方向ベクトルを lerp していたため、真後ろへ歩いても足が反転しなかった。
- 選択の重心を溜めていた一時ベクトルを、連結線の描画が上書きしてギズモの位置がずれていた。
  （共有一時変数の使い回しで踏んだ 3 件目。数値は必ずテストで押さえている。）
- 彫刻のアンドゥ 1 手ぶんを積む処理がポインタハンドラの中に直書きされていて、
  ストロークを API から始めると履歴に残らなかった。`beginStroke()` として切り出した。
- ローリングの回転数が壊れたセーブから `NaN` になり得た。`clamp(NaN)` は `NaN` のままなので、
  ブロックのクォータニオンごと汚染して機体が消える。数値でない値は既定へ落とすようにした。
- ポーズメニューのテストがボタンを**添字**で押していた。ボタンを1つ増やしたら
  「リスポーン」ではなく「キー設定」を押すようになり、**フィールドがポーズしたまま**
  後続のテストに渡って、無関係な移動テストがまとめて落ちた。ラベルで探すよう直した。
  （以前 1 度だけ観測した field mode の同時失敗も、おそらく同じ形の状態漏れだった。）
- 「弾が飛んでいること」を、あるフレームの生存数だけで見ていた。近距離では撃った弾が
  数フレームで消えるので、たまたま 0 になって落ちる。バースト全体の最大値で見るよう直した。
- 弾の当たり判定がフレーム端点のサンプルだけだった。ガトリングは 1 フレームで約 3m 進むので、
  それより細い相手を**すり抜けていた**。線分と球の最近接距離で掃引するように直した。
- 武器の照準を機体のエイムアシストに任せていたら、25m の相手に 62 発撃って命中 0 だった。
  アシストのリードは「機体を向ける」ためのもので、弾速ごとの会合点ではない。
  武器ごとに偏差を解くようにして 22/62 命中（残りは相手の回避）。
- **人型の腕が腰を貫いていた。** 見れば一目で分かるのに、テストは1つも落ちていなかった。
  「交差していないこと」を測っていなかったから。腕の下のブロックと胴のブロックの
  AABB 交差を検査するテストを足した。**目で見て分かる欠陥ほど、測っていないと素通りする。**
- **プリセットのコアが腹から見えていた。** 覆ったつもりの殻が覆えていなかった。
  八面体は、自分より小さい立方体の角を8箇所とも通してしまう（内接半径は
  半径の 1/√3 しかない）。コア表面の26点が他のブロックの**実際の形マスク**の
  内側にあるかを調べるテストを書いたら、20/26 が外に出ていた。
- **20種の形を使ったら QR に入らなくなった。** 形で埋めたボクセルは、
  誰も彫っていなくても RLE で数千ラン。JSON が 152,174 文字になり、
  共有コードは QR の上限の3倍を超えた。彫っていないブロックを「形＋色」で
  保存するようにして 8,272 文字（1/18）へ。
- **タイトルメニューがマウスに反応しなかった。** ホバーでハイライトを動かすのに
  メニュー全体を作り直していたため、**カーソルの下のボタンそのものが差し替わっていた**。
  クリックは「同じ要素での押下と解放」で成立するので、間で要素が入れ替わると
  ブラウザは click を1回も発火しない。ホバーで光りはするので、**見た目は生きていて
  完全に死んでいる**という出方をした。
  テストが全部素通りしたのは、`.click()` も `choose()` もヒットテストと押下／解放の対を
  通らないから。直したうえで、(1) ホバー後も同じノードが残っていること、
  (2) デスクトップ版のスモークテストが**実際のマウス入力**でタイトルを1つ押すこと、
  の2つで押さえた。
- **吹き飛ばしが半分溶けてから飛んでいた。** 「着地したら立ち直る」を接地の平滑値で
  見ていたので、撃たれた直後の数フレーム — まだ足が床にある扱いの間 — に `downed` が
  半分消えていた。上下方向の速度も落ちていることを条件に足した。
- **吹き飛ばしの通知が、渡す相手に届く前に消えていた。** 1フレームだけ立つイベントを
  `body.update()` の先頭で消していたので、ステップ後半で解決したダメージによる吹き飛ばしが
  **次のステップの update に踏み潰されて**いた。被弾ログと同じく、
  **受け取った側が消すラッチ**に変えた。
- **被弾の発光が弾より1フレーム遅れていた。** ダメージが解決されるのは全機のポーズが
  済んだ後なので、減衰パスに任せると点灯が次のフレームになる。手応えは
  **その1フレームが全部**だったので、ダメージ処理のその場で点けるようにした。
- **横に流れている機体が時速100kmでムーンウォークしていた。** 脚が届く以上に遠くを、
  動ける以上に速く振る歩容を、速度だけ見て回し続けていた。
  自分の `groundSpeedCap` を超えたら歩容をブレンドアウトして、両脚を寝かせるようにした。
- **ドラッグ配置が、列ではなく鎖を作っていた。** 甲板を1回横切ると29個置かれ、
  甲板に乗ったのは**1個**、残り28個が数珠つなぎ。1個置くたびに選択が移り、
  次のホバーが「いま置いたブロック」に当たっていた。フィールドでは28個が
  最初の1個に乗るので、**土台を消すと全部消える**。単発クリックは正しかった。
- **HUDの読み出しのために `offsetHeight` を毎フレーム読んでいた。** レイアウトの
  再計算が毎フレーム走り、**アプリ全体の実行時間が倍**になっていた（テストスイートで
  247秒→199秒）。値が変わるのは表示・折り畳み・リサイズのときだけなので、そこで測る。
- **ソロプレイの読み出しが、操作説明バーの下に完全に隠れていた。** バーは画面幅の98%を
  占め、ウェーブ・のこり・スコア・**残機**はすべてその矩形の中に描かれていた。
  走りの状態が、走っている間ずっと見えなかった。**どのウィンドウサイズでも**。
- **運動モデルの調律用の数値（ZETA / JERK / ASSIST / FRAME）が、プレイヤーの画面に出ていた。**
- **HPを賭けた選択なのに、HPが数字でどこにも無かった。** 画面の縁は60%を切るまで何も言わない。
- **下部ヒントバーがウィンドウ幅と無関係に1198px固定で、900pxでは左右が画面外だった。**
- **編集パネルが900pxのウィンドウで画面の48%を占めていた。** 組んでいる対象より、
  それを操作するUIのほうが広かった。
- **ガトリングが全武器中ワーストだった。** 持続DPS 14.1（最高は56.3）。
  「押しっぱなしの主力」という顔の銃が一番弱く、しかも「握ると散る」を入れた直後で、
  **握る前提の銃を握ったことで罰していた**。
- **ショットがスプレッドの下位互換だった。** 散布は狭いが throughput が1/3。
  狭さで埋まる差ではなかった。
- **スナイパーの射程576mは、半径120mのアリーナで意味を持たなかった。**
  ビームが射程以外の全項目で上回っていたので、スナイパーの取り柄はスコープだけだった。
- **武器の搭載枚数に上限が無かった。** プレート1枚は機体質量の1割未満なので、
  **10種類ぜんぶ積んで巡回するのが最適解**。きれいに分かれた10通りのコスト構造は、
  誰も答えなくていい問いだった。
- **コアのスライダー1本が、他の全要素より強かった。** 耐久がコア辺長の**二乗**で、
  スライダー1本で耐久8倍。代償は機動性だけで、敵のDPSが15前後では
  「90秒立っていられる」ほうが勝つ。
- **速攻ボーナスが45秒固定で、ウェーブ7以降は取れなかった。** 取れないボーナスが
  画面に居続けるのは、無いより悪い。
- **腕前ボーナスがウェーブ1では意味を持ち、ウェーブ20では10%だった。**
  固定値だったので、腕が効くべき場面で腕が点にならなかった。
- **ブラウザスイートが、誰も見ないピクセルを7,600回描いていた。** ピクセルを見るテストは
  419件中9件。バックグラウンドのタブでは1フレーム93〜260msかかるので、
  それだけで20分から数時間だった。
- **そのうち5件が全体の79%を食っていた。** 固定ステップの再現性テストが1件190秒。
  比べているのは数値なのに、描画を飛ばすヘルパーに変え忘れていた1か所だった。
- **`npm run test:browser` が開発サーバーを開いていた。** ソースを保存するたびに
  HMRがページをリロードし、走っていたスイートは1件目からやり直していた。
  **編集しながら回すと永遠に終わらない。**
- **乱数の流れが419件で共有され、一度も巻き戻らなかった。** 前のテストが何個
  乱数を消費したかが、後のテストの敵の湧く位置を決めていた。遮蔽とロック取得時間が
  入った瞬間、**実行のたびに違うテストが落ちる**という形で表に出た。
- **ブルームのテストが、シェーダではなくコンポジタに質問していた。** 合成済みの
  キャンバスの中身は未定義で、誰も見ていないウインドウでは描かれないこともある。
- **弾が柱をすり抜けていた。** アリーナは最初から柱だらけで、その仕事は
  「ロックを切る」の1つだけ。当たり判定は地面とアリーナの壁にしか無かったので、
  **柱の後ろに立っても撃たれた**。効きそうに見えて効かない遮蔽は、遮蔽が無いより悪い。
- **HPが低いときは、死んだほうが得だった。** 撃破されると残機を1つ払う代わりに
  **HP全快**で戻り、ウェーブクリアの回復は35%だった。残機というコストが、
  回復というご褒美に負けていた。
- **5ウェーブごとのエースは、硬いだけの同じ敵だった。** `toughness × 2.4` 以外に
  違いが無く、戦い方は完全に同じ。**硬さは同じ戦闘を長くするだけで、難しくはしない。**
- **4体の敵は「距離の違う同じ相手」だった。** 射撃ロジック・バースト・後退条件を
  全部共有していて、違うのは好みの距離と移動の癖1行。個別に覚えることが無かった。
- **プレイヤーだけがバースト規律を持っていなかった。** 敵には「隙間こそがゲーム」
  と言って撃ち方を作ったのに、こちらは引き金を握りっぱなしが最適のままだった。
- **スコアが「どれだけ長く座っていたか」の記録だった。** 命中率も無被弾も速さも
  1点にならなかった。
- **機体を見回すたびに、ブロックが1個落ちていた。** 配置ツール中の左ボタンは
  カメラ回転と配置の**両方**に割り当てられていて、しかも配置は**押した瞬間**に走った。
  彫刻ツールは同じ理由でとっくに左ボタンを専有していたのに、配置だけが取り残されていた。
- **面のどこを押しても、ブロックは面の中央に着いた。** `faceAnchor` が法線方向にしか
  ずらしていなかったので、カーソルとゴーストが**常にずれている**のが既定の状態だった。
  横に並べるには毎回ギズモで動かすしかなく、「面をなぞって並べる」が成立しなかった。
- **「左右対称」が、体ではなく親の中心線で折り返していた。** 左肩に飾りを付けると、
  右肩ではなく同じ左肩の反対側に双子が出た。それが体の中心線になるのは
  親が中心にあるときだけで、UIのラベルは違うことを約束していた。
- **21形のうち14形が、実質使えていなかった。** ドーム・円錐・斜面・階段…はどれも
  向きを持つのに、**配置時の回転がどこにも無かった**。置いてからインスペクタに
  90 と打つか、ギズモを15°刻みでドラッグするしかなかった。
- **面付けしたブロックは、寸法を変えると親に沈んだ。** mount は配置時の寸法で
  焼き付けられ、リサイズはそれを触らなかった。ブロックは自分の中心を軸に育つので、
  追加した寸法の半分が親の中へ消えた —— 内側なので、見た目でも気づけない。
- **スタンプのゴーストは、置き場所について二重に嘘をついた。** 外接箱で測って
  外接箱ぶん押し出すのに、実際に置かれるのは部品の**ルート**だった。
  ルートが箱の中心にある部品はまず無い。
- **同じブラシスライダが、4mのブロックでは1mのブロックの4倍の穴を開けていた。**
  ボクセルの格子は常にブロックいっぱいに張られるので、「格子の何%」は
  世界の中では固定サイズではない。
- **敵が一度も撃っていなかった。** 武器プレートを積み、AIが間合いを取り、
  弾倉もリロードも実装されているのに、**敵の武器システムを駆動するコードが
  どこにも無かった**。プレイヤー専用の `_fire()` しか無く、しかも弾の判定対象は
  `enemies` だけだったので、仮に撃っていても当たらなかった。
  ソロプレイの残機3が一度も減らないことに、誰も気づいていなかった。
- **中央から離れた機体には影が無かった。** シャドウカメラが原点固定で、箱は 46m 四方。
  アリーナは半径 120m あるので、**外周で戦うと誰も影を落としていなかった**。
  箱をプレイヤーに追従させ、ついでに 30m まで絞った（同じ 2048px で狭い床を覆うので、
  影は前よりくっきりする）。光源の向きは動かしていない — 歩くたびに向きが変わると
  アリーナごと回って見える。
- **着地が検出できなかった。** 「空中だった→接地した」を接地の平滑値で見ていたら、
  一度も発火しなかった。`grounded` は半減期 0.05 秒で上がるので、1ステップでは 0.21、
  0.6 を超えるのは3ステップ目 — その頃には「空中だった」がもう false になっている。
  しかも**どれくらいの速さで落ちてきたかは、跳ね返しで既に書き換わっている**。
  地面プローブが接触したそのサブステップでだけ落下速度を記録するようにした。
- **ロックオンすると全弾当たっていた。** 会合点を正しく解いて、そこへ撃っていたから。
  正しさが面白さを殺していた例で、テストは全部通っていた（「当たること」しか
  測っていなかった）。原因は3つ重なっていて、どれか1つを直しても足りなかった:
  弾が速すぎて**見えないうちに着弾していた**（ビームは25mを5フレームで渡る）、
  当たり判定が**外接球＝機体の高さと同じ幅**で3.5m横の弾も命中していた、
  そして狙いが**完璧**だった。速度を落とし、当たり判定を機体の体積から出した円柱にし、
  会合点の手前を撃つようにした。**避ける操作に意味が出た**ので、
  「横切る速さ別の命中表」をテストにしてある。
- **サークルに乗っているパーツを動かすと、動かした分より下がっていた。** 乗り手はリングの
  中に預けられているので、動かしたあとの位置を**リングの座標系から読んで**マウントに
  書き戻していた。マウントは本来の親から見た値なのだから、プレートの取り付け位置の分だけ
  毎回ずれる。矢印キー1回ごとに 0.25m 沈んでいたのに、**沈んでも同じ線の上に居続けた**ので
  誰も気づかなかった（「触れている」を半径だけで見ていた頃は、高さが変わっても判定が
  変わらない）。線から高さも見るようにした途端、テストが落ちて出てきた。
  マウントは**組んだときの座標系**で書き、乗り手の「元の場所」も一緒に更新する。
- **サークルが「線の上にあるのに回らない」を2回やった。** 1回目は隣のブロックに付いた
  パーツを見ていなかったから。2回目はそのうえで**関節をまたいだ相手を見ていなかった**から
  — 首の先の頭にプレートを貼り、胴に付けた球が線を貫いているのに、球は候補にすら
  入っていなかった。どちらも「同じ親か」「同じ剛体か」という**作った側の都合**で
  絞り込んでいたのが原因で、遊ぶ側に見えているのは線だけなのだから、
  絞り込みの根拠になり得ない。プレートの**親をたどる道すじ**を根まで下り、
  そこから枝分かれするものは全部候補にした（関節の**先**にぶら下がっているものだけは
  除く。そこは既にその関節のものだから）。
  ただし候補を機体全体に広げたぶん、「触れている」の判定が**半径だけ**では緩すぎた
  （高さを見ないので、頭に貼ったプレートが反対側の脚を掴む）。
  円線は面ではなく**線**なのだから、軸方向にも届いているかを測るようにした。
  ついでに1脚プリセットの浮きビットを、その円線の上に置き直している —
  ギミックは、動いている実物が1つ入っていないと誰も気づかない。
- 接地ロックオンの浮き上がりが 3 経路を塞いでもまだ残っていた。4 つ目は
  **フレームロックが相手の上昇速度を渡していた**もので、距離で効くため
  「近づいたときだけ浮く」という出方をしていた。実測すると、距離 6.4m で blend が 1 に
  乗った直後に vy が 0 → 8.8 まで立ち上がっていた。

## 7. デスクトップ版（Steam配信用）

Steam で配るには、ブラウザとローカルサーバが要らない**単体の実行ファイル**でなければならない。
そこで Electron のシェルを一枚かぶせている（[electron/main.js](electron/main.js)）。
**ゲーム側のコードは何も変わっていない** — 同じレンダラ、同じ固定ステップ、同じ DOM。
シェルが足すのは、これまでブラウザが代わりにやっていたことだけだ。

| | |
|---|---|
| `npm run game` | リリースビルドを作ってデスクトップアプリとして起動 |
| `npm run game:dev` | `npm run dev` を別で立てておき、そこに繋いで起動（ホットリロードのまま） |
| `npm run pack` | 配布フォルダ `release/win-unpacked/` を作る。**これがそのまま Steam の depot** |
| `BLOSTOM_SMOKE=1 <exe>` | 起動して、描画され、保存でき、全画面にできるかを確認して終了する |

### なぜ `file://` ではなく独自スキームなのか

ビルド済みのゲームは `game://` という**登録済みスキーム**から配信している。`file://` では

- **ES モジュールが読めない。** Chromium は file:// のモジュールを常に別オリジン扱いにする
- **localStorage が使えない。** 組んだ機体もキー設定もキーコンフィグも消える

`standard: true, secure: true` で登録したスキームは普通のセキュアなオリジンとして扱われるので、
**サーバに置いたときと1ビットも変わらない条件**でビルドが走る。

### ゲームとシェルの間

またぐ口は [electron/preload.cjs](electron/preload.cjs) の **4つだけ**：終了、全画面、
Steam の状態、実績の解除。`contextIsolation` は有効、`nodeIntegration` は無効、`sandbox` も有効。
共有コードで他人のビルドを読み込めるゲームが、ファイルシステムに一手で届いてはいけない。

ゲーム側は [src/platform/desktop.js](src/platform/desktop.js) 越しにしか触らない。
ブラウザではブリッジが無いだけで、**全ての呼び出しが安全に「できない」と答える**。
だからタイトル画面の「ゲームを終了」はデスクトップ版にだけ現れ、
「フルスクリーン」は両方に出る（ブラウザでは Fullscreen API に落ちる）。

### Steam に繋ぐ

現状は**繋ぐ用意ができた状態**で、実際の接続には App ID が要る。
[electron/steam.js](electron/steam.js) は Steam が無い前提で書いてあり、
クライアントが無くても App ID が無くてもネイティブモジュールが無くても、
**ゲームは同じように起動する**（起動を止めないことだけは絶対に守る）。

繋ぐ手順:

1. Steamworks で App ID を取得する
2. `npm install steamworks.js` — ネイティブバインディング
3. exe と同じ場所に `steam_appid.txt`（中身は App ID）を置く。
   クライアント外から起動したときに Steam が読む。`.gitignore` 済み。
   環境変数 `BLOSTOM_STEAM_APP_ID` でも指定できる
4. `npm run pack` して `release/win-unpacked/BLOSTOM.exe` を起動。
   タイトル画面の右下に `STEAM ・ <名前>` が出れば繋がっている

繋がると手に入るもの: **オーバーレイ（Shift+Tab）**、Steam が数える**プレイ時間**、
そして実績（`window.desktop.steam.unlock('ID')` → [desktop.js](src/platform/desktop.js) の
`unlockAchievement`）。実績名を1つも作っていなくても、この呼び出しは安全に何もしない。

### アップロードするもの

`npm run pack` が吐く `release/win-unpacked/` を**フォルダごと** depot に入れる。
Steam はインストーラを要求しない（Steam 自身がインストーラなので）。
起動ファイルは `BLOSTOM.exe`。

セーブデータ（機体・パーツ庫・キー設定・ベストスコア）は Electron の localStorage、
つまり `%APPDATA%/BLOSTOM/Local Storage/` に入る。
Steam Cloud に載せるなら、ここをファイルに移す作業が別途要る。

> **アイコンと exe のメタ情報は未設定。** Windows で exe の情報を書き換えるには
> electron-builder が symlink を含むツールを展開する必要があり、
> 開発者モードか管理者権限が要る。現在は `signAndEditExecutable: false` で回避しているので、
> 配信前にアイコンを入れるときはそこを戻すこと。

`media/blostom-promo.mp4` — 14.5秒 / 1280×720 / 30fps / H.264。

**リポジトリに残していない**（本体の動作に一切関係しないため）。

## 9. 現状の割り切り

たたき台なので、以下は意図的に単純化してある。

- 当たり判定は機体 1 個につき球 1 個（AABB との距離判定）。パーツ単位の被弾判定はまだない。
- 敵は撃ち返してこない。装備プレートを持つのはプレイヤー機だけで、敵 AI は間合いと回避のみ。
- 被弾判定は機体 1 個につき球 1 個。プレートを撃ち抜く、腕だけ壊す、といったことはできない。
- ブレードは「プレートの周りの球に入ったか」の判定で、実際の刃の当たりではない。
- 装備プレートを 1 枚も付けていない機体には、内蔵バルカン（ロック方向へのヒットスキャン）が
  そのまま残る。素の機体でもフィールドに出て遊べるようにするため。
- 敵 AI は「好みの間合いを保って左右にジンクする」だけ。アシスト側に予測させる素材が目的。
- フィールドは平地＋柱＋浮遊床の固定レイアウト。
- 加工は 1 ブロック単位。複数ブロックをまたぐ彫刻はできない。
- 浮遊パーツは見た目上そこにあるだけで、当たり判定や独立した挙動は持たない
  （連結先のセグメントと一緒に動く）。ビットが自律して飛ぶわけではない。
- アンドゥは文書全体のスナップショットなので、履歴の深さはメモリと引き換え。
  1/100 解像度を多用すると 60 手より手前で古い履歴が落ちる。
- パーツ庫は localStorage なので、ブラウザ・プロファイル・デスクトップ版をまたいでは持ち歩けない
  （持ち出すなら `書出` の JSON）。
