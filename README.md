# BroStom

ブロックでロボを組み立てて戦わせる、ロボット対戦ゲームのたたき台。
現状は **平面フィールドのデバッグ環境**、**エディタ**、**パーツ編集（ワークベンチ）** の 3 モード構成。

運動モデルは `ZMF (ZOE Motion Framework) Core v1.0.0` をそのまま実装している。

```bash
npm install
npm run dev
```

テスト:

```bash
npm test
```

描画・DOM を含む全網羅テストは `npm run dev` してから `/tests.html` を開く（詳細は 6 節）。

## 1. 2つのモード

| | |
|---|---|
| **EDIT** | コアブロックにパーツを生やしてロボを作る。設置・移動・寸法変更・ボクセル加工。 |
| **PART** | パーツ 1 個だけをじっくり作り込むワークベンチ。作ったものは「パーツ庫」に保存して EDIT で呼び出す。 |
| **TEST FIELD** | 平地アリーナに出て動かす。敵機 3 体（2脚・多脚・1脚）が相手をする。 |

右上の `▶ TEST FIELD` / ポーズメニューの「編集画面に戻る」で往復。エディタでは `Enter` でも出撃できる。

### エディタ操作

| 操作 | |
|---|---|
| 左ドラッグ / 右ドラッグ / ホイール | 視点回転 / 平行移動 / ズーム |
| クリック | パーツを選択、または設置 |
| **Ctrl+クリック** | 複数選択（もう一度で解除）。Mac は Cmd |
| **ギズモをドラッグ** | 選択したパーツを任意の位置へ移動・回転 |
| `V` | 選択 / 移動（統合済み） |
| `B` `L` `A` `F` `C` | ブロック / レッグ / アーム / フェイス / カスタム ボーン |
| **`G`** | **装備プレート**（左パネルで種類を選ぶ） |
| `T` / `R` | ギズモを移動 / 回転に切替 |
| `X` `Z` `P` | 削る / 盛る / 塗る（ボクセル加工） |
| `[` `]` | ブラシサイズ |
| `J` / `Shift+J` | **連結 / 連結解除** |
| **`Ctrl+Z` / `Ctrl+Y`** | **元に戻す / やり直し**（`Ctrl+Shift+Z` も可） |
| **`Ctrl+C` `Ctrl+X` `Ctrl+V`** | **コピー / 切り取り / 貼り付け** |
| `Ctrl+A` / `Ctrl+D` | 全選択 / 複製 |
| **矢印キー** | **選択パーツを微調整**（画面の向き基準・0.25刻み） |

| **`Ctrl+S`** / `Shift+S` | 保存 |

**加工中（削る／盛る／塗る）もカメラは動かせる。** 左ボタンはブラシ専用になり、
視点回転は右ドラッグ、平行移動は中ドラッグ、ズームはホイールに移る。

#### 矢印キーで詰める

ギズモのドラッグは 0.25 の格子に乗るが、**最後の数センチは矢印キーのほうが速い**。

- **画面の向き基準**で動く。カメラを回しても「→」は常に画面の右
- `Shift`+上下で高さ、`Alt` で 0.05 刻み（格子より細かく）
- 複数選択なら剛体としてまとめて動く。親と子を同時に選んでも子は二重に動かない
- 1回の押下が 1手のアンドゥ

#### パネルは今使うものだけ出す

寸法スライダを全部並べると、左パネルは画面の倍以上の長さになって、いま効く3つが
埋もれる。そこで **「ツール設定」には選択中のツールの設定だけを出す**。

- 選択 → ギズモ / ブロック → 新規ブロック寸法 / ボーン → 新規ボーン寸法 /
  装備 → プレートの種類と径 / 削る・盛る・塗る → ブラシと解像度
- ツール自体の並びは**作業の順番**にしてある。選ぶ → 組む（ブロック・装備）→
  ボーン（**フェイス → アーム → レッグ → カスタム**、ロボの上から下の順）→ 呼び出す
- 薄く表示するのではなく**消す**。薄いままでは場所を取り続けるので意味がない
- 「加工 (上級)」のツール一覧は既定で畳んである。キーボード（`X` `Z` `P`）で
  加工ツールに入ったときは自動で開く
- 右パネルの「パーツ庫」「色」「スペック」も見出しクリックで畳める（既定は畳んだ状態）

#### ヘルプ（F1）

上部バーの `？`、`F1`、`?` キーのいずれかで開く。ポーズ中のメニューからも入れる
（そのときは「テスト」の操作ページが開く）。ページは
**はじめに / 編集画面 / 形 / ボーン / 装備 / テスト**。

**中身は全部、ゲームが実際に使っているテーブルから生成している。**
装備テーブルにプレートを1行足せばヘルプにも出るし、キーを割り当て直せば
操作ページの表記もその場で変わる。手で書き写したヘルプは1週間で嘘になり、
**嘘のヘルプは無いより悪い**（読んだ人が試してから間違いに気付く分だけ損をする）。

このウインドウも縁のドラッグでサイズを変えられる。

#### ウインドウのサイズは自分で決められる

**左右のパネルも、キー設定・共有のポップアップも、縁をドラッグしてサイズを変えられる。**

- **内側の縁**で幅、**下の縁**で高さ、**角**で両方。掴める場所は触ると光る
- **ダブルクリックで既定サイズに戻る**
- サイズは `localStorage` に覚えるので、次に開いても広げたまま
- 画面の 60% より広くはできない（パネルだけになってしまうので）。
  小さい画面に切り替えたときも、画面からはみ出さないように詰め直す

実装で 2つ引っかかった点:

| 問題 | どうしたか |
|---|---|
| パネル自体がスクロールしていたので、縁に置いた掴み手が中身と一緒にスクロールして消える | パネルを**スクロールしない外枠**にして、スクロールを内側の `.panelscroll` に移した |
| 右パネルは画面右端に固定なので、右の縁を引いても伸びる向きが逆 | 右パネルの幅の掴み手は**左の縁**に置いた（実際に動くのはそちら側） |

画面中央に出るポップアップは、1px ドラッグしても縁は 0.5px しか動かないので、
**倍のゲイン**で追従させている（そうしないとポインタから置いていかれる）。


実測で、左パネルの中身は **1586px → 563〜674px**。ほとんどのツールでスクロールなしに収まる。

「左右対称でつける」を入れると ±X 位置の設置が自動でミラーされる。

### フィールド操作

| キー | |
|---|---|
| `W A S D` | 移動（機体前方基準、**A が右 / D が左**） |
| `W`/`A`/`S`/`D` を2回押し | **ダッシュ。前後左右すべて可能** |
| `Space` | 上昇 / 接地中はジャンプ。押しっぱなしで飛行 |
| `Shift` | 下降 |
| `E` | ブースト |
| `F` | ロックオン / 解除、`Tab` でターゲット切替 |
| `1` `2` `3` | ABC レイヤー切替（Active / Balance / Cooling） |
| マウス | 視点 |
| **左クリック** | **選択中の武器を撃つ** |
| **`C` / `X`** | **武器を次 / 前に切替** |
| **右ドラッグ**（`Alt`+マウス） | **カメラを機体のまわりで回す**（機体は向きを変えない） |
| **ホイール** | **ズーム。ブームの長さが伸び縮みする** |
| `R` | リスポーン |
| `Esc` | **ポーズ / 再開** |

**この表はゲーム内にも出ている。** フィールド上部の帯に、**武器のキーを先頭に**して現在の
割り当てが並ぶ。キーコンフィグで変えれば帯の表示もその場で変わるので、
「撃つボタンが分からない」が起きない。

**フィールドに入るとすぐゲームが始まる。** `Esc` でポーズすると、止まった画面の上に
**［再開］［リスポーン］［キー設定］［編集画面に戻る］** が出る。
マウスがロックを外れたときも自動でポーズ。

左右の割り当ては `InputManager` の `profile.invertStrafe` 1つで入れ替わる
（既定 true ＝ A が右）。

ダッシュは推力コマンドではなく **インパルス** として入る。スプールを通すと、わざと鈍く
してある後退プロファイルに後ろダッシュが吸われてしまうため。

### キーコンフィグ

**全アクションを自由に割り当て直せる。** 上部バーの `⌨` か、ポーズメニューの［キー設定］から。

- 行のキーをクリック → 押したキーがそこに入る（`Esc` で中止）
- `＋` で **1アクションに複数キー**（既定でも前進は `W` と `↑` の2つ）
- `×` で余分なキーを外す。**最後のひとつは外せない**（無言で操作不能になるのを防ぐため）
- マウスボタンも割り当てられる。`F5` `F11` `F12` `Esc` はブラウザ側に必要なので拒否する
- **1キー1役**。すでに使われているキーを割り当てると前の持ち主から取り上げ、
  「○○ から移しました」と表示する。取られた側が空になったときは
  **「○○ が未設定です」と警告し、その行を赤で表示する**
- 変更は localStorage（`brostom.keys.v1`）に保存。**既定から変えた行だけ**保存するので、
  あとから既定が増えても新しいキーがちゃんと入る
- ［初期設定に戻す］でいつでも全部戻せる

ゲーム側は**キーではなくアクションだけを読む**（`input.isDown('fire')`）。だから
割り当てを変えても、物理も武器もヒント帯も何ひとつ書き換えずに追従する。

## 2. パーツの仕組み

### コアブロック

銀色のブロック。ロボのルートで、削除できない。
**ローカル +Z が前方**（＝移動進行方向）、+Y が上。エディタの床に出ている水色の矢印がそれ。

### 配置：ソケットは廃止、位置は完全に自由

パーツの位置は **親の座標系における自由な position + rotation**。格子もソケットもない。

- **面をクリック** → その面にぴったり吸着して置かれる（従来のソケットと同じ結果）
- **何もない所をクリック** → 選択中パーツを通る水平な作業平面の上に置かれる
- 置いたあとは **ギズモで任意の場所へ**。0.25 / 15° スナップは切り替え可能
- インスペクタで座標・角度を直接数値入力もできる

**触れていないパーツを作れる。** ビットやファンネルのような浮遊ブロックはこれで作る。
プリセット「浮遊ビット FUNNEL」がその例。

パーツは位置とは別に **連動先（親）** を持つ。これは「どのパーツと一緒に動くか」だけを決める
もので、位置には一切影響しない。ボーンを連動先にすると、その関節から先で動く。
インスペクタの「連動先」で後から変えられ、変更しても見た目の位置は動かない。

複数選択したまま動かすと、剛体としてまとめて移動・回転する。親と子を同時に選んでも
子が二重に動くことはない（親だけに変換を適用し、子は階層で付いてくる）。

### 連結（コネクト）

**複数選択して `J` を押すと、最後に選んだパーツに他の全部が連結される。**
最後に選んだパーツ＝連結先は **水色の枠** で表示され、他は黄色。連結関係は
**緑の線** で描かれるので、何が何に付いているかが常に見える。

- ボーンの先で動いているブロックに連結すれば、**その関節で一緒に振れる**（ビットや増加装甲など）
- `Shift+J` でコアに戻す（連結解除）。位置は一切動かない
- 連結しても解除しても **見た目の位置は 1mm も動かない**。ワールド変換を新しい親の座標系に
  変換し直しているだけ
- 親と子を同時に選んでも、内部の構造は壊れない（最上位のパーツだけが付け替わる）
- 自分の子孫には連結できない（木が自分を食べてしまうため）

ボーンに **直接** 連結した場合は、中点より手前なら「固定側」、奥なら「可動側」になる。
どちらに入ったかはインスペクタと連結時のメッセージに出る。固定側だと動かないので、
動かしたいときはギズモで中点より先へずらせばよい。

### 装備プレート

**平べったいシールのような薄板**を、ブロックやボーンの好きな面に貼りつける。形は 2 種類だけに
統一してある。

| | |
|---|---|
| **〇 丸** | 武器プレート |
| **□ 四角** | その他プレート（効果はさまざま） |

厚みは固定で、変えられるのは**径だけ**（0.3〜1.6）。「機体にキットを貼った」ように見せたいので、
シルエットは揃えてある。面をクリックすればその面にぴたりと寝て、法線が外を向く。ボーンの側面に
貼れば、シャフトの表面に外向きで乗る。

#### 武器プレート（丸）

| | 弾数 / リロード | 撃ち方 | 弾色 |
|---|---|---|---|
| **ビーム** | **長く細い一線を撃つビームライフル。**威力は高いが連射は効かない（5発／リロード1.4秒） |
| **スナイパー** | 超長射程・高威力の一撃。**`Q` でスコープ**（画角が狭まって拡大される） |
| **レーザー** | **押している間、太いレーザーを撃ち続ける。**弾ではなく熱で払う。溜まりきると強制冷却 |
| **ガトリング** | 押しっぱなしで連射。30発でリロード3秒 |
| **ショット** | 3方向へ拡散。6発でリロード3秒 |
| **スプレッド** | 9発を大きく拡散。近ければ全弾当たる |
| **マグナム** | 至近距離用の一撃。射程は短いが非常に重い |
| **グレネード** | 山なりに飛ぶ爆弾。着弾点で小爆発（範囲ダメージ） |
| **ミサイル** | **小型5発をばらまいて追尾。**白い航跡を引く |
| **ブレード** | 押している間、**連結したブロックがまとめて光り**、触れた敵を削る |
| **シールド** | 機体を覆うバリア。**被弾を肩代わりし、体当たりでダメージ。**時間で消える |
| **ブースト** | **ブースト（`E`）が使えるようになる。**ダッシュの効果も小アップ（+14%、重ね貼りで加算） |
| **グラビティ** | **空中浮遊不可**になる代わりに耐久 +45%。**1枚しか付けられない** |
| **ローリング** | **貼りついたブロックを回し続ける。**向き（正転/逆転）と速さ（5〜400rpm）を選べる |
| **サークル** | 貼った場所を中心に、決めた半径の円に入ったパーツをまとめて回す |
| **フロート** | 常に地面から少し浮く。1枚のみ |


#### 撃ち方が違うものは、仕組みも違う

弾を飛ばすだけの武器ばかりでは同じものが並ぶので、**「何で払うか」**を分けてある。

| 払うもの | 武器 |
|---|---|
| **弾数** | ビーム / スナイパー / ガトリング / ショット / スプレッド / マグナム / グレネード / ミサイル |
| **熱** | レーザー（押している間ずっと溜まり、離すと冷める。溜め切ると強制冷却） |
| **時間** | シールド（張った瞬間から自分の時計で減る。トリガーは関係ない） |
| **接触** | ブレード（弾も熱もない。当たっている間だけ削る） |

- **レーザーは弾ではなく線**。毎フレーム、銃口から射程まで線分を引き、
  **最初に当たった1機だけ**を焼く（後ろの機体は前の機体が遮る）
- **グレネードは落ちる**。速度に重力を足しているだけで、着弾点で範囲ダメージ。
  距離に応じて減衰するので、直撃と至近弾で差が出る
- **マグナムの射程は寿命**。速度×寿命がそのまま届く距離になる（約36m）
- **シールドは `Robot.damage` の手前に入る**。吸収しきれなかった分だけが機体に届き、
  0 になったバリアはその場で割れる

#### スコープ

スナイパーを選んで `Q` を押している間、**カメラの画角を 42% まで絞る**。
カメラを動かさずに拡大するので、機体は今いる場所のままで狙える。離せば戻る。

#### ブースト

**ブーストは「巡航では届かない速度に連れて行くもの」**として調整してある。
巡航 18m/s に対して**ブースト時のピークは 31m/s（約1.75倍）**。

| | 変更前 | 現在 |
|---|---|---|
| 速度上限の倍率 | ×1.55 | **×2.35** |
| 推力の倍率 | ×1.55 | **×2.05** |
| ダッシュの初速 | 22 | **34** |
| ダッシュの再使用 | 0.42秒 | **0.26秒** |
| 立ち上がり | 0.035 | **0.018**（半減期） |

燃費も少し軽くしてある（0.40→0.34/秒）。**待たされるブーストは使われなくなる**ので、
立ち上がりと再使用の速さは速度そのものと同じくらい効く。

**ブーストは装備しないと使えない。** プレートが1枚もない機体は `E` を押しても何も起きないし、
燃料も減らない（`canBoost` が false のまま、入力を受け取る前に切れる）。

**噴射エフェクトはプレートそのものから出る。** 貼った面の向き（+Y）が噴射方向なので、
背中に貼れば後ろへ、腹に貼れば下へ吹く。ローリングと同じで**どこに貼るかがそのまま設定**。

- プレート面に**白いディスク**、そこから**円錐の炎**が伸びる。炎がカメラに対して真横を
  向いていなくても光源が読めるように、この2枚構成にしてある
- プレート中央のアクセントも一緒に増光する（emissive を 0.85 → 4.0 まで）
- 消えるときは**すぐ切れずに落ちていく**。パチンと消える推進器は「切った」ように見えて
  「使い切った」ようには見えないので
- 機体後方の汎用プルーム（推力に連動する円錐の噴射）はそのまま。ブーストの炎はそれとは別物

なお、以前は機体の原点に**放射状のスプライト**も置いていて、推力に応じて光っていた。これは
「コアブロックが光っている」ようにしか見えず、ダッシュのたびに胸が発光する見た目になっていた
（ダッシュ自体が発光させていたわけではなく、ダッシュ中はスプールが振り切れるため）。
プレートが自前の炎を持つようになった今、機体の真ん中で正体不明にぼやける光は
**どのパーツが仕事をしているのか**を分かりにくくするだけなので撤去した。噴射はプルームだけ。

実測: 素の2脚が最高 22.1 m/s のところ、背中にブーストを1枚貼ると **30.9 m/s**。

#### ローリング

**貼った面の向きがそのまま回転軸**になる。上面に貼れば水平に回り、側面に貼れば縦に回る。
どこに貼るかが設定を兼ねているので、軸を選ぶ UI がいらない。

- 回るのは**ブロックごと**。そのブロックに載っているもの（別のブロック、ボーン、他のプレート）も
  一緒に回る。レーダー、砲塔、観覧車、プロペラはこれで作る
- **編集画面でも回っている。**「常に回る」パーツが止まって見えるのはただの嘘なので、
  歩行プレビューとは無関係に常時回す
- **コアには貼っても回らない**（機体ごと回ってしまうため）。ボーンに貼っても回らない。
  どちらもインスペクタが赤字で警告する
- 左右対称配置でミラーすると、**対になったほうは逆回転**になる（左右のプロペラのように）

グラビティは「浮けなくなる」のであって「跳べなくなる」のではない。脚があればジャンプはできる。
できなくなるのは、上昇入力で重力を買い戻して**飛び続ける**ほう（4節「空中戦と地上戦の両立」の
`gravityScale` がそのまま 1 に固定される）。

2枚目のグラビティは、置こうとしても・型を差し替えようとしても・パーツ庫から移植しようとしても
弾かれる。ルールが 1 箇所ではなく、通り道すべてで効いている。

#### 弾はどこへ飛ぶか

ロックオン中は、**プレートごとに自分で偏差射撃を解く**。相手の位置と速度、そして
**その武器の弾速**から会合点を求めて、そこへ撃つ（不動点反復2回）。

機体のエイムアシストが向いている先ではダメだった。アシストは「機体を向けるためのリード」を
出していて、弾速の違う武器それぞれの正解ではないので、遠距離では丸ごと外れる。実測すると
25m の相手に62発撃って**命中0**だった。会合点で撃つようにしてからは、同じ条件で
62発中22発が当たる（残りは相手のジンクで避けられている、という健全な外れ方）。

結果として、**弾の速い武器ほど当てやすい**という当たり前の関係が自然に出る。
ロックしていないときは機体の正面へ素直に飛ぶ。

### ボーンを組むのが楽になる仕掛け

ボーンは「中央が関節、手前半分は動かない」という構造が強い代わりに、
**組んでフィールドに出るまで結果が分からない**のが弱点だった。そこを 3 つ潰してある。

**1. 関節が見える。** ボーンを1本選ぶと、その場に読み取り線が出る。

| | |
|---|---|
| **青い弧** | 可動範囲。`可動域` を変えると弧も広がる／狭まる |
| **黄色い線** | 回転軸そのもの（ヒンジ） |
| **緑の線** | **動く側**（関節から先端まで）|

「思っていたのと逆に曲がる」「なぜ動かない（＝固定側に付けていた）」が、
出撃せずに分かる。

**2. 先端にボーンを継げる。** インスペクタの `＋ 先端に○○ボーン` 一発で、同じ属性のボーンが
先端に生える。太腿→脛のような連結を、数ピクセルの棒の先端を狙ってクリックせずに作れる。

**3. 固定側／可動側をボタンで移せる。** ボーンに付いている子を選ぶと
`根元へ` `可動側へ` `先端へ` が出る。中点をまたぐドラッグを目分量でやらずに済む。

### カスタムボーンの動きを作る

「軸・振幅・速さ・ソース」だけでは、実際どう動くのか想像するしかなかった。

**動き方（波形）を選べるようにした。**

| | |
|---|---|
| **波（なめらか）** | サイン波。既定 |
| **往復（一定速）** | 三角波。等速で往復する |
| **パタパタ** | 矩形波。2つの角度を行き来する |
| **回転（ぐるぐる）** | **可動域を無視して回り続ける。**プロペラ、レーダー、タイヤ向け |

- **回転だけは可動域を無視する。** 70°で止まるプロペラはプロペラではないので
- 回転の駆動ソースは**角度ではなく回転速度**にかかる。速度連動にしておくと、
  減速したときに角度が巻き戻らず、回転がゆっくりになるだけで済む
- **中心角**（-90〜90°）で振れの中心をずらせる。「上向き45°を中心に±20°」が作れる
- **位相ずらし**（0〜1）で、同じ設定のボーン同士の動きをずらせる。多脚の波打ちや、
  左右で逆位相の腕はこれで作る
- **選択している間、編集画面でその動きが再生される。** 他の関節は止めたままなので、
  いま触っているボーンの動きだけが見える

### アンドゥ・リドゥ

**すべての編集操作が 1 手ずつ戻せる。** `Ctrl+Z` / `Ctrl+Y`、または左上の `↶` `↷`。

方式はスナップショット式で、変更の**直前**の文書全体（JSON、ボクセルは RLE）を積む。差分方式に
しなかったのは、彫刻・寸法変更・連結・パーツ移植が同じ木を別々の粒度で触るので、差分の定義自体が
操作ごとにばらけるため。スナップショットなら「復元 = `Assembly.fromJSON` してリグを組み直す」の
一手で、どの操作から戻ったかを気にしなくてよい。

- 履歴は **60 手 / 48MB** のどちらかに当たった時点で古いものから捨てる
  （1/100 解像度のブロックを何個も抱えたまま 60 手ぶん持つとメモリが破綻するため）
- ボタンの tooltip に「元に戻す: 削る」のように**何が戻るか**が出る
- 彫刻は **1 ストローク＝1 手**。ドラッグ中のフレームごとには積まない
- 履歴は**文書ごとに独立**。メイン機体とワークベンチのパーツは互いの履歴を汚さない
- プリセット読み込み・ファイル取込は履歴をクリアする（そこが新しい起点になる）

### コピー＆ペースト

`Ctrl+C` / `Ctrl+X` / `Ctrl+V`。複数選択したままでも動く。

コピーは選択パーツ（の配下ごと）を **独立した文書として切り出し**、貼り付けは
それを木に**移植**する。つまりコピペとパーツ庫は同じ 2 つの操作でできている:

| | |
|---|---|
| `Assembly.extract(id)` | 部分木を独立した文書へ。ルートは `block` に降格し、使っている色だけを持つ小さなパレットに詰め直す |
| `Assembly.graft(doc, parent, mount)` | 文書まるごとを別の木へ。ID を振り直し、パレットを併合し、貼り先のボクセル解像度に合わせる |

同じものを何度貼っても ID は衝突しない。コアをコピーしても、貼られる側は普通のブロックになる
（コアが 2 つある機体は作れない）。

### パーツ編集（ワークベンチ）とパーツ庫

上部の `パーツ編集` に入ると、**パーツ 1 個だけの文書**を編集する画面になる。ルートはコアではなく
ただのブロックで、機体と同じようにブロック・ボーンを生やし、寸法を変え、削って盛って塗れる。

- **`パーツ庫に保存`** … 名前を付けて localStorage（`brostom.parts.v1`）に保存。同じ名前は上書き
- **`新規`** … まっさらな 1 ブロックから作り直す
- **`← メイン編集`** … 機体編集へ戻る。**機体とパーツは完全に別の文書**なので、往復しても
  どちらの編集内容も履歴も失われない

メイン編集の右パネルに **パーツ庫** が出る。

- **`配置`** … スタンプツールが装填される。**置きたい場所をクリックするとその場に移植される**。
  面をクリックすれば吸着、何もない所なら作業平面の上。1 手で戻せる
- **`編集`** … そのパーツをワークベンチで開く（庫の中身とは独立したコピーなので、
  保存するまで元は変わらない）
- **`×`** … 庫から削除
- **`選択パーツを登録`** … 逆向き。**機体で選んでいるパーツを配下ごと庫に入れる**。
  作り込んだ腕を反対側にも使う、といった用途

### ブロックとサイズ

ブロックの面にさらにブロックやボーンを生やせる。

- **寸法は XYZ 個別に 0.25〜4.0 を 0.25 刻みで自由に変更できる**（インスペクタのスライダ）。
  隣り合うブロックの間隔は「双方の寸法の半分ずつ」で計算されるので、どんな寸法でも面がぴたりと合う。
- ボーンは **長さ**（0.5〜12）と **太さ**（0.04〜0.6）を自由に変えられる。細／中／太はプリセットボタン。

### ブロックの形（20種）

**ブロックは四角だけではない。** ツールパネルとインスペクタの「形」から 20 種類を選べる。

| 分類 | 形 |
|---|---|
| **基本** | 立方体 / 球 / 円柱 / カプセル / 六角柱 |
| **先細り** | ドーム / 円錐 / 円錐台 / 四角錐 / 八面体 |
| **角** | 四面体 / 面取り / 斜面 / 三角柱 / 階段 |
| **抜き** | 筒 / 輪 / アーチ / 十字 / 皿 |

#### 形は「別のジオメトリ」ではなく、ボクセルの詰め方

20種類を現実的な工数で入れるための一手。**形はマスク関数 1本**で、ブロックは今まで通り
ただのボクセルグリッドのままにしてある。おかげで

- **どの形でも削る・盛る・塗るがそのまま効く**（球を彫れる）
- グリーディメッシャ・保存・共有コード・当たり判定は**一切変更していない**
- **重さが勝手に正しくなる。** 質量は元から実体セル数で計算しているので、
  球は同じ寸法の箱の **約53%** の重さになる

代償は「球がボクセルの球になる」こと。ただしボクセルブロックで組む
ゲームなので、**なめらかな球のほうが浮く**。こちらが正しい側の割り切り。

#### 寸法に合わせて伸びる

マスクは **正規化座標**（各軸 -1..1）で判定している。つまり形は常にブロックの箱いっぱいに入る。
`2 × 0.5 × 1` のブロックに球を入れれば**潰れた楕円体**になる。円柱を薄くすれば板になる。
形 20 種 × 自由な寸法なので、実際に作れるシルエットはもっと多い。

#### 覚えておくこと

- **形を変えると中身は作り直される。** 彫った跡は消える（1手のアンドゥで戻せる）
- 複数選択したまま形を選べば**まとめて切り直す**。ボーンや装備プレートは黙って飛ばす
- 形は「何から切り出したか」の記録。そのあと彫れば、当然その通りにはならない
- **コアの面取りも今は形の 1つ。** 従来 `bevel(0.22)` で削っていたものと
  既定解像度 1/32 で**1セル違わず同じ**になるよう合わせてあるので、既存の機体の見た目は変わらない
- 古い保存データに形の情報は無いが、当時は全部四角だったので**そのまま四角として読む**
- **設置カーソルも選んだ形になる。** 「球」を選んでいるのに四角い枠が出ていたら、
  カーソルが嘘をついていることになる。プレビューは本番と同じ `VoxelBlock` と
  メッシャで切っているので、出るものがそのまま出る
  - ただし**解像度は 1/32 で頭打ち**。半透明のプレビューで 1/100 との差は見えないし、
    マウスを動かすたびに 100万セル刻むのは高すぎる。形ごとに 1回だけ切って使い回す
  - **白い枠線は箱のまま。** これは形ではなく**占有する範囲**で、次のパーツが
    どこに置けるかを決めているのはこちらなので

#### 解像度を上げると、彫っていない形は切り直す

加工の細かさを変えたとき、**まだ誰も彫っていないブロックは新しいグリッドで形を切り直す**。
再サンプルだと球の階段が拡大されるだけで、細かくした意味がないため。
一度でも彫ってあるブロックは従来通り再サンプルする（彫った跡を消さないため）。

### 加工（ボクセル）

1 ブロックの中身を削る／盛る／塗れる。刻みは **1辺あたり 1/16・1/32・1/50・1/100 から選択**（既定 1/32）。

> **1/100 は 1 ブロックあたり 100×100×100 = 100 万セル**になる。破綻せず編集できるよう、
> グリッドをチャンクに分割し、ブラシが触れたチャンクだけメッシュを作り直している。
> それでも 1/100 はメモリ 1MB/ブロックを食うので、既定は 1/32 にしてある。
> 解像度を切り替えると既存の形状は最近傍でリサンプルされる。

ブラシサイズは **ブロック辺長に対する %** で持っている。解像度を変えても削れる範囲は変わらない。

#### ブラシの形は立方体

**削る・盛る・塗るは、いずれも軸に沿った立方体で加工する。** 半径 r なら
`(2r+1)³` セルぴったり。

丸いブラシはグリッドに落とすと形が保たない。半径 1 の球は「中心＋面隣接 6 セル」＝
**十字（3D のプラス記号）**、正四面体は塊にはなるものの**斜めに欠けた楔**になり、
どちらも「どこがどう削れるのか」が読めない。立方体なら

- **カーソルの箱がそのまま結果になる。** 見えている通りに削れる／盛れる
- **常に正方形。** どの向きから見ても同じで、面と角がグリッドに揃う
- **同じクリックは必ず同じ形。** 半径はセル単位の整数なので、余裕（スラック）も要らない

ボクセルグリッドの上に四角いブロックを積んでいくゲームなので、加工の単位も四角が正しい。

#### 盛るはブロックの外へはみ出せる

**ブロックの外側を「盛る」と、その方向にブロックが 0.25 だけ伸びる。** 面で止まらない。

やり方はいくつか考えたが、採ったのは「**箱を伸ばして中身を組み直す**」案。

| 案 | 却下した理由 |
|---|---|
| はみ出した分を別ブロックとして生やす | 1つの形が細かいブロックに分裂して、あとで扱えない |
| グリッドをブロックの外にはみ出させる | 「ジオメトリは単位立方体空間」という前提が壊れる |
| **箱を伸ばして中身を再グリッド** | 採用。形も寸法も 1つのブロックのまま |

グリッドは常に n³ でブロックの箱ぴったりを覆うので、箱が伸びると**セルが大きくなり**、
既存の中身は新しいグリッドの一部分を占めることになる。そこで再グリッドでは
**新セルが覆う旧セルを全部見て、1つでも実体があれば実体にする**。
最近傍で拾うと 1セル厚のディテールが消えるが、この方式なら太る方向にしか転ばない。

- **既存の形はその場から動かない。** 箱の中心が半分ずれるぶん、ブロック自身の
  マウントを同じだけ動かして相殺する
- **そのブロックに付いているものも動かない。** 子のマウントを逆向きに同じだけ動かす。
  でないと「+X に伸ばしたら -X 側の腕まで一緒に動いた」ことになる
- コアにはマウントが無いので、そこだけは子だけが動く
- カーソルがブロックの外に出ると**黄色**に変わる（次のクリックで箱が伸びる合図）
- 上限は通常の寸法と同じ 4.0。超えるとトーストで断る
- 1回の拡張＋盛りが 1手のアンドゥ

加工が効くのは見た目だけではない：

- **質量は「実際に詰まっているボクセル体積」で決まる**
- **推力は「ブロックの表面積」で決まる**

つまり **中を刳り抜くと、推力そのままで軽くなる** = 機動性が上がる。
逆に **ブロックを大きくすると質量は体積（3乗）で、推力は表面積（2乗）でしか増えない** ので、
大型化は必ず鈍重になる。

### 色

- **標準色 16 色** … 固定。パレット先頭に常に居座るので、インデックスの意味が変わらない。
- **カラーサークル** … HSV の色相環＋明度スライダ＋16進入力。選んだ色はパレット末尾に追加され、
  カスタム色として並ぶ。保存時に、どのボクセルからも参照されていないカスタム色は自動で掃除される。

色はボクセル1つ1つがパレットの添字を持つ形で保存されるので、後から色を選び直しても
すでに塗った面の色は変わらない。

### ボーン

細長い骨パーツ。**中央が関節**で、手前半分は親側と一体、奥半分から先が可動部になる。

```
      親ブロック
          │
   ┌──────┴──────┐
   │  near half  │  ← 親と一体（ここに刺したブロックは動かない）
   ├─────●───────┤  ← 関節（ここが曲がる）
   │  far half   │  ← 可動（ここに刺したブロックが動く）
   └─────────────┘
          ↓ 先端にさらにボーンを繋げば「膝」になる
```

シャフトにはブロックを串刺しにできる。位置は自由なので、シャフト上のどこにでも置けるし、
シャフトから離して浮かせることもできる。**中点より手前なら親と一体、奥なら可動部**という
判定だけがあり、ギズモで中点をまたいで動かすと連動先の半分が自動で切り替わる。

| 属性 | 挙動 |
|---|---|
| **レッグボーン** | 脚。1 本なら跳ねる、2 本なら歩く、3 本以上は**多脚**歩行 |
| **アームボーン** | 腕。移動中は歩調と逆位相で振り、ロックオン中はロック方向を向く |
| **フェイスボーン** | 顔。進行方向に傾き、ロックオン中はターゲットを向く |
| **カスタムボーン** | 軸（前後／ひねり／上下）・振幅・速さ・駆動ソース（常時／**歩調**／速度／推力／衝撃／ロックオン） |

> **「脚 1 本 / 2 本 / 3 本以上」は “脚の本数” で数えている。**
> レッグボーンの総数ではない。腿＋脛のように 1 本の脚をボーンで繋いだ場合、
> 上流にレッグボーンを持たないボーンだけを 1 本の脚として数える。
> そうしないと「膝のある二足歩行」が作れないため。

#### 肩・股関節・腰は、種類を増やさずに属性で作る

肩ボーン・腰ボーン・股関節ボーン…と種類を足していくと、**組み合わせのぶんだけ
実装が増えて、しかもどれを使えばいいのか分からなくなる**。そこで種類は 4 つのまま、
**すべてのボーンに 2 つの数値**を持たせた。

| 属性 | 範囲 | 何を決めるか |
|---|---|---|
| **効き** (`gain`) | 0〜2 | その属性の動きを**どれだけ取るか**。0 で固定、1 で標準、2 で大振り |
| **ずらし** (`lag`) | 0〜1 | 歩調 1 周のうち**いつ動くか**。先端側ほど遅らせるとしなる |

これで、よくある関節はすべて既存のボーンで表せる。

| 作りたいもの | 作り方 |
|---|---|
| **肩** | アームボーンを腕の付け根に置き、効きを 0.4 程度まで落とす |
| **肘** | その先にアームボーンを繋ぐだけ（後述の自動減衰が働く） |
| **股関節** | 脚の根元のレッグボーン。効きは標準のまま |
| **膝** | その先のレッグボーン。ずらしを 0.05〜0.1 入れると脛が振れて見える |
| **腰** | カスタムボーンで軸「ひねり」、駆動ソース「**歩調**」 |

インスペクタには **肩／股関節／しなり／固定** のワンクリック設定も置いてある。

**アームの連鎖は自動で減衰する。** アームボーンの上にさらにアームボーンがある場合、
下側は「前腕」とみなして振り幅が `0.55^深さ` になり、少し遅れて追従する。
これがないと肩と肘が同じ角度だけ曲がり、**腕が二重に折れて**しまう。

**駆動ソース「歩調」** は、波の時計に**歩行サイクルそのもの**を使う。
自由な時計で回すと足の運びとだんだんズレていくが、歩調なら定義上ズレない。
腰のひねりに必要なのはこちら。止まれば歩調も止まるので、腰も止まる。

#### ボーンの向きについての注意

パーツの位置と回転は **常に親のローカル座標** で解釈される。ボーンの先端に別のボーンを繋ぐと、
その回転は「親ボーンのローカル軸」基準になる（ボーンのローカル +Y ＝ シャフト方向）。
横向きのボーンの先に「-Y 方向」を繋ぐと、下ではなく機体側へ折り返してしまう。
多脚プリセットは **股関節を真下に向けて生やし、開き（splay）はアニメーション側で付ける**
構成にしてあるのはこのため。

#### サークル：円の中にあるものを、まとめて回す

ローリングが「貼りついたブロックを回す」のに対して、サークルは
**貼った場所のまわりに立っているものを回す**。砲塔のリングや回転する足回りはこれ。

- **半径**をインスペクタで決める（0.5〜6.0m）
- 対象は**同じブロックの上に載っているパーツ**。その円に入っていれば、
  そこから先に繋がっているものは全部一緒に回る
- 判定は**軸に対して横方向の距離だけ**。高く伸びたパーツも、円の中に立っていれば回る
- インスペクタに「回るパーツ」の数が出る。0 なら半径が足りていない

どのパーツがリングに乗るかは**リグを組むときに決まる**（プレートの兄弟を集めて、
回転グループに付け替えている）。プレートを置いた時点では兄弟がまだ存在しないので、
これだけは木を組み終えてからの後処理にしてある。半径を変えると組み直す。

#### フロート：接地しない

**常に地面から 1.4m 浮いた状態で「着地」する。** 実装は乗り高（rideHeight）を
その分だけ上げているだけで、歩行も旋回もジャンプもそのまま動く。脚は宙に浮く。

**グラビティとは同時に装備できない。** 片方が「地面から離れない」、
もう片方が「地面に触れない」と言っているので、両立しようがない。
付けようとすると理由を出して断る。

#### 浮いている間の脚は、歩かない

床が無いのに歩容を再生すると「宙で足踏み」になる。そこでフロート装備時は
**歩調の時計そのものを止め**（腕は待機の揺れに落ち、歩調駆動の腰も止まる）、
脚は歩容ではなく**慣性**で動かす。

土台は 1本のベクトルだけ。**振り遅れ（legSway）** ＝
「加速の逆向きに放り出され、進行方向に引きずられる」を減衰で追わせたもの。
遅れて着いて遅れて止まるので、*保持されている*のではなく *ぶら下がっている* ように見える。

| 脚 | 動き |
|---|---|
| **1本** | 純粋な振り子。慣性が置いていった場所にいる。膝は伸び切らない |
| **2本** | ANUBIS のジェフティのように、少し後ろへ垂らして膝を軽く畳み、爪先を伸ばす。推力が強いほど後ろへ流れ、左右は逆位相でわずかに揺れる |
| **3本以上** | 内側へ円を描いて折り畳む（虫の飛行時）。関節ごとに同じ向きへ少しずつ多く曲げると、その連なりが弧になる。前脚は前へ、後脚は後ろへ畳むので、脚が真ん中で団子にならない |

> **符号について。** ストライド軸は `Z × S` で、`(Z × S) × S = -Z`。
> つまり**正の回転で先端は後ろへ**動く（横方向も同じで、正で内側へ）。
> フロートの姿勢はすべて「後ろ・内側が正」で書いてある。
> ぶら下がった脚は、生の軸の符号よりそちらの言葉のほうがはるかに素直に書ける。

### 耐久力と、負けたときの壊れ方

**HP はコアブロックのサイズと機体の重さで決まる。**

```
HP = 40 + コアの一辺² × 60 + 質量 × 5      （×グラビティの +45%）
```

コアの一辺は体積の立方根なので、`4×1×1` のような平たいコアも体積で正しく評価される。

| コア | HP（2脚・質量約9） |
|---|---|
| 0.5 | 95 |
| 1.0 | 144 |
| 1.5 | 231 |
| 2.0 | 359 |
| 3.0 | 752 |

- **タフさを買う手段はコアを大きくすること。** その代わりコア自体の質量で鈍くなるので、
  「硬いが遅い」「脆いが速い」がひとつのつまみで表現される
- 重さも効くが**穏やかに**。そうしないと「とりあえずブロックを盛る」が
  「コアを設計する」に勝ってしまう

#### 爆発とバラバラ

HP がゼロになると、機体は**自分のパーツのままバラバラになる**。

- 破片は**そのパーツのジオメトリと色をそのまま使う**。汎用のキューブを撒くと、
  このゲームの唯一の取り柄（自分が組んだ形が壊れる）を捨てることになるので
- 破片は死んだ瞬間の**そのパーツのワールド変換から**飛び出す。腕は腕の位置から、
  脚は脚の位置から離れていく
- 中心から外向き＋やや上向きに射出され、重力で落ち、地面でバウンドして転がって止まる。
  3〜4.5秒で消える
- 爆発は 白い閃光 → オレンジの火球 → 地面を走る衝撃波リング ＋ 火花。
  **大きさは機体の寸法から決める**（アリーナの寸法から決めたら核になった）

#### お試し：撃破したら復活する

デバッグフィールドなので、**倒された機体は 2.6 秒後に復活する**。

- 敵はプレイヤーから 34〜60m 離れたアリーナ内のどこかに、HP 満タン・弾倉満タンで戻る
- プレイヤーが落ちたときはスタート地点に戻る（通常のリスポーンと同じ経路）
- 復活待ちの機体は AI も物理も止まる。残っているのは転がっている破片だけ

### QRコードで共有する

上部バーの `⧉`（パーツ編集では ⧉ 共有）から、**いま編集しているものを QR とテキストコードで
持ち出せる**。機体でもパーツでも同じ画面。

書き出し:

- **QR** … 画面表示、［拡大］で全画面、［PNG保存］でファイル
- **テキストコード** … `BRO1:` で始まる1行。チャットに貼れる

読み込み:

- **QR画像をドロップ**（またはクリックして選択）
- **コードを貼り付け**
- 読み込んだものが**機体なら編集画面へ、パーツならパーツ庫へ**入る。
  作業中の機体がパーツ1個で上書きされることはない
- 取り込みは 1手のアンドゥで戻せる

#### 中身と、正直な制約

JSON をそのまま QR に入れるのは無理（2脚で 4.9kB、QRの上限は 2953バイト）。そこで
**deflate して base64url** にしている。2脚で **1.0kB**、4脚で 1.1kB。プリセットは全部収まる。

| | JSON | 共有コード |
|---|---|---|
| コアのみ | 1.5kB | 489B |
| 2脚 | 4.9kB | 1.0kB |
| 4脚 | 5.5kB | 1.1kB |

**制約: この密度の QR は小さく写すと読めない。** 実測で、129モジュールの QR は
1モジュールあたり約6ピクセル（＝760px 以上）ないと読み取りに失敗する。

- スマホで読むなら **［拡大］で全画面表示**してから写す
- ファイルで渡すなら **［PNG保存］（10px/モジュール、約1400px）をそのまま送る**。
  途中で縮小されると読めなくなる
- 細かく彫り込んだ機体はコードが伸びる。QR に入らない場合はその旨を表示して、
  テキストコードだけを出す

エンコードは `qrcode-generator`、読み取りは `jsqr`。どちらも実績のある実装で、
**書き出した QR を実際に jsQR で読み戻せることをテストで確認している**
（自前で QR コーデックを書くと、外部の読み取り機で検証できないまま
「読めない QR」を出荷する危険があるので避けた）。

## 3. 歩容

| 脚 | キー | 動き |
|---|---|---|
| 0 | `hover` | ホバー。脚はふわふわ流れるだけ |
| 1 | `hop`（単脚） | 接地で縮んで溜め、離陸で伸び、空中では畳む |
| 2 | `walk` | 位相反転のストライド＋片方向にしか曲がらない膝 |
| 3+ | `multileg` | **多脚**。左右交互＋前後スイープの位相配分 |

**脚は慣性の向きに踏み出す。** 真横に平行移動しているときは足も真横へ、斜め移動なら斜めへ。
機体のローカル水平速度から進行方向 D を出し、ストライド軸を `A = D × S` として毎フレーム
組み替えている（`Z×S` と `X×S` の線形結合で済む）。進行方向ベクトルは lerp ではなく
**角度で回して**いる — 真後ろへの反転を lerp すると原点を通って潰れ、後退時に足が
逆位相にならないため。

多脚は「前後のストライド」「振り出し時の持ち上げ」「膝の畳み」「外向きの開き」を別チャンネルで
駆動している。関節をどの軸で回すかは **バインド時にボディ座標から解いている**：

> ボーンを軸 A で回すと先端は `A × S`（S はシャフト方向）に動く。
> だから前へ踏み出したいなら `A = Z × S`、持ち上げたいなら `A = Y × S`。
> 真下に伸びた脚は `Y × S` が退化する ＝ 股関節では足を持ち上げられないので、
> その場合は持ち上げを膝に全部任せる。

これのおかげで、真下向きの脚でも横向きの脚でも、同じ「前へ踏み出す」が正しく出る。

### プリセット

**プリセットは 4 機とも「そのまま出撃できる状態」で組んである。**
ブーストは装備プレートがなければ使えないので、装備の無い機体を初期状態に置くのは
「動かない機体」を配ることになる。武装も同じ。

| プリセット | 歩容 | 武装 | その他 | 見どころ |
|---|---|---|---|---|
| **2脚 STRIDER** | walk | ビーム（右手）／ガトリング（左手）／ミサイル（胸） | ブースト×4 | **肩・肘・腰・膝**の作例。標準機 |
| **1脚 POGO** | hop | ショット（頭）／ブレード×2（腕）／ビーム×2（ビット） | ブースト×3 | 効き 1.2〜1.4 の大振り。接近戦 |
| **4脚 CRAWLER** | multileg | ガトリング（頭）／ミサイル×2（アウトリガー）／ビーム（尾） | **グラビティ**／ブースト | 重量機。飛べない代わりに耐久 +45% |
| **浮遊ビット FUNNEL** | hop | ビーム（前）／ショット×3（ビット）／ミサイル（脚） | **ローリング**×3／ブースト | 浮遊ビットが回り続ける |

**武器の並び順＝パーツ木の順**なので、出撃した瞬間に選ばれている武器が
「撃てない武器」にならないよう、近接武器は腕より上流に置かないようにしてある。

グラビティは 1 枚制限なので、積んでいるのは CRAWLER だけ。

- 右パネルの「スペック」に歩容バッジが出る。ただし**脚が0本のときは出さない**。
  「ホバー」は歩き方ではなく歩き方が無いことなので、出すと在りもしない歩行の
  調整を誘ってしまう。テスト中の右下の読み出しからも同じ理由で GAIT 行が消える

### 空中戦と地上戦の両立

仕様書は無重力前提だが、地上戦も気持ちよくする必要があるので次のように橋渡ししている。

- 重力は常にかかっているが、**上昇入力を握っている間だけ `gravityScale` が 0.14 まで落ちる**。
  「飛ぶと決めた瞬間に重さを買い戻す」ことで、空中では ZMF そのままの無重力挙動になり、
  離した瞬間から 0.3 秒で重さが戻ってくる。
- 接地中は推力が水平面に射影され、**脚の本数がそのままトラクション**になる（`grip`）。
- ζ（抗力）は接地中に少し増える。これが「地面に足が付いている感触」。
- カメラのブームはピッチに **42% しか追従せず、さらに水平から 20° 相当で頭打ち**にしてある。
  急降下時に真上からの視点になるのを防ぐため。

#### 接地中はロックオンしても浮き上がらない

真上の敵をロックオンすると機首が上を向く。これをそのまま素直に扱うと、機体は
**4つの経路で勝手に離陸してしまう**。接地中はそのすべてを水平面に閉じ込めてある。

1. **推力** … スプールを機体姿勢そのままで回すと、上を向いた機首が推力を揚力に変える。
   接地中は **ヨーだけの座標系** で推力を組み立て、垂直成分は上昇入力チャンネルだけに任せる。
2. **アシスト** … Pro-Nav の加速度指令は上空の敵を指すので、接地中は Y 成分を落とす。
3. **向心力アシスト** … 運動量を機首方向へ回すと、走る速度が上昇速度に化ける。
   接地中は水平成分だけを回し、垂直成分には触れない。
4. **フレームロック（§5 相対空間）** … ロックした相手は参照フレームとして登録され、
   その速度の一部を機体が「一緒に運ばれる」形で受け取る。相手が跳ねる機体だと、
   **近づいた瞬間にその上昇速度をもらって浮いてしまう**。接地中は
   **垂直成分だけを接地度に応じて落とす**（水平成分はそのまま）。地面に立っている間、
   乗っているのは地面であって相手ではない。

この 4 番目は「敵に近づいたときだけ浮く」という形で出るので厄介だった。フレームロックは
**距離で効き始める**（相手の半径の約 5.7 倍以内）ので、遠距離では何も起きない。

離陸したとたん 4 つとも解除されるので、空中では今までどおり機首方向に飛べるし、
大きな相手に持ち上げられる §5 本来の挙動も戻る。

#### そもそも接地中は機体が傾かない

上の 4 つは「浮かない」ようにする話で、**見た目**は別問題だった。真上の敵をロックすると
機体はのけぞったまま歩く。物理的には浮いていなくても、**浮きそうに見える**。

そこで接地中は、**コアブロックを常に地面と平行に保つ**ようにした。狙うのは
「傾く」のではなく「**向き直る**」ことでやる。

- 接地度に比例して、姿勢の目標ベクトルから**ピッチ成分だけを抜く**。ヨーはそのまま効くので、
  真上の敵でも機体はちゃんとそちらを向く
- **狙いは落とさない。** 抜く前のベクトルを `aimForward` として別に持っていて、
  フェイスボーン（頭）はそちらを向くし、武器もそちらへ撃つ。頭だけ見上げて胴は水平、になる
- ロックしていないときも同じ。マウスで上を向いてから離陸すると、**足が離れた瞬間に
  機首がそこへ向く**（`freeForward` にピッチが残っているため、スナップしない）
- 接地度でクロスフェードするので、ジャンプでも段差でも切り替わりが見えない
あわせて、接地中は注視点の上振れも抑えてあり、真上の敵をロックしても自機は画面内に残る。

### 追跡カメラを自分で回す

ブームは基本的に機体の後ろに付いてくるが、**右ドラッグ（または `Alt`+マウス）で
機体のまわりを自由に回せる**。ホイールでブームの長さも変えられる。

- 回している間、**マウスは機体ではなくカメラを動かす**。機首は動かない
- しかも**照準の振れとしてカウントしない**ので、カメラを回してもロックオンは外れない
  （ロックのソフト解除はエイム入力の大きさで判定しているため、ここが分かれていないと
  「見回したらロックが切れた」になる）
- ピクセル→角度の直接対応。エイムのようなレート＋エキスポ curve は通していない。
  カメラは手に 1:1 で付いてこないと壊れて感じる
- **止まっている間は回した位置を保つ。走り出すと後ろへ戻ってくる**
  （戻る速さは実速度に比例。横を向いたままの追跡カメラでは運転できないので）
- 真上・真下は少し手前で止まる（`lookAt` が破綻するため）
- 大きく回すと注視点が機体そのものへ寄る。前方リード点のままだと、正面から見たときに
  機体が画面外へ出るため
- ズーム倍率は **0.42〜2.8 倍**。リスポーンで角度は戻るが、**ズームは好みなので残る**

### 重さ・軽さの調整点

`computeStats()`（`src/core/Assembly.js`）が唯一の真実。ここから下流は全部これを読む。

| 出力 | 由来 | 効く先 |
|---|---|---|
| `mass` | 実ボクセル体積 + ボーン長×太さ² | 加速度、ABC の効き |
| `thrust` | ブロック体積^(2/3) の総和 + 脚の本数 | 最大加速度 |
| `weightClass` | 質量 0〜1 正規化 | ζ の粘性、旋回権限、マウス感度 |
| `agility` | 推力重量比 | スプール、最高速、FOV |
| `extent` | リグの外接半径 | 当たり判定、カメラブーム長 |
| `gait` | 脚の本数 | 歩容 |

## 動かし方の設計

### 試合は固定ステップで進む

**画面が何fpsでも、試合は 1/60 秒の固定ステップで進む。** 余った時間は次のフレームへ
繰り越し、1フレームで進めるのは最大4ステップまで。

以前は実フレーム時間をそのまま物理に流し込んでいた。これには3つ問題があった。

- **同じ操作が同じ結果にならない。** 走らせるマシンの速さで試合が変わるので、
  再現もリプレイもできない
- **重いフレームが1回入ると、その1回が巨大な1ステップとして積分される。**
  機体が壁を抜ける典型的な原因
- **遅れを取り戻そうとすると、さらに遅くなる。** 上限を切らない追いつき処理は、
  重いフレームがもっと重いフレームを呼ぶ悪循環になる

上限に当たったぶんは**捨てる**。時間の進みが遅くなって見えるが、これは回復できる。
追いつこうとして雪だるま式に崩れるほうは回復できない。

### 「試合を決めるもの」と「見え方を決めるもの」を分ける

`update()` は試合だけを進め、`present()` はカメラ・画面効果・読み出しだけを扱う。
**`present()` は試合を読むが、変えない。**

この線引きがあるから、

- 読み出し（HUD）は **30Hz に落とせる**。2Dキャンバスの全面再描画で、
  144Hz で毎フレーム描き直す価値がない
- カメラをどう振っても、bloom を切っても、**試合の結果は1ビットも変わらない**
- 重いときに削るなら `present()` 側から削れる、と場所が決まっている

### 乱数は種から再生できる

`Math.random()` を使っていた箇所（弾のばらつき、AIの回避、敵の湧き位置、命中判定）は
**種を持つ生成器**に置き換えた。試合は「どの種で、どのステップに何を押したか」だけで
完全に決まる。

**ストリームは2本に分けてある。**

| ストリーム | 決めるもの |
|---|---|
| 試合用 | 弾のばらつき、回避の向き、湧き位置、命中判定 |
| 演出用 | 破片、火花、画面の揺れ |

分けてあるので、**破片を多く出しても弾の飛ぶ先は動かない**。同じ生成器を共有していると
「演出が増えた回だけ弾がズレる」という、原因の分からないバグになる。

### 重い処理を、試合の事実で割り振る

遠くの機体は**姿勢の更新回数を落とす**（26m まで毎ステップ、55m まで2ステップに1回、
それ以遠は3ステップに1回）。飛ばしたぶんの時間は次の姿勢計算に渡すので、
歩調の速さは変わらない。

**割り振りの根拠は「機体間の距離」＝試合の事実であって、フレーム時間やカメラの向きではない。**
これは重要で、姿勢は銃口の位置を決める＝試合に影響するため、
画面都合で決めると同じ操作が同じ結果にならなくなる。

（視錐台カリングのような**描画だけ**の間引きは逆に、実時間やカメラで決めてよい。
同じ「間引き」でも、試合を変えるものと変えないものは別物として扱う。）

### 計算を1回に

| 直したもの | 何が起きていたか |
|---|---|
| ワールド行列の更新 | 機体を組み終えたあと**1回だけ**更新する。以前は武器側が毎フレーム再度全走査しており、約200オブジェクト×機体数ぶん、同じ行列を2度計算していた |
| 弾の向き付け | 定数ベクトルを**毎フレーム・毎弾**確保していた |
| 回転パーツの更新 | 2つの配列を毎回結合していた（多くの機体では空の配列を作るためだけに） |
| AIの進行方向 | ベクトルを毎ステップ複製していた |
| 読み出しの座標計算 | 毎描画でベクトルを2本確保していた |

**実測（機体4体、同一条件）**

| | 変更前 | 現在 |
|---|---|---|
| 1ステップの試合処理 | 1.55 ms | **0.42 ms** |
| 1フレームの表示処理 | （試合処理に同居） | 0.16 ms |
| 読み出しの再描画 | 毎フレーム | 30Hz |

## 絵づくり

見た目は「暗い場所で、光るものが光って見えること」に賭けている。この game は
ほぼ真っ暗な中で、**意味のあるものがだいたい光源**（ビーム、曳光弾、スラスター、
ブレード、爆発、装備プレートの発光）だから、そこを描けるかどうかで全部決まる。

### 1枚のポストチェーン

シーンは **HDR ターゲットに1回描いて、画面に1回解決する**。その間に明るい部分を
抜き出してぼかす。全部で小さなパス5枚、`src/game/PostFX.js` に閉じてある。

```
scene → [HDR target, MSAA×4]
          ├→ bright pass (1/2)  → blur H,V (1/4) → blur H,V (1/8)
          └→ 最終合成（bloom + 色収差 + スピードライン + 粒子 + ビネット + トーンマップ）
```

- **明度抽出は 1/2、ぼかしは 1/4 と 1/8。** いきなり 1/4 に落とすとテクセルを
  飛ばすので、ビームや曳光弾のような**細い明るいものがチラつく**。1回きれいに
  半分にしてから落とすのがそれを止める
- **2スケール合成。** 光源のすぐ周りの締まったグローと、遠くまで広がるハローは
  1つのぼかし半径では両立しない。光は両方やる
- **ソフトニー付きのしきい値**。硬く切ると、明るさがしきい値を跨ぐたびに
  bloom が点いたり消えたりしてチラつきに見える
- **ブルームのコストは、ポスト有効時のフレームの約19%**（実測、ソフトウェア
  ラスタライザ上での比率）。`setBloom(0)` でチェーンごと丸ごと飛ぶ

### アンチエイリアス

**シーンをターゲットに描いた時点で、キャンバスの `antialias: true` は何もしない。**
ずっとギザギザだったのはこれが理由で、いまはオフスクリーンターゲット自体に
**MSAA×4** を要求している。

### 空と、金属が映すもの

`src/game/Sky.js` が**手続き的な空**を1枚作る。64×256 のキャンバスに縦方向の
グラデーションを描き、PMREM に通してラフネス別のミップにしたもの。

- **見える背景であり、同時に `scene.environment`。** 映り込みと目に見える空が
  食い違いようがない
- ボーンやプレートは metalness の高い金属で、**映すものが無い金属はただの黒い染み**。
  ライトを何本足しても解決しないのはこれ
- 環境光が入ったぶん、**半球ライトは 1.45 → 0.62 に落とした**。両方全開だと
  二重に照らして立体感が消える
- アリーナと編集画面で色味だけ変えた同じ仕組みを使う

### アリーナ

| | 変更 |
|---|---|
| 床 | 反射を少し拾う暗い金属寄りに。外周に**光るリング**（ここが終わりだと遠くからも分かる） |
| 柱のキャップ | 発光を 1.4 → 2.1 に。**bloom が拾うのはここ** |
| 地平線 | 外周に**遠景のビル群**を加算で並べた。フォグで消えるだけの縁ではなく「遠く」になる |
| フォグ | 空の地平線バンドと同じ色に。距離が空に溶ける |
| リムライト | 冷たいのと暖かいのの2本。1本では、動き続けるカメラのある角度でしか効かない |

### 機体

- ボーンの `envMapIntensity` を上げた。**空を映してはじめて機械加工の金属に見える**
- プレートの発光を 0.85 → 1.9 に。**1を超えないと bright pass が拾わない**＝
  光らないランプになる
- ブースターの炎の芯は逆に**落とした**（0.8 → 0.55）。bloom が自前で光を撒くので、
  そのままだと中心が白飛びする

## 5. ディレクトリ

```
src/
  core/        データモデル：Assembly（パーツ木＋自由配置）/ VoxelBlock（チャンク分割グリッド）/
               Random（種から再生できる乱数）/
               Shapes（ブロック20形状のマスク）/ Palette（色）/ Rig（→Three.js階層）/
               Share（共有コードの圧縮と復元）
  zmf/         運動モデル。シーンには一切触らない
  anim/        Animator：属性ごとの手続き型モーション
  game/        Sky（手続き的な空と環境マップ）/ World / Robot / SimpleAI / FieldScene / Hud / PostFX /
               Weapons（弾のプール＋プレートごとの弾倉・リロード・照準）/
               Debris（撃破時の爆発と、自分のパーツで散る破片）
  editor/      EditorScene：設置・ギズモ移動・複数選択・寸法変更・ボクセル加工 /
               History（スナップショット式アンドゥ）/ PartLibrary（パーツ庫）
  ui/          EditorUI（DOMパネル）/ Help（使い方・テーブルから生成）/
               KeyConfig（キー割り当て画面）/
               ShareDialog（QRの生成と読み取り）/ ColorWheel /
               dom（h・slider・折りたたみ）/ style.css
tests/         Vitest スイート（ロジック）
tests/browser/ ブラウザ内スイート（描画・DOM）
```

層はこの順に一方向依存になっている。

```
Assembly (データ)  →  Rig (Three.js)  →  ZMFBody (運動)  →  Animator (見た目)
```

ブロックのジオメトリは **単位立方体空間** で作られ VoxelBlock 側にキャッシュされる。
実寸はメッシュのトランスフォームに乗るだけなので、**寸法を変えてもメッシュは作り直されない**し、
リグを組み直しても彫刻結果は失われない。

機体のセーブは localStorage（`brostom.assembly.v1`）、パーツ庫は別キー（`brostom.parts.v1`）。
`書出` / `取込` で JSON ファイルにもできる。旧フォーマットも読める：
v1（gauge 名でボーン太さを持っていた頃）と v2（ソケット＝面／スロット指定）は、読み込み時に
自由な position + rotation へ変換される。ソケットで表現できたことは自由変換の特殊ケースなので、
情報は失われない。

**脚が無いときの歩容表示**（バッジもHUDの行も出ないこと）、
**フロートとサークル**（浮くこと・グラビティとの排他の理由表示・半径スライダで乗り手が変わること・1手のアンドゥ）、
**ブロックの形**（パネルに 20個並ぶこと・選ぶと切り直されること・
ツールが持っている形で置かれること・1手のアンドゥ・複数選択・
20種すべてが実際にメッシュになること・球も彫れること）、
**関節の効き**（パネルの説明とワンクリック設定・効き 0 で止まること・保存で残ること）、
全プリセットの飛行、ポストプロセスと HUD の描画までを通す。
結果はページ上と `window.__TEST_RESULTS` に出る。

> テスト間の yield は `setTimeout(0)` ではなく `MessageChannel` を使っている。
> バックグラウンドのタブではタイマーが「1分に1回」まで絞られるので、
> setTimeout だとスイートが遅くなるのではなく **止まる**。
>
> ブラウザスイートはアプリと同じオリジンで動くので、起動時に localStorage の
> `brostom.assembly.v1` と `brostom.parts.v1` を消して白紙から始める。
> **残しておきたい機体・パーツがあるなら、走らせる前に `書出` で JSON に出しておくこと。**

### テストで見つけて直したもの

書きながら実際に潰れたバグ（どれも手触りに直接効く場所だった）:

- `slew()` がスティックを離した瞬間（目標 0）を「符号反転」と誤判定し、常に上昇レートを使っていた。
  仕様の非対称スプール（後退の制動 Jerk を高くする）が効いていなかった。
- `smoothstep()` が逆順の境界（減少ランプ）を扱えず 0 を返していた。
  §8.1 の「エネルギー限界付近のジッター振動」が一度も発火していなかった。
- `KineticFeedback` が範囲外の衝撃値をそのままシェーダ uniform に流していた。
- カメラのブームがピッチ追従を減衰させるだけでは足りず、急降下で真上に回り込んでいた。
- 多脚のボディバウンドが、脚数ぶんの周波数で振動して平滑化に吸われ、見えなくなっていた。
- 空のタンクでもブーストの燃料を請求し続けていた。
- 複数パーツを同時にドラッグすると、共有していた一時行列が上書きされ、2個目以降に
  壊れた変換が適用されていた。
- 親と子を同時に選択して動かすと、子に変換が二重に適用されていた。
- 進行方向ベクトルを lerp していたため、真後ろへ歩いても足が反転しなかった。
- 選択の重心を溜めていた一時ベクトルを、連結線の描画が上書きしてギズモの位置がずれていた。
  （共有一時変数の使い回しで踏んだ 3 件目。数値は必ずテストで押さえている。）
- 彫刻のアンドゥ 1 手ぶんを積む処理がポインタハンドラの中に直書きされていて、
  ストロークを API から始めると履歴に残らなかった。`beginStroke()` として切り出した。
- ローリングの回転数が壊れたセーブから `NaN` になり得た。`clamp(NaN)` は `NaN` のままなので、
  ブロックのクォータニオンごと汚染して機体が消える。数値でない値は既定へ落とすようにした。
- ポーズメニューのテストがボタンを**添字**で押していた。ボタンを1つ増やしたら
  「リスポーン」ではなく「キー設定」を押すようになり、**フィールドがポーズしたまま**
  後続のテストに渡って、無関係な移動テストがまとめて落ちた。ラベルで探すよう直した。
  （以前 1 度だけ観測した field mode の同時失敗も、おそらく同じ形の状態漏れだった。）
- 「弾が飛んでいること」を、あるフレームの生存数だけで見ていた。近距離では撃った弾が
  数フレームで消えるので、たまたま 0 になって落ちる。バースト全体の最大値で見るよう直した。
- 弾の当たり判定がフレーム端点のサンプルだけだった。ガトリングは 1 フレームで約 3m 進むので、
  それより細い相手を**すり抜けていた**。線分と球の最近接距離で掃引するように直した。
- 武器の照準を機体のエイムアシストに任せていたら、25m の相手に 62 発撃って命中 0 だった。
  アシストのリードは「機体を向ける」ためのもので、弾速ごとの会合点ではない。
  武器ごとに偏差を解くようにして 22/62 命中（残りは相手の回避）。
- 接地ロックオンの浮き上がりが 3 経路を塞いでもまだ残っていた。4 つ目は
  **フレームロックが相手の上昇速度を渡していた**もので、距離で効くため
  「近づいたときだけ浮く」という出方をしていた。実測すると、距離 6.4m で blend が 1 に
  乗った直後に vy が 0 → 8.8 まで立ち上がっていた。

## 8. 現状の割り切り

たたき台なので、以下は意図的に単純化してある。

- 当たり判定は機体 1 個につき球 1 個（AABB との距離判定）。パーツ単位の被弾判定はまだない。
- 敵は撃ち返してこない。装備プレートを持つのはプレイヤー機だけで、敵 AI は間合いと回避のみ。
- 被弾判定は機体 1 個につき球 1 個。プレートを撃ち抜く、腕だけ壊す、といったことはできない。
- ブレードは「プレートの周りの球に入ったか」の判定で、実際の刃の当たりではない。
- 装備プレートを 1 枚も付けていない機体には、内蔵バルカン（ロック方向へのヒットスキャン）が
  そのまま残る。素の機体でもフィールドに出て遊べるようにするため。
- 敵 AI は「好みの間合いを保って左右にジンクする」だけ。アシスト側に予測させる素材が目的。
- フィールドは平地＋柱＋浮遊床の固定レイアウト。
- 加工は 1 ブロック単位。複数ブロックをまたぐ彫刻はできない。
- 浮遊パーツは見た目上そこにあるだけで、当たり判定や独立した挙動は持たない
  （連結先のセグメントと一緒に動く）。ビットが自律して飛ぶわけではない。
- アンドゥは文書全体のスナップショットなので、履歴の深さはメモリと引き換え。
  1/100 解像度を多用すると 60 手より手前で古い履歴が落ちる。
- パーツ庫は localStorage なので、ブラウザ・プロファイルをまたいでは持ち歩けない
  （持ち出すなら `書出` の JSON）。
